# Реальное время для `/app`: журнал изменений в gateway и поток SSE

- **Дата:** 2026-10-12.
- **Статус:** дизайн согласован с владельцем решения по разделам; спецификация ждёт ревью.
- **Связано:** [frontend#1](https://github.com/JustIkra/umir-frontend/issues/1), [factory#2](https://github.com/JustIkra/umir-factory/issues/2), [gateway#19](https://github.com/JustIkra/umir-gateway/issues/19) (списание по сроку через gateway), [gateway#10](https://github.com/JustIkra/umir-gateway/issues/10) (предупреждения о конце сессии).

## 1. Цель и рамки

Экраны рабочего приложения `/app` обновляются без перезагрузки. Нужно три сценария:

1. **Несколько экранов сразу.** Продажа на кассе, приём поставки или правка справочника сразу обновляют остатки, стоп-лист, рекомендации и историю на других открытых экранах.
2. **Время и сроки.** Списание по сроку и окончание сессии видны без перезагрузки. Метки вида «истекает через 6 ч» и окно сроков перерисовываются.
3. **Мгновенный итог команды.** Результат действия приходит сразу. Если итог ещё неизвестен (`ConfirmationPending`), попытка проверяется, как только меняется состояние, а не по таймеру.

**Вне рамок:**
- Публичная часть: лендинг, документы, форма обратной связи.
- Перенос действий на поток: заказы, поставки, справочники и вход остаются HTTP-запросами с текущими правилами CSRF и идемпотентности.
- Повтор пропущенных событий, несколько реплик gateway, хранение журнала между перезапусками.
- Интерфейс предупреждений о конце сессии: он остаётся в gateway#10.

## 2. Принятые решения

| Решение | Причина |
| --- | --- |
| Поток сервер → клиент на SSE (`text/event-stream`), без WebSocket | Данные идут только в одну сторону. SSE — обычный HTTP: браузер сам переподключается, cookie `SameSite=Strict` и отсутствие CORS исключают межсайтовое чтение, а `tests/http` проверяет поток тем же клиентом. |
| Поток передаёт сигнал, данные перечитываются существующими GET | Модели чтения остаются в одном контракте (OpenAPI) и проверяются существующими тестами. Сигнал не дублирует схемы и не устаревает при их изменении. |
| Журнал изменений хранится в памяти gateway | Все изменяющие запросы проходят через gateway. Позже журнал станет очередью запросов, поэтому он устроен как её предшественник (раздел 4). |
| Списание по сроку запускает gateway | Таймер склада записывает `BatchExpired` без внешнего запроса, и журнал такие записи не видит. Подробно — в gateway#19. |
| Поток и фоновые запросы не продлевают сессию | По ГОСТ Р 52872-2019, 2.2.1, сессию продлевает только действие пользователя. |

Gateway не разбирает тела бизнес-запросов и ответов. Журнал оперирует методом, путём и HTTP-статусом, поэтому правило «доменный BFF в gateway не добавляется» (`docs/go-architecture.md`) сохраняется.

## 3. Архитектура и поток данных

```
браузер ──HTTP──► nginx ──► gateway ──► serving / warehouse
   ▲                          │
   │                          ├─ журнал изменений (память процесса)
   │                          ├─ планировщик списания по сроку (gateway#19)
   └──SSE /api/live◄──────────┘   ← сигналы журнала, такт, состояние сессии
```

1. Gateway проксирует изменяющий бизнес-запрос, как сейчас.
2. По итогу ответа gateway добавляет запись в журнал.
3. Если состояние могло измениться, все открытые потоки получают событие `change` с новым номером записи.
4. Frontend помечает общие данные устаревшими и перечитывает видимые экраны обычными GET.

## 4. Журнал изменений

**Что записывается:**
- изменяющие запросы (`POST`, `PUT`, `PATCH`, `DELETE`) под `/api/serving/` и `/api/warehouse/`;
- `PATCH /api/operator/me/display-name`, потому что имя оператора видно на всех экранах;
- запуски списания по сроку (gateway#19).

Вход, выход, смена пароля и обратная связь в журнал не попадают. Изменения сессии передаёт событие `session`.

**Запись содержит:**

| Поле | Значение |
| --- | --- |
| `seq` | Порядковый номер в пределах `epoch`, растёт на 1 без пропусков |
| `at` | Время записи, Москва `+03:00` |
| `source` | `request`, `expiration` или `external` |
| `method`, `path` | Метод и путь без строки запроса; для `expiration` и `external` пусто |
| `status` | HTTP-статус ответа; пусто при транспортной ошибке |
| `outcome` | `success`, `pending`, `rejected` или `unknown` |
| `count` | Для `expiration` — число списанных партий |

Тела запросов и ответов, идентификаторы сессий, IP и заголовки в журнал не записываются.

**Как определяется `outcome`.** Только по HTTP-статусу, без разбора тела:

| Статус | `outcome` | Состояние могло измениться |
| --- | --- | --- |
| 2xx, кроме 202 | `success` | да |
| 202 | `pending` | да |
| 4xx | `rejected` | нет: владелец отказал этому запросу |
| 5xx, тайм-аут или транспортная ошибка | `unknown` | да |

`rejected` не порождает событие `change`, остальные исходы порождают. Сигнал после `success` может оказаться лишним: например, `prepareOrder` или ответ `EmptyOrder` ничего не меняют. Лишний сигнал стоит одного перечитывания видимых экранов. Ради точности gateway пришлось бы разбирать тела ответов, поэтому это допустимая цена.

**`epoch`.** Непрозрачная строка от 1 до 64 символов. Создаётся при старте gateway через подставляемый генератор ID. После перезапуска gateway журнал пуст, `epoch` новый, а `seq` начинается с 1.

**Объём.** Кольцевой буфер последних записей, настройка `JOURNAL_CAPACITY`, по умолчанию 1000. Буфер нужен для диагностики и будущей очереди. Клиенты читают только последний номер.

**Интерфейс для будущей очереди.** Компонент `journal` в gateway:
- `Append(entry) → seq` — добавить запись;
- `Last() → (epoch, seq)` — последний номер;
- `Subscribe(ctx) → <-chan struct{}` — пробуждение после записи, которая могла изменить состояние;
- `Entries(after) → []Entry` — записи после номера, для диагностики.

Записи добавляются под одной блокировкой. Пробуждение не блокирует запись: канал подписчика с буфером 1 означает «есть новое». Очередь запросов позже добавит записи в состоянии «принят» до отправки запроса. Нынешние записи соответствуют завершённым.

**Изменения вне журнала.** Свежая операция склада сама записывает наступившую просрочку, поэтому списание может случиться внутри проксируемого чтения. Gateway сравнивает `stateVersion` из ответов своих плановых запусков списания. Если версия изменилась, а записей `request` с момента прошлого удачного запуска не было, добавляется запись `external` с `outcome: unknown`. Так замечается и перезапуск склада: версия падает до 0.

**Неудачные запуски.** 5xx, тайм-аут или неразобранный ответ дают одну запись `expiration` с `outcome: unknown` на серию неудач подряд, а не на каждый запуск. Иначе недоступный склад будил бы экраны каждую секунду. Отказ соединения и 4xx записи не дают.

## 5. Поток `GET /api/live`

**Ответ:**
- `200` с заголовками `Content-Type: text/event-stream; charset=utf-8`, `Cache-Control: no-store` и `X-Accel-Buffering: no`;
- первая строка — `retry: 3000`;
- каждые 15 с служебный комментарий `: ping`.

**События.** Поле `data` содержит одну строку JSON:

| `event` | `data` | Когда |
| --- | --- | --- |
| `change` | `{"epoch": string, "seq": DecimalString}` | При подключении (текущий номер) и после каждой записи, которая могла изменить состояние. Несколько записей подряд склеиваются в одно событие с последним номером. |
| `tick` | `{"serverTime": MoscowTimestamp}` | При подключении и в начале каждой минуты по времени gateway. |
| `session` | `{"idleExpiresAt": MoscowTimestamp, "absoluteExpiresAt": MoscowTimestamp}` | При подключении и после продления сессии действием пользователя. Для запомненной сессии оба поля равны абсолютному сроку. |
| `session-ended` | `{"reason": "signed_out" \| "revoked" \| "expired"}` | Выход из любой вкладки, отзыв сменой пароля, наступление срока. Затем поток закрывается. |
| `upstream` | `{"available": boolean}` | `false` после трёх подряд неудачных запусков списания (склад недоступен), `true` после первого успешного. При подключении отправляется текущее значение. |

**Ошибки:**

| Статус | Когда | `code` в problem JSON |
| --- | --- | --- |
| `401` | Нет действующей сессии; cookie первого шага входа не подходит | `Unauthenticated` (существующий ответ) |
| `403` | `Sec-Fetch-Site` присутствует и не равен `same-origin` | `InvalidOrigin` (существующий ответ `CsrfRejected`) |
| `405` | Метод не `GET` | `MethodNotAllowed` (существующий ответ) |
| `429` | Больше 8 потоков на сессию или 64 на gateway | `TooManyStreams` (новый) |
| `503` | Режим восстановления учётной записи | `AuthUnavailable` (существующий ответ) |

После любой из этих ошибок браузер не переподключается: `EventSource` закрывается на ответе, отличном от `200 text/event-stream`.

## 6. Сессия и безопасность

- **Проверка без продления.** Операторский сервис получает операцию `Peek(id)`: проверяет сессию так же, как `Authenticate`, но не сдвигает `lastSeen` и не пишет файл аккаунтов. Её используют `/api/live`, пинги, такты и фоновые запросы.
- **Фоновые запросы.** Запрос с заголовком `X-Umir-Activity: background` проходит те же проверки, что и без заголовка: сессию, а для изменяющих методов — ещё CSRF и `Origin`. Отличие одно: используется `Peek`, и сессия не продлевается. Заголовок только отказывается от продления, поэтому злоупотребить им нельзя. Запросы без заголовка продлевают сессию, как сейчас. Заголовок действует и на `GET /api/operator/me`: с ним маршрут отвечает тем же профилем и сроками через `Peek`, без продления и без записи файла аккаунтов.
- **Уведомления о сессии.** Сервис сообщает об изменениях через внедряемый порт `SessionObserver`: продление, выход, отзыв. Вызов идёт после фиксации и вне мьютекса сервиса. Поток подписан на изменения своей сессии.
- **Наступление срока.** Поток держит таймер на ближайший из `idleExpiresAt` и `absoluteExpiresAt` и переставляет его при продлении. Когда срок наступает, поток вызывает `Peek`; если сессия истекла, отправляет `session-ended` с `expired`.
- **Межсайтовые запросы.** Cookie `SameSite=Strict` не уходит с чужих сайтов, а чужая страница без CORS не может читать поток. Проверка `Sec-Fetch-Site` — дополнительная защита.
- **Ресурсы.** Лимиты 8 и 64 потоков. Каждому клиенту — очередь на одно сообщение, где хранится последнее состояние.

## 7. Frontend

Поток подключается только внутри `/app` после входа. По слоям:

- **application** — порт `LiveFeed` с методом `subscribe(onEvent, onStatus) → unsubscribe`. События — строгое объединение `change | tick | session | session-ended | upstream`. Статус соединения: `connecting | open | closed`.
- **adapters/live** — обёртка над `EventSource('/api/live')`. По ESLint `EventSource` разрешён только в `src/adapters`. Каждое `data` проверяется во время выполнения; некорректное событие отбрасывается и считается сбоем потока.
- **application/live-sync** — сценарий синхронизации. Порт, часы и планировщик подставляются снаружи.

**Реакция live-sync:**
- **`change`, тот же `epoch`, больший `seq`** → общие данные помечаются устаревшими: остатки, сроки, история, справочники, меню, стоп-лист, рекомендации, профиль. Номер не больше уже известного → ничего.
- **`change` с новым `epoch`** → gateway перезапускался. Все модели перечитываются, сравнение номеров начинается заново.
- **Попытки `ConfirmationPending`** → `resolve` вызывается при каждом новом `change` и после переподключения. Вызовы идут по одному, с теми же `commandID` и `proposalID`.
- **`tick`** → обновляется время сервера, перечитываются окно сроков и рекомендации, перерисовываются относительные метки. Метка только форматирует серверный `expiresAt`. Решение «истекло» остаётся за сервером.
- **`session`** → обновляется хранилище сроков сессии.
- **`session-ended`** → поток закрывается без переподключения и открывается экран «сессия истекла».
- **Поток закрылся (`closed`).** `EventSource` закрывается на любом ответе, кроме `200 text/event-stream`, и не сообщает статус, поэтому `401` от него не отличить от `502`. Live-sync один раз на обрыв проверяет сессию фоновым `GET /api/operator/me`:
  - `401` — сессия закончилась: поток останавливается навсегда, открывается экран «сессия истекла»;
  - `200`, другой ответ или сетевая ошибка — новая подписка через 3 с, а отсчёт 10 с до «устаревших данных» не сбрасывается.
- **`upstream: false`, а также поток не открыт дольше 10 с** → экраны показывают состояние «Устаревшие показанные данные» из дизайн-брифа со временем последнего успешного чтения.

**Перечитывание:**
- Перечитываются только видимые экраны. Скрытая вкладка откладывает запросы до `visibilitychange` и делает один запрос, если что-то изменилось.
- Если запрос уже идёт, а данные снова помечены устаревшими, после него выполняется ровно один запрос.
- Экран применяет только ответ на свой последний запрос. Ответы на более ранние отбрасываются: порядок задаёт счётчик запросов клиента, а не `stateVersion`.
- Перечитывание по сигналу или такту идёт с `X-Umir-Activity: background`. Запросы, вызванные пользователем, — без него.
- Presentation получает данные через хук на `useSyncExternalStore`, а сценарии — из контекста сервисов. Прямых `fetch` и `EventSource` в presentation нет.

## 8. Тайм-ауты и сбои

- **Nginx** (frontend). Отдельный `location = /api/live`:
  - `proxy_http_version 1.1` и `proxy_set_header Connection ""`;
  - `proxy_buffering off`, `proxy_cache off`, `gzip off`;
  - `proxy_read_timeout 60s`.
- **Gateway.**
  - `/api/live` не проходит через общий `withDeadline` (`UPSTREAM_TIMEOUT`).
  - Перед каждой записью — срок 5 с через `http.ResponseController`. Клиент, не принявший запись за 5 с, отключается.
  - При остановке потоки закрываются через `RegisterOnShutdown`, и браузер переподключается к новому процессу.
- **Перезапуск gateway.** Журнал теряется, `epoch` меняется, клиенты перечитывают всё. Сессии хранятся в файле аккаунтов и переживают перезапуск.
- **Недоступность склада или serving.** Чтения возвращают свои ошибки, как сейчас. Недоступность склада дополнительно видна по `upstream`.

## 10. Тесты

**Gateway (Go):**
- **Журнал:** номера идут без пропусков; `outcome` по таблице статусов; `rejected` не будит подписчиков; кольцевой буфер; ни тел, ни идентификаторов в записях.
- **`/api/live`:**
  - коды 401, 403, 405, 429;
  - первое `change` содержит текущий номер, а несколько записей подряд дают одно событие;
  - пинги и такты идут на подменённых часах;
  - поток переживает `UPSTREAM_TIMEOUT`, а медленный клиент отключается.
- **Сессия:**
  - поток и запросы с `background` не продлевают сессию и не пишут файл, а обычный GET продлевает;
  - `session-ended` при выходе, отзыве и истечении сессии;
  - событие `session` после действия пользователя.
- **`external`:** запись появляется, если версия выросла без записей `request`.

**Frontend (Bun):**
- **live-sync:** номера только растут, новый `epoch` сбрасывает сравнение, запросы склеиваются, скрытая вкладка ждёт.
- **Последний запрос:** ответ на ранний запрос не применяется.
- **Устаревшие данные:** состояние включается через 10 с.
- **Попытки:** `resolve` вызывается один раз на сигнал.
- **Конец сессии:** `session-ended` останавливает поток.
- **Адаптер:** разбор событий и отбрасывание некорректных.

**Factory, `tests/http`** — через реальную цепочку nginx → gateway → serving/warehouse:
- поток отдаёт `change`, `tick`, `session` и `upstream`;
- `POST` поставки даёт новый `change` в течение 2 с;
- отклонённая поставка (409) не даёт `change`;
- после перезапуска gateway `epoch` новый;
- выход даёт `session-ended`;
- фоновый запрос не сдвигает `idleExpiresAt`;
- партия с коротким сроком даёт `change` без запросов браузера (gateway#19).

**Браузер (Playwright)** — когда появятся экраны `/app`. Две вкладки: поставка в одной видна в другой; список сроков обновляется сам.

## 11. Порядок работ

Каждый пункт — отдельный PR в своём репозитории со ссылкой на эту спецификацию:

2. **warehouse:** маршрут списания, удаление тикера (gateway#19).
3. **gateway:** журнал, `/api/live`, `Peek` и фоновые запросы, `SessionObserver`, планировщик списания (gateway#19).

5. **factory:** `tests/http` по разделу 10.

## 12. Известные ограничения

- **Лишние сигналы.** Успешный запрос, ничего не изменивший, вызывает лишнее перечитывание (раздел 4).
- **Изменения вне журнала** замечаются при ближайшем запуске списания, то есть с задержкой до `EXPIRATION_RUN_INTERVAL` (1 с).
- **Одна реплика gateway.** Журнал и подписки живут в памяти одного процесса. Это совпадает с текущим ограничением gateway («Несколько реплик gateway не поддерживаются»).
- **Без повтора событий.** Пропущенные события не повторяются: после переподключения клиент получает текущий номер и перечитывает данные.

# ADR 0002. PostgreSQL, RabbitMQ и Redis для durable-стека

Дата: 15.10.2026. Статус: принято 15.10.2026. Часовой пояс: Europe/Moscow.

Этот ADR заменяет ADR 0001 («PostgreSQL и RabbitMQ для продовой сборки»). ADR 0001 так и не попал в `main`: он существует только на ветке prod-readiness, коммит `bcb573e` (`docs/adr/0001-postgres-rabbitmq.md`). Читать его можно командой `git -C <umir-factory> show bcb573e:docs/adr/0001-postgres-rabbitmq.md`. С момента принятия ADR 0002 действует только он; ветка prod-readiness как источник решений больше не используется, её заготовки служат лишь исходным материалом для эталона `reference/durable`.

Решения пользователя U1–U8 и правила R1–R20 взяты из главной спеки оркестрации durable-стека (раздел 2 и 3), решения C1–C53 — из её раздела 10. Таблица «решение → пункт» ниже связывает каждое решение ADR с этими пунктами. Числа сроков хранения и бюджетов допуска остаются предложением до шлюза G1, их утверждает пользователь.

## Контекст

Сейчас состояние живёт в памяти процесса или в файлах: Warehouse и Serving держат всё в памяти, Auth пишет один JSON-файл, Feedback ведёт JSONL-журнал, у Gateway в памяти журнал изменений для SSE и эпоха процесса. После рестарта склад и заказы пропадают, эпоха меняется, клиенты получают `RuntimeReset`.

Целевая сборка должна переживать рестарт любого сервиса, работать в двух репликах Gateway и Serving и выдерживать масштаб одной ячейки: до 100 организаций × 1–100 ресторанов. Хостинг прежний: одна ВМ, docker compose за Nginx Proxy Manager (ZeroTier).

ADR 0001 решал часть задачи: Postgres и RabbitMQ без Redis, одна реплика на сервис, Auth одним документом, эпоха в базе, RLS «следующим шагом», импорт текущих данных. После сверки планов группы приняли другой набор решений. Ниже записано, что из 0001 сохраняется и что меняется.

## Решение

### 1. Что переносится из ADR 0001 без изменения смысла

1. **Postgres — единственный источник истины.** База и роль на каждый сервис с состоянием: Auth, Warehouse, Serving, Feedback. Сервисы не читают чужие базы. Один кластер Postgres 17.
2. **Драйвер — `github.com/jackc/pgx/v5` (`pgxpool`), без ORM и генераторов запросов.** Тонкие обёртки в `internal/adapters/postgres`: пул (размер, таймауты, `application_name`), перевод ошибок драйвера в ошибки портов с сохранением причины, запуск миграций.
3. **`InTx(ctx, opts, fn)`.** Повторяет транзакцию при SQLSTATE `40001` и `40P01`, не больше 3 попыток. Если исход `COMMIT` неизвестен (обрыв соединения после отправки), `InTx` возвращает отдельную ошибку неизвестного исхода и не повторяет вслепую: решение о повторе принимает вызывающий код по идемпотентному ключу команды.
4. **Миграции.** Файлы `NNNN_name.sql`, встроенные через `embed`, применяются только вперёд. Применение идёт в транзакции под `pg_advisory_xact_lock` с ключом сервиса. Учёт ведёт таблица `schema_migrations(version int primary key, name text not null, applied_at timestamptz not null)`. Применённую миграцию менять нельзя. Сервис, увидевший в базе схему новее своего кода, отказывается стартовать.
5. **Секреты — файлами.** DSN, URL брокера и Redis, ключи сервисов приходят из `*_FILE`. Значений секретов нет ни в окружении, ни в аргументах процессов, ни в логах.
6. **Интеграционные тесты** идут под build tag `integration` и `make integration`, на настоящих Postgres, RabbitMQ и Redis. Каждый тест создаёт собственную временную базу, vhost и префикс Redis и удаляет их в конце. Пропуск теста при отсутствии переменных окружения запрещён: набор падает с понятной ошибкой. `FLUSHALL` и `FLUSHDB` запрещены.
7. **Брокер — RabbitMQ 4**, клиент `github.com/rabbitmq/amqp091-go`. Kafka не берём: replay из брокера не нужен, источник истины — Postgres.
8. **Outbox и идемпотентные потребители.** Сообщение пишется в outbox в той же транзакции, что и бизнес-факт; relay публикует с publisher confirms; потребитель идемпотентен, ack после обработки, переподключение с backoff.
9. **Warehouse — event store** (append-only журнал событий с оптимистичной конкуренцией по версии потока ресторана, снапшоты). Семантика повтора и границы страниц повторяют адаптер в памяти, контрактные тесты общие для обоих адаптеров. Детали схемы принадлежат подспеке Warehouse.

### 2. Что меняется относительно ADR 0001

#### 2.1. Redis добавлен (U3, R7, C17, C47)

ADR 0001 заявлял «Redis не нужен». Теперь нужен, но только как общее краткоживущее состояние реплик и кеш. Redis никогда не источник истины и не входит в бэкап.

- **Два экземпляра.** `redis-limiter` — лимиты, бюджеты допуска и аренды Gateway: AOF `appendfsync everysec`, политика `noeviction`, заданный `maxmemory`. `redis-cache` — кеш: без персистентности, `allkeys-lru`; стартовый `maxmemory 512mb`, число уточняет нагрузочная приёмка R13.
- **Доступ.** Свой ACL-пользователь на сервис, права только на свой префикс `umir:<owner>:<kind>:…` (`owner` — `gw` или `wh`; `auth` в схеме префиксов зарезервирован, но у Auth Redis нет, C51). Команды `FLUSH*`, `CONFIG`, `KEYS`, `DEBUG`, `SHUTDOWN` запрещены.
- **Кеш сейчас нужен только Warehouse** — для захватов страниц (C27): один захват не больше 16 MiB, квоту по размеру Warehouse ведёт сам под `umir:wh:`. Кеш чтений (меню, рекомендации, `/access`) добавляется по замерам R13, решение выносится на G2. До замеров его в коде нет.
- **Маркер непрерывности limiter** (R7, C47). Ключ `umir:limiter:generation` записывает задание `redis-init` при каждом `up` и `restore`; сервисы лишь сравнивают его с `<SVC>_LIMITER_GENERATION`. Если маркера нет или он расходится, limiter на самое длинное окно политики (не больше 1 ч) переходит в строгий режим: квоты сжаты до минимума, но не до нуля. Начало окна фиксирует `SET umir:limiter:strict_since <now> NX`, общее для всех реплик; по окончании окна любая реплика восстанавливает маркер командой `SET umir:limiter:generation <значение> NX` и удаляет `strict_since`. Полное закрытие входа на час после перезагрузки ВМ недопустимо. Барьера в Postgres нет: у Gateway нет базы, а надёжные бюджеты безопасности Auth лежат в Postgres.
- **Auth без Redis** (C51). Бюджеты по клиенту и preauth держит Gateway; надёжные бюджеты Auth (выдачи кодов, лимиты по адресу и логину, неверные коды) остаются в Postgres в одной транзакции с действием.

#### 2.2. Аренды фоновых работ (C4)

- Сервисы с базой (Auth, Warehouse, Serving, Feedback) держат аренды в Postgres: таблица эталона `worker_leases(name PK, holder, fence bigint, expires_at)`. Относится и к relay outbox: строки outbox захватываются через `claimed_by`, `claim_fence`, `claim_expires_at`. Вместо `pg_try_advisory_lock` из ADR 0001 действует аренда с fencing-токеном: устаревший держатель не может записать результат.
- Redis-аренды только у Gateway: планировщик просрочки (R6) и лимиты потоков SSE.
- Блокировка предложения Serving — строка с lease и fence в самой таблице предложений. Это не фоновая работа и в эталон не входит.

#### 2.3. Gateway по-прежнему без базы (R3, R4)

- У Gateway нет Postgres. Он перестаёт быть пиром жизненного цикла Auth (R3): множество ресторанов и надгробия берёт из реестра Auth по ревизии и сам закрывает scope удалённых.
- Live (R4): владелец пишет событие в outbox в одной транзакции с изменением; relay публикует в `umir.events`; каждая реплика Gateway держит свою exclusive auto-delete очередь и небольшое ленивое кольцо на ресторан в памяти. Redis cache не источник replay. Разрыв последовательности, рестарт или чужой экземпляр в курсоре дают `refresh-required`.

#### 2.4. Реплики сейчас (U7, C19, C20)

ADR 0001 откладывал две реплики на «следующий шаг». Теперь они часть цели:

- в целевом compose по две реплики Gateway и Serving; Warehouse и Feedback — по одной, но без состояния в процессе, то есть готовы к двум;
- в приёмке по зонтичному плану #17 ещё и вторая реплика Auth (профиль `auth-ha`);
- factory задаёт уникальный `INSTANCE_ID` каждой реплике (`gateway-a`, `serving-b` и т. д.);
- SSE закрепляется за репликой по сессии на frontend Nginx (`hash … consistent`); Gateway кладёт в курсор и в `epoch` SSE случайный boot-nonce независимо от `INSTANCE_ID`.

#### 2.5. Эпоха заменяется storage generation (R2, C9, C19)

- `runtimeEpoch` на проводе сохраняет формат, но означает **storage generation**: она стабильна при рестарте и при смене реплики и меняется только при сбросе или восстановлении базы на более раннюю историю. Это записано в дополнении DUR1 ([docs/durable-api-amendment.md](../durable-api-amendment.md)), а не меняется «молча».
- Generation создаёт первая миграция: строка `storage_meta` с `gen_random_uuid()`. У всех сервисов с базой одинаковые подкоманды `migrate`, `serve`, `generation rotate --reason <текст>`; последняя выполняется только при остановленном сервисе и под ролью-владельцем. `serve` без generation не стартует и ключей не создаёт.
- Идентификатор экземпляра процесса отделён от generation и виден в health, логах и (единственное исключение, C19) в `epoch` SSE и курсоре Gateway.

#### 2.6. RLS обязателен, две роли на сервис (R8, C5, C8)

ADR 0001 оставлял RLS «следующим шагом». Теперь это условие готовности:

- На сервис две роли: `umir_<svc>_owner` — владелец таблиц, используется только заданием `migrate-<svc>`; `umir_<svc>` — среда выполнения, не владелец, `NOBYPASSRLS`. Сам себя ни один сервис не мигрирует. DSN владельца (`<SVC>_MIGRATE_DATABASE_URL_FILE`) видит только это задание.
- При старте каждый сервис вызывает `AssertRuntimeRole` (роль не суперпользователь и не владелец) и `VerifySchema` (схема не новее кода, см. п. 1.4).
- Контекст ставит обёртка транзакции из эталона: `Scope{Actor, OrgID, RestaurantID, UserID}` и `InSystemTx(ctx, reason)`; переменные `umir.actor` (`tenant`, `user`, `anonymous`, `system`), `umir.org_id`, `umir.restaurant_id`, `umir.user_id`. Хелперы SQL для политик тоже в эталоне; своих GUC у групп нет.
- Утечку контекста через пул проверяет тест с настоящей ролью, а не с владельцем.

#### 2.7. Auth нормализуется по таблицам

Документ `authority` из ADR 0001 §1.8 (один агрегат в `bytea` с compare-and-swap по ревизии) отменён. Auth хранится построчными таблицами с очисткой по сроку (R9); шифрование полей и ключи владельца читаются из смонтированного только на чтение каталога `owner.json` v2, который создаёт `secrets.sh` (C6, C52). Импорт `auth.json` не делается (п. 2.10).

#### 2.8. RabbitMQ: один узел, quorum-очереди, не HA (U2, C1–C3, C38)

- **Не HA.** Один узел RabbitMQ 4. Quorum-очереди дают лишь устойчивость к рестарту процесса и порядок записи, но не отказоустойчивость узла: кластера из трёх узлов нет, потеря ВМ означает потерю брокера. Это решение пользователя, и оно записывается так же явно в README. Потерянные сообщения восстанавливаются из outbox: источник истины — Postgres.
- **Один vhost `umir`**, пользователь на сервис с правами по шаблону имён. Права `.*` на весь vhost, как было в заготовках, запрещены. Таблица прав — в [docs/durable/events.md](../durable/events.md).
- **Топологию объявляет только задание `mq-init`** (C2): обменники и durable-очереди с retry и DLQ. Сервисы объявляют лишь собственные exclusive-очереди, остальное проверяют пассивно.
- **Обменники.** `umir.events` (topic, единственный производитель — Warehouse, C38), `umir.auth` (topic, уведомления жизненного цикла Auth, C1), `umir.tasks` (direct: `auth.mail`, `feedback.smtp`, `feedback.telegram`), `umir.dlx`. Вместо одного `umir.events` из ADR 0001.
- **Очереди.** Задачи — quorum, retry-очередь с TTL 30 с, `x-delivery-limit` 5, затем `.dlq`. Fan-out: exclusive auto-delete `gateway.live.<instance>`, `gateway.auth.<instance>`, `serving.auth.<instance>`; durable quorum `feedback.auth` (только при включённом профиле Feedback). Gateway привязывается к `warehouse.#`.
- **Конверт и политика `mandatory`** (C3, C30, C45) описаны в [docs/durable/events.md](../durable/events.md). Для `umir.events` и всех ключей `umir.auth` неотмаршрутизированное сообщение считается опубликованным (accept, растёт метрика), для ключей `umir.tasks` — ошибка конфигурации и повтор (retry). События Auth — только подсказки, они не дают прав.
- **Outbox и inbox** (C4): единая форма `outbox(id uuid PK, position bigserial UNIQUE, exchange, routing_key, headers jsonb, body jsonb, org_id, restaurant_id, created_at, not_before, published_at, routed, attempts, claimed_by, claim_fence, claim_expires_at)` и `inbox(consumer, message_id, received_at, PK(consumer, message_id))`. Срок опубликованного outbox 7 дней, inbox 14 дней (R9, предложение до G1). Цель задержки relay: p95 не больше 1 с.
- **Без брокера** сервис стартует, `readyz` показывает деградацию возможности `events`, outbox копится и уходит после восстановления.
- **Доставка писем и обращений** (R18): строка задания в Postgres (аренда, попытки, исход) — источник истины, RabbitMQ — транспорт-будильник с повторами и DLQ; внешняя доставка остаётся at-least-once.

#### 2.9. Конфигурация и запрещённая память (R20, C10, C32, C33)

- Переменной `<SVC>_STORAGE` нет, режима `memory` в боевых бинарниках нет: бинарник без DSN не стартует, запасного пути «база недоступна → память или файл» нет. Memory-адаптеры живут только в тестовом коде (C46). Это отменяет §1.4 ADR 0001.
- Если заданы и файл, и переменная DSN, это ошибка (эталонный `LoadDSN`), а не «побеждает файл», как в 0001.
- Контракт имён переменных и таблица команд — [docs/durable/configuration.md](../durable/configuration.md). Auth сохраняет JSON-конфигурацию `UMIR_AUTH_CONFIG_FILE`, её пишет генератор factory.
- У каждого сервиса `GET /healthz` (процесс жив) и `GET /readyz` (возможности `ok|degraded|down`); healthcheck compose смотрит `/readyz`. Эндпоинтов метрик нет: приёмка читает SQL владельцев, management API RabbitMQ, `INFO` Redis и логи. Логи Postgres, RabbitMQ и Nginx без ПДн.

#### 2.10. Чистый лист, импорта нет (U4, R1)

ADR 0001 предусматривал `server import-json`. Теперь данные текущего стенда не переносятся: импортёры JSON Auth и JSONL Feedback, экспорт памяти Warehouse и Serving не пишутся. Новый стек стартует с новой storage generation и пустыми базами. Старые тома стенда новым стеком не монтируются и не удаляются без отдельного поручения. Откат = запуск старых образов на старых томах, пока новый стек не принял записей.

#### 2.11. Эталон копируется, не импортируется (R15)

Общие адаптеры пишутся один раз в `reference/durable` — отдельном Go-модуле со своими интеграционными тестами: пул и `InTx`, миграции под advisory lock, RLS-контекст, `worker_leases`, outbox relay, inbox-потребитель, connector AMQP, Lua-скрипт допуска Redis, аренда Redis с fencing. Сервисы копируют код в `internal/adapters/{postgres,rabbitmq,redis}` с комментарием-источником (`umir-factory reference/durable@<sha>`). Межсервисных Go-модулей и новых репозиториев нет.

#### 2.12. Отказоустойчивость и безопасность канала

- **Postgres и Redis без HA, RabbitMQ не HA.** Один контейнер каждого. Защита данных — бэкап: `pg_dump` и `pg_restore` по каждой базе под согласованным `stack.sh backup --consistent`; цели RPO не более 24 ч и RTO не более 1 ч проверяются учением по восстановлению. **Остаточный риск одной ВМ принят** (Q10): потеря ВМ — это потеря данных до RPO, копии за пределами ВМ обеспечивает пользователь. Риск записан в README.
- **TLS на проде** к Postgres, RabbitMQ и Redis: `verify-full` с общим частным CA (`sslrootcert`, `amqps://`, `rediss://`), как во FIN1. Тестовая инфраструктура работает без TLS. Заготовки с `sslmode=disable` не переносятся.
- **Часы** (R12). Все сервисы на одной ВМ, допуск на расхождение `iat` нулевой; требование записывается в README, `stack.sh preflight` сравнивает часы.

## Последствия

- Рестарт любого сервиса не теряет данные и не меняет storage generation. Generation меняется только явной ротацией при восстановлении или сбросе; клиенты после этого получают `RuntimeReset` или `refresh-required`, и это снова означает реальную потерю состояния.
- Сборка получает четыре вида хранилищ (Postgres, RabbitMQ, `redis-limiter`, `redis-cache`) и задания `migrate-<svc>`, `init-auth`, `mq-init`, `redis-init`. Порядок старта и права закреплены в compose factory; сервисы без заданий не стартуют.
- Единая точка отказа — ВМ. Потеря ВМ означает потерю Postgres, брокера и Redis; восстановление идёт из бэкапа с RPO до 24 ч. Этот остаточный риск принят (Q10), включая отсутствие HA у Postgres, Redis и RabbitMQ.
- Потеря RabbitMQ не теряет бизнес-факты: они в outbox. Потеря `redis-limiter` не закрывает вход, а включает строгий режим на окно не более 1 ч.
- Копирование эталона даёт независимые релизы сервисов, но требует `copy.sh --check`, чтобы расхождения с `reference/durable` были видны.
- Контракт DUR1 меняет смысл `runtimeEpoch`, вводит ревизию реестра, статус попытки `Interrupted`, `CommandConflict` и лимиты; фронтенд и все потребители перепиниваются на составной контракт по SHA.
- Числа сроков и бюджетов, лимиты SSE и заказа, нагрузочные пороги остаются предложением до G1. Выкат и слияние в `main` — только по отдельному поручению (U5).
- Перенос данных не делается: до принятия записей в новый стек остаётся откат на старые образы и тома.

## Отвергнутые варианты

- **Событийная плоскость управления (вариант B).** Регистрация ресторанов и авторизация через RabbitMQ вместо HTTP. Отвергнуто (U6): HTTP проще проверять и отлаживать, а регистрация и авторизация требуют ответа в запросе. Брокер разрешён только для уведомлений `umir.auth` (R17), и они не заменяют вызовов и не дают прав.
- **Импорт данных стенда.** `server import-json`, импорт JSONL Feedback, экспорт памяти Warehouse и Serving. Отвергнуто (U4, R1): данные стенда не ценны, а lossless-перенос дорог и рискован. Вместо него чистый лист и откат на старые образы.
- **Redis как источник истины.** Хранение сессий, бюджетов безопасности или бизнес-данных в Redis. Отвергнуто (U3): `redis-limiter` с AOF `everysec` теряет до секунды записи, `redis-cache` не персистентен. Бюджеты безопасности Auth остаются в Postgres, Redis хранит только пересоздаваемое состояние.
- **Redis-аренды у всех сервисов.** Отвергнуто (C4): сервисам с базой аренда в Postgres даёт fencing в той же транзакции без лишней зависимости.
- **Запасной путь «база недоступна → память или файл».** Отвергнуто (R20): тихая потеря данных хуже явной недоступности.
- **Auth одним документом `authority`.** Отвергнуто в пользу построчных таблиц: срок хранения и очистку (R9) документом не выразить, а RLS на документ не накладывается.
- **mTLS между сервисами.** Не принято сейчас: границы доверия документируются, решение откладывается отдельно. TLS `verify-full` до хранилищ сохраняется. Внутренние вызовы остаются под сервисными токенами.
- **HA Postgres, RabbitMQ и Redis.** Вне объёма: решение пользователя о единственной ВМ (U8, Q10).
- **Kafka.** Отвергнуто ещё в ADR 0001 и остаётся: replay журнала из брокера не нужен.
- **Событийные ключи `serving.*`.** Резерва нет: Serving ничего не публикует (C38).

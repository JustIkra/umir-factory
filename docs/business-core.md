# Спецификация бизнес-логики ресторана

Создано: 2026-10-09. Обновлено: 2026-10-10. Часовой пояс: Europe/Moscow.

Это основной документ бизнес-контрактов проекта. При расхождении описаний контрактов в README и docs приоритет имеет docs. README описывают запуск и дают ссылки на этот документ. Решения пользователя определяют согласованный объём; отдельно обозначенные предложения остаются на рассмотрении.

Статус: границы пяти репозиториев согласованы. Warehouse и serving реализуют бизнес-сценарии, публичные контракты и хранилища в памяти; фабрика содержит совместные bridge-проверки. Документ задаёт правила и обязательные приёмочные сценарии. Событийный допуск по просрочке, совместное обновление остатков и очереди, неизменяемое состояние для чтения, меню доступных блюд и фоновое сохранение снапшотов после полных команд покрыты текущей реализацией. Постоянные хранилища, бизнес-HTTP и сетевое восстановление pending остаются следующими этапами; observability остаётся отдельным предложением.

## 1. Цель и границы

Спроектировать законченный рабочий процесс для одного ресторана: приём партий продуктов, подготовку и подтверждение заказов, расход ингредиентов по FEFO, списание просрочки, расчёт доступности блюд и рекомендации по их приоритетной продаже.

Стек: Go для backend и React для интерфейса. Уже работают каркасы HTTP-сервисов с healthz, маршрутизация gateway, сборка контейнеров и CI/CD. Бизнес-команды, постоянное хранилище и экраны ещё предстоит реализовать. Аутентификация, роли приложения и платформа для нескольких ресторанов находятся вне базовой версии; автоматический деплой на сервер пока не настроен. Фикстуры и демонстрационные данные размещаются вне каталогов с производственным кодом.

Пользователь включил в текущую версию автоматическое списание просрочки и рекомендации по продаже блюд. Генерация заказов и поставок остаётся независимой от рекомендаций. Отчёт о недостающих ингредиентах для закупки исключён из текущей версии по решению пользователя. Механизм минимального и целевого остатка также не входит в контракты. Причины нехватки ингредиентов сохраняются в стоп-листе и предупреждениях заказа.

Цель архитектуры под нагрузкой — стабильность и расширение с небольшим объёмом переделки бизнес-правил. Хранилища и транспорт заменяются через порты; тяжёлые расчёты чтения отделяются от сериализации изменений. Численный RPS не является условием начала каркаса. Пропускная способность, стоимость копирования и предел памяти проверяются при реализации; in-memory адаптер не доказывает производительность будущей базы или сети.

## 2. Согласованные правила и технические решения

Согласованы пять репозиториев: umir-factory, umir-gateway, umir-serving, umir-warehouse и umir-frontend. Бизнес-правила: частичное оформление заказа с явным подтверждением, обработка позиций в исходном порядке, отсчёт годности от изготовления, московское время, количества с фиксированной точностью, FEFO, автоматическое списание, Event Sourcing, снапшоты и ранжирование рекомендаций по фактическому распределению партий по FEFO.

Пользователь согласовал хранение продуктов, блюд и рецептур в warehouse вместе с событиями. Один поток warehouse содержит регистрацию справочников, поступления, оформленные заказы и списания просрочки. MenuService в serving читает и регистрирует определения через порт склада; авторитетное состояние справочников принадлежит warehouse.

Пользователь согласовал событийную обработку просрочки. Перед новым оформлением и запросами актуальных остатков warehouse восстанавливает очередь, записывает наступившие списания и применяет события к проекции. При ошибке подготовки новая операция возвращает техническую ошибку. Успешное оформление подтверждается только записанным OrderPlaced. Партии содержат данные проекции; отдельная проверка даты в заказе или меню не добавляется.

Остатки и очередь публикуются вместе на границе полной записанной команды. Обычная подготовка использует пригодную проекцию текущей версии; полная сверка нужна при восстановлении или известном сбое. Неизменяемое состояние чтения захватывается вместе с evaluatedAt/stateVersion внутри единого допуска; чистые расчёты могут выполняться после освобождения сериализации. Снапшот сохраняется в фоне и меняет точку начала восстановления только после успешного сохранения. GetMenu содержит только доступные блюда без количества порций.

Контракт каркаса также включает следующие технические решения:

- Определения продуктов и блюд создаются командами и остаются неизменяемыми в этой версии. Для редактирования существующих определений потребуется отдельный контракт.
- Предлагаемый состав заказа хранится отдельно от бизнес-событий. Это неизменяемое временное значение, которое не резервирует остатки.
- Запись проверяет ожидаемую версию потока и атомарно добавляет весь набор событий команды.
- deliveryID уникален в состоянии склада независимо от commandID. Очередь истечения восстанавливается из партий при работе процесса. Подтверждение и замена одного предложения сериализуются у его владельца, включая вызов склада.
- Частота сохранения снапшотов задаётся настройкой приложения: положительным количеством событий. Состояние захватывается после полной команды; очередь сохранения ограничена.

| MenuService | serving | Формировать меню доступных блюд; читать и регистрировать определения через порт склада; предоставлять рецептуру одной порции. |
| InventoryService | warehouse | Рассчитывать количество порций и списания по FEFO на подготовленной проекции событий склада. |
| DeliveryService | warehouse | Проверять поставку целиком и формировать факты поступления. |
| OrdersService | serving | Хранить предложения и координировать подтверждение согласованного состава. |
| ExpirationService | warehouse | Через общую обработку очереди формировать BatchExpired, применять записанные факты и завершать задачи. |
| MonitoringService | warehouse | Показывать остатки и партии до заданного срока. |
| StopListService | serving | Определять блюда, для которых нельзя приготовить одну порцию. |
| RecommendationsService | serving | Ранжировать доступные блюда и объяснять приоритет. |

Компоненты находятся внутри двух самостоятельных бизнес-сервисов. Warehouse владеет InventoryState, журналом событий, снапшотами и задачами истечения. Он атомарно фиксирует окончательный состав продажи вместе с расходом ингредиентов. Serving владеет временными предложениями и обращается к складу через явный порт. После ошибки связи исход окончательного оформления проверяется по идентификаторам команды и предложения.

Общие правила доступности и FEFO выполняются в warehouse. Один владелец сериализует подготовку проекции и запись изменений. Перед операцией, которой нужны актуальные остатки, он выполняет порядок из раздела 8. Чтение захватывает неизменяемое состояние и рассчитывается вне сериализации; новое оформление повторно проверяет и записывает расход внутри неё. Serving получает результат со stateVersion и evaluatedAt; меню, стоп-лист и заказы не реализуют собственную проверку срока. Межсервисный транспорт будет определён при реализации API.

При запуске warehouse восстанавливает InventoryState из снапшота и последующих событий, затем восстанавливает задачи истечения. Serving собирает обработчики и ProposalStore. Пустой поток событий означает пустое состояние склада и справочников. Идентификатор ресторана, его регистрация и жизненный цикл не входят в сущности и операции этой версии.

Текущий каркас реализует только healthz, gateway и инфраструктурные проверки. Публичный [README фабрики](../README.md) содержит команды запуска, порты и правила выпуска. Обновлять main и объединять PR может только JustIkra; Kxqusos работает в других ветках. Остальные участники используют issue, fork и PR.

## 4. Контракты значений

### Идентификаторы и время

- Идентификаторы — непустые строки. Бизнес-логика не зависит от их внутреннего формата. Идентификаторы сущностей сохраняются в событиях и при восстановлении.
- Каждая новая попытка оценки доступности получает evaluatedAt в warehouse после ожидания и подготовки проекции. Время, версия и состояние фиксируются в одной точке допуска внутри сериализации. Это момент принятия бизнес-решения, а не получения запроса клиентом и не получения ответа. Внутри оценки время фиксировано. После доказанного отказа без записи новый расчёт повторяет подготовку и получает новое время; неизвестный исход сначала разрешается с исходными событиями.
- Бизнес-время содержит полную дату, время и московское смещение +03:00. Календарные вычисления используют Europe/Moscow.
- Дата без времени недопустима на этой границе бизнес-логики. Поставки вводятся через интерактивную форму с обязательными полями даты и времени; входной адаптер отклоняет неполное значение до построения бизнес-значения. Загрузка и распознавание документов не входят в текущую версию.
- Время записи события — время выполнения операции. Даты изготовления и поступления партии хранятся как отдельные факты.

### Количества

- Каждый Product имеет одну baseUnit из фиксированного набора g, ml, pcs.
- Quantity — знаковое 64-битное целое число, выражающее тысячные доли базовой единицы продукта.
- Например, 40 г представлены числом 40000, 0,5 г — числом 500, одна штука — числом 1000.
- Входное количество положительное. Остаток может быть нулевым и никогда не становится отрицательным.
- Значения с точностью более трёх знаков после запятой нельзя молча округлять до точности контракта.
- Количество порций в заказе — положительное целое число. Количества в рецептуре относятся к одной порции.
- Арифметические операции должны отклонять значения и результаты, выходящие за допустимый диапазон.

### Срок годности

- ShelfLife содержит положительное целое value и unit из фиксированного набора day, month.
- Это значение с единицей времени. day означает 24 часа; month — календарный месяц. Прибавляется всё value к исходной дате с сохранением времени суток и сокращением дня до конца целевого месяца при необходимости.
- expiresAt рассчитывается один раз при регистрации из manufacturedAt и ShelfLife. Результат сохраняется в событии поступления.
- При восстановлении применяется сохранённый expiresAt без повторного расчёта.
- При evaluatedAt >= expiresAt запланированное списание должно быть записано и применено до допуска к актуальным остаткам. Единственное правило наступления срока находится в обработчике очереди: время обработки >= dueAt, где dueAt равен сохранённому expiresAt. Заказы и меню используют подготовленную проекцию.

При реализации на Go прямой вызов AddDate(0, value, 0) не выполняет правило сокращения дня: библиотека переносит лишние дни в следующий месяц. Например, 31 января 2026 + один месяц даёт 3 марта. Для month требуется отдельный календарный расчёт целевого месяца и допустимого дня. day прибавляет фиксированную длительность value × 24 часа с проверкой переполнения. Это ограничение реализации подтверждено [документацией time.AddDate](https://pkg.go.dev/time#Time.AddDate); бизнес-правило конца месяца остаётся прежним.

## 5. Модели и вложенные значения

| Модель или вложенное значение | Обязательные данные |
| --- | --- |
| Продукт Product | productID, name, baseUnit. |
| Блюдо Dish | dishID, name, непустая рецептура. |
| Ингредиент рецептуры | productID, положительное количество на порцию. Продукт встречается в рецептуре один раз. |
| Поставка Delivery | deliveryID, number (номер поставки), createdAt (полные дата и время создания поставки), упорядоченные строки поступления. |
| Строка поступления | productID, manufacturedAt, ShelfLife, receivedAt, quantity. |
| Партия Batch | batchID, deliveryID, lineNo, productID, manufacturedAt, ShelfLife, receivedAt, expiresAt, receivedQuantity, remainingQuantity. |
| Позиция заказа | lineNo, dishID, положительное целое количество порций. |
| Распределение списания Allocation | productID, batchID, положительное списываемое количество. |
| Предложение OrderProposal | proposalID, evaluatedAt, stateVersion, requestedPositions, acceptedPositions, changes. |
| Оформленный заказ | orderID, proposalID, принятые позиции, точные списания по партиям, placedAt. |

Рецептура одной порции задаёт ингредиенты для одного приготовленного блюда. Например, одна порция пасты требует 150 г макарон, 40 г сыра и 50 мл сливок. Для трёх порций количества умножаются на три. В модели и событиях они представлены целыми тысячными соответствующей базовой единицы.

Одна строка поступления создаёт одну партию. Разные даты изготовления и сроки годности требуют отдельных строк, в том числе для одинакового продукта. Номера строк назначаются в исходном порядке. Идентификаторы партий назначаются один раз и сохраняются в событии.

Product, Dish, Delivery, Batch, OrderProposal и оформленный заказ имеют собственные идентификаторы. Ингредиент, строка, позиция, Allocation, Quantity и ShelfLife — вложенные значения; отдельные хранилища и сервисы для них не нужны. quantity строки становится receivedQuantity партии и после прихода не меняется. remainingQuantity изменяют только записанные расход и списание. Batch является данными проекции; функция ОценитьПартию или отдельный метод проверки срока на Batch не требуется.

При сокращении заказа сохраняются исходные lineNo; позиции не перенумеровываются. Повтор dishID в разных позициях допустим: каждая обрабатывается в своём месте исходного списка.

InventoryState — восстановленное состояние warehouse: справочники, поставки по deliveryID, партии, заказы по orderID и proposalID, результаты записанных команд по commandID. Индексы не являются отдельными бизнес-сущностями и обновляются при применении событий. Стоп-лист, объяснения нехватки ингредиентов при заказе и рекомендации — результаты расчёта; они не имеют собственного жизненного цикла и не сохраняются как бизнес-факты. Содержание предложения неизменно; отметка о его замене хранится отдельно в ProposalStore. Источник истины об оформлении — OrderPlaced в warehouse.

## 6. Команды и результаты

Каждая команда, способная записать бизнес-события, требует commandID. При повторной отправке того же запроса вызывающая сторона сохраняет этот идентификатор. Serving передаёт его warehouse без замены; окончательная запись и защита от повторного списания принадлежат warehouse. Повторное использование уже записанного commandID с другим типом команды или входными данными приводит к CommandIdentityConflict.

Отпечаток входных данных учитывает тип публичной команды и нормализованные данные вызывающей стороны. Он исключает время выполнения, сгенерированные внутри команды идентификаторы, ожидаемую версию потока и рассчитанные списания. Порядок входных позиций сохраняется при расчёте отпечатка. Для ConfirmOrder отпечаток строится из типа ConfirmOrder и переданного proposalID; принятый состав берётся из неизменяемого предложения. Внутренний CommitAcceptedOrder сохраняет эту идентичность команды, а не создаёт новую команду расхода.

| Операция | Обязательные входные данные | Успешный результат |
| --- | --- | --- |
| RegisterProduct | commandID, productID, name, baseUnit | Зарегистрированный продукт. |
| DefineDish | commandID, dishID, name, упорядоченные ингредиенты | Определённое блюдо. |
| ReceiveDelivery | commandID, deliveryID, number, createdAt, упорядоченные строки поступления | Идентификаторы поставки и партий. |
| PrepareOrder | Упорядоченные позиции dishID/portions | Неизменяемое предложение заказа, в том числе с пустым принятым составом. |
| ConfirmOrder | commandID, proposalID | Один из результатов, определённых ниже. |
| ExpireBatch | commandID, batchID | Списанное количество; ноль означает, что нового списания не потребовалось. |
| ProcessDueExpirations | Внешнее время не передаётся; используется функция now | Результаты обработки отдельных задач. |

RegisterProduct и DefineDish не заменяют существующие определения. Отсутствующая сущность, некорректные данные, неподдерживаемая единица и переполнение — ошибки, при которых бизнес-события не записываются.

### Приём поставки

1. Проверить записанный commandID и отпечаток. Точный повтор возвращает прежний результат; другой запрос с этим commandID возвращает CommandIdentityConflict.
2. Проверить deliveryID в состоянии той версии, с которой будет выполнена запись. Существующий deliveryID с новым commandID возвращает DeliveryAlreadyReceived без событий, даже если данные поставки совпадают. Номер поставки не заменяет deliveryID как ключ уникальности и не считается уникальным.
3. Проверить непустой список и все строки до записи событий. Каждый продукт должен существовать. Проверить manufacturedAt <= receivedAt <= время выполнения и createdAt <= время выполнения.
4. Рассчитать все expiresAt. Назначить идентификаторы партий. Сформировать DeliveryReceived для поставки целиком.
5. На временной проекции DeliveryReceived построить задачи поступивших партий и применить единое правило выбора наступивших задач на времени этой команды. Для уже наступивших сроков добавить BatchExpired на всё поступившее количество к набору событий этой команды, без отдельной записи списаний и повторной загрузки временной проекции. Не публиковать её до атомарной записи.
6. Атомарно записать весь набор событий с проверенной expectedVersion. Если хотя бы одна строка некорректна, ничего не записывать. При конфликте версии перечитать состояние и повторить проверку уникальности перед новой попыткой. Две команды одного deliveryID могут породить только один приход.
7. Применить записанные факты и обновить индекс задач по правилам раздела 8. Сбой индекса не отменяет успешную поставку. Просроченное поступление завершается нулевым остатком и записанной операцией списания.

### Подготовка заказа

1. Проверить входные позиции и существование блюд. Назначить lineNo в исходном порядке.
2. Порт warehouse готовит проекцию по разделу 8. При ошибке возвращается InventoryUnavailable; новое предложение не сохраняется.
3. Получить захваченное неизменяемое состояние, evaluatedAt и stateVersion. Оценка может выполняться вне сериализации warehouse. Рабочий остаток берётся из положительных remainingQuantity; отдельного сравнения сроков внутри подготовки заказа нет.
4. Обработать позиции в порядке lineNo. Для каждой рассчитать максимальное целое количество доступных порций, ограниченное запрошенным количеством.
5. Распределить ингредиенты принятых порций по FEFO. Вычесть эти списания только из временного рабочего остатка.
6. Сохранить принятые позиции с положительным количеством порций. Вернуть описание каждого уменьшения и удаления.
7. Сохранить неизменяемое предложение в ProposalStore. Подготовка не записывает события заказа, не расходует ингредиенты и не резервирует остатки. Системная подготовка склада перед расчётом может записать BatchExpired; эти факты сохраняются, даже если предложение не создано.

OrderProposal содержит обязательные proposalID, evaluatedAt, stateVersion, requestedPositions, acceptedPositions и changes. Каждое изменение содержит lineNo, dishID, requestedPortions, acceptedPortions и непустой список дефицитов ингредиентов. Каждый дефицит содержит productID, requiredQuantity и availableQuantity на момент обработки данной позиции.

### Подтверждение заказа

Serving получает неизменяемое предложение из своего ProposalStore и передаёт точный принятый состав warehouse для повторной проверки и атомарного оформления. Произвольно отредактированный принятый состав не принимается. Возврат RequiresConfirmation означает подготовку новой версии предложения в serving, а не запись продажи в warehouse.

OrdersService сериализует ConfirmOrder по proposalID. Исключительный доступ охватывает проверку записанной команды и заказа, чтение предложения, завершение вызова warehouse, а также сохранение замены или возврат заказа. Для нового оформления warehouse сначала выполняет подготовку проекции по разделу 8, затем фиксирует время оценки. Блокировки только на чтение или замену ProposalStore недостаточно.

- Пустой принятый состав возвращает EmptyOrder без события заказа и расхода ингредиентов.
- Для нового оформления подготовить склад по разделу 8. При InventoryUnavailable проверка заказа и запись OrderPlaced не начинаются; клиент получает техническую ошибку.
- Повторно проверить только принятые позиции в сохранённом порядке по подготовленным остаткам.
- Если все принятые количества доступны, рассчитать текущие списания по FEFO и атомарно записать OrderPlaced. OrderConfirmed возвращается только после установленной успешной записи.
- Увеличение остатков не восстанавливает удалённые блюда и не увеличивает принятые порции.
- Если хотя бы одно принятое количество нужно уменьшить, создать и сохранить новое предложение, пометить предыдущее как заменённое и вернуть RequiresConfirmation. События заказа не записывать. Новое предложение требует явного подтверждения пользователя.
- Новое предложение с пустым принятым составом возвращается с объяснениями. Оформить его нельзя.
- Повторное использование заменённого предложения возвращает ProposalSuperseded с идентификатором его замены.
- ProposalNotFound требует заново подготовить заказ. Потеря неподтверждённых временных предложений при перезапуске не изменяет склад.
- Повтор уже записанной команды возвращает существующий заказ до попытки загрузить предложение.
- Одно предложение может породить не более одного оформленного заказа. Если proposalID уже принадлежит заказу, вернуть этот заказ даже при новом commandID. Проверка выполняется до чтения ProposalStore в тех же границах проверки версии склада.

Для замены requestedPositions равны acceptedPositions предыдущего предложения с сохранением lineNo. Суммарное количество каждого блюда и принятые количества позиций не увеличиваются. Сохранение нового предложения и ссылки supersededBy у старого атомарно. При ошибке этого сохранения старое остаётся активным; RequiresConfirmation возвращается только после успешного сохранения замены. Повторное обращение к старому возвращает уже существующую замену.

Перед вызовом warehouse serving сохраняет pendingCommandID рядом с предложением. Пока результат вызова неизвестен, serving не заменяет предложение и не начинает второе оформление по нему. Повтор этого commandID продолжает попытку с неизменными proposalID и принятым составом; другой commandID получает ConfirmationPending без вызова оформления. Технический ответ об неизвестном исходе не снимает отметку незавершённой попытки. Отсутствие заказа в одном запросе чтения не доказывает, что незавершённая запись не состоится. Разрешение попытки требует определённого ответа warehouse: записанный заказ либо завершённая проверка без записи. Ошибка связи возвращается как техническая неопределённость, а не как EmptyOrder или RequiresConfirmation. pendingCommandID снимается после разрешения; при замене — атомарно вместе с сохранением замены. InventoryUnavailable, полученная как определённый отказ подготовки до попытки OrderPlaced, разрешает попытку без заказа и позволяет снять pendingCommandID. Потеря ответа сама по себе этого не разрешает.

В тестовом каркасе один экземпляр serving владеет предложениями; достаточна локальная сериализация по proposalID. Второй экземпляр serving нельзя подключать к тем же предложениям без общего механизма сериализации. При переходе к сети нужно отдельно обеспечить восстановление незавершённой попытки после перезапуска serving; временный ProposalStore сам по себе этого не обеспечивает.

OrderConfirmed содержит записанный заказ. RequiresConfirmation содержит новое предложение. InventoryUnavailable — техническая ошибка подготовки актуальных остатков, допускающая повтор; она не означает нехватку ингредиентов, не создаёт замену предложения и не возвращается как успешное оформление. Если уже записанный заказ найден по commandID или proposalID, возвращается он до подготовки очереди. Сбой обновления индекса после OrderPlaced не отменяет этот факт. Неизвестный исход записи заказа возвращается как техническая неопределённость и разрешается по правилам повтора.

## 7. FEFO и доступность

На подготовленной проекции пригодны партии с remainingQuantity > 0: все наступившие на evaluatedAt списания уже применены. Сортировка FEFO использует сохранённые expiresAt, затем receivedAt, затем batchID. Каждая партия расходуется до своего остатка перед переходом к следующей. FEFO не повторяет проверку наступления срока.

Для заказа количество целых порций по рецептуре — минимум среди её ингредиентов: floor(пригодный остаток продукта / количество на порцию). Для меню, стоп-листа и рекомендаций каждое блюдо оценивается независимо на одну порцию; количества доступных порций в эти результаты не добавляются. Независимую доступность блюд с общим ингредиентом нельзя считать гарантированной совместной доступностью.

Блюдо попадает в стоп-лист при нулевом количестве доступных порций. Причины указывают ингредиенты, которых не хватает на одну порцию. Заказ дополнительно проверяет весь упорядоченный состав, используя общий временный остаток.

## 8. Задачи истечения и история

### Источник задач и запись фактов

DeliveryReceived содержит expiresAt каждой партии. Из записанных поступлений, расходов и списаний warehouse восстанавливает внутренний индекс ожидающих ExpireBatch. Ключ задачи — batchID, dueAt — сохранённый expiresAt. Внешнее сообщение о наступлении срока не требуется. BatchExpired является фактом выполненного списания и заранее в журнал не записывается.

Индекс содержит ровно партии с remainingQuantity > 0, включая уже просроченные. Очередь и InventoryState являются проекциями одного полного записанного префикса потока. Индекс хранит lastSequence последней полностью применённой команды; при частичном сбое маркер не продвигается. Версия продвигается и на командах справочников, которые не меняют задачи. Перед допуском обе проекции должны соответствовать последней записанной версии потока. Совпадение маркеров не заменяет инвариант полноты индекса.

Один владелец warehouse строит следующий вариант InventoryState и индекса по полному набору команды и публикует их вместе только после подтверждённой записи. DeliveryReceived добавляет задачи положительных остатков; OrderPlaced сохраняет их при положительном остатке и удаляет при нуле; BatchExpired применяет списание и удаляет задачу. При уже просроченном поступлении публикуется только окончательный результат полного набора DeliveryReceived/BatchExpired. Изменяемые части не разделяются с состоянием, удерживаемым читателем или worker снапшота.

Ошибка построения или публикации не оставляет проекции пригодными с новой версией. Если команда уже записана, сбой проекции не отменяет факт: её результат возвращается из записанной команды или восстановления. Проекции помечаются непригодными и восстанавливаются перед следующей свежей операцией. Отдельный брокер, постоянное хранилище очереди и новый интерфейс для каждой проекции не требуются.

Полная сверка выполняется при запуске/восстановлении, известном сбое, обнаруженном нарушении или явном повреждении через тестовую fault-injection. На обычной операции используются закрытое владение, совместная публикация, признак пригодности и подтверждённая версия. Любое известное повреждение, включая удаление единственной задачи, обязано пометить проекцию непригодной. Произвольная незаметная порча внутренней памяти при корректных маркерах без проверки содержания не гарантированно обнаруживается; этот режим не обещает полную сверку на каждом запросе.

### Единый порядок перед актуальной операцией

Warehouse сериализует следующие шаги с применением событий и новым расходом:

1. До требования восстановить проекции разрешить неизвестную исходную запись и проверить записанный commandID/отпечаток и оформленный proposalID через EventStore либо доказанно актуальный результат. Точный повтор возвращает исходный факт; конфликт идентичности остаётся ошибкой. Сбой чтения результата не доказывает отсутствие заказа и не разрешает снять pendingCommandID. Восстановление остатков и очереди не является условием возврата уже записанного заказа.
2. Для свежей операции довести InventoryState и индекс до подтверждённой версии, проверить пригодность согласованной проекции. При отставании применить полные записанные команды; при непригодности выполнить восстановление/полную сверку. Новый вариант публикуется вместе с InventoryState только после успеха. Пустой индекс допустим только как часть пригодной полной проекции текущей версии; сам по себе он ничего не доказывает.
3. Получить текущее время из now. Выбрать задачи с dueAt <= этому времени в порядке dueAt/batchID. Будущие задачи не блокируют операцию.
4. Выполнить наступившие ExpireBatch. Записать BatchExpired и применить его к InventoryState; завершить задачу после установленной успешной записи. Неизвестный исход записи сначала разрешить по правилам EventStore.
5. После обработки вновь получить текущее время и проверить наступившие задачи. Новые наступившие сроки также обрабатываются. Повторять до согласованной точки, в которой наступивших задач нет и обе проекции актуальны.
6. Внутри той же сериализации одновременно зафиксировать это время как evaluatedAt, версию как stateVersion и соответствующее состояние. Между проверкой очереди и захватом другая команда не выполняется. Для нового оформления на них выполнить оценку и попытку записи; сериализация сохраняется до определённого результата. Для чтения захватить неизменяемое значение и освободить доступ перед чистым расчётом. Раннее поступление запроса не сохраняет ему прежнюю годность.

При ошибке восстановления, сверки или обязательного списания подготовка завершается InventoryUnavailable. Новый заказ и расход не записываются; OrderConfirmed, EmptyOrder или RequiresConfirmation вместо этой ошибки не возвращаются. Уже успешно записанные списания других партий сохраняются. Очередь остаётся для следующей попытки, а операция может быть повторена после устранения сбоя.

Успех допуска к актуальной проекции и неизвестный исход OrderPlaced — разные состояния. Если запись заказа уже подтверждена, последующая ошибка индекса или снапшота не превращает заказ в неоформленный. Если исход записи неизвестен, нельзя сообщать успех или обещать отсутствие заказа до разрешения исходной попытки.

### Фоновая обработка и восстановление

- Приложение вызывает ProcessDueExpirations через положительный expirationCheckInterval. Тик и поступление операции остатков используют один механизм подготовки; пропуск тика не пропускает просрочку перед заказом. Бизнес-логика не запускает таймеры; тесты явно вызывают обработку и продвигают часы.
- Каждый цикл использует тот же допуск пригодной проекции. Полная сверка при восстановлении/сбое и её публикация сериализуются с применением событий; устаревший индекс не восстанавливает задачу уже израсходованной партии.
- Для обычной задачи используется постоянный commandID expiration/{batchID}; это пространство зарезервировано за обработчиком. Повтор не создаёт второго списания.
- ExpireBatch допускается тем же правилом dueAt <= время обработки. Ранний вызов возвращает NotDue без события. В обработчике списания отдельная проверка срока на модели Batch не добавляется.
- Наступившее списание использует весь текущий remainingQuantity. Полный расход по OrderPlaced или уже выполненное списание завершают устаревшую задачу без события нулевого количества.
- При ошибке записи цикл завершается технической ошибкой; задача сохраняется. Уже записанные факты не откатываются. При записанном списании и неудавшемся удалении следующая сверка удаляет задачу нулевого остатка.
- При восстановлении события применяются без часов и без создания новых фактов. Затем строится индекс, обрабатываются наступившие сроки и только после успеха допускаются актуальные операции. Ошибка этой обработки сохраняет недоступность операций остатков до успешного повтора.
- Уже просроченное поступление использует то же правило на временной проекции: DeliveryReceived и нужные BatchExpired записываются атомарно одной командой. Незаписанная временная проекция не становится общим состоянием.

Баланс каждой партии: receivedQuantity = remainingQuantity + consumedByOrders + writtenOffForExpiry.

### Неизменяемое состояние для расчётов

Чтение захватывает нужные определения и данные остатков/партий вместе с evaluatedAt/stateVersion до освобождения сериализации. Допустимы ссылки на уже неизменяемые части; если данные изменяемые, отделённая копия завершается внутри захвата. Дальнейшая сборка результата и чистый FEFO-расчёт выполняются вне доступа владельца. Внутренние изменяемые карты, очередь, история, результаты команд и ProposalStore читателю не передаются.

Последующая продажа или течение времени не меняют захваченное значение. Ответ описывает доступность на своей точке допуска и не является резервом. Следующий свежий запрос снова проходит подготовку, даже если версия потока ещё не изменилась. Подтверждение заказа повторно проверяет актуальные остатки в сериализации. Расчёт захваченного значения не обращается к now и не добавляет проверку срока партии.

Это временное значение в памяти, не сохраняемый снапшот восстановления. Атомарная замена указателя не делает вложенные карты/срезы неизменяемыми. Конкретная структура копирования остаётся реализационным выбором; отсутствие изменяемых общих ссылок обязательно. Полная копия также может быть дорогой и требует измерения стоимости.

## 9. Контракты запросов и рекомендаций

Каждый результат запроса содержит evaluatedAt и stateVersion. GetInventory, GetMenu, GetStopList, GetExpiringBatches и GetRecommendations проходят подготовку склада из раздела 8; при её сбое возвращается InventoryUnavailable. Чтение справочников получает одну полную применённую версию, но не требует списания просрочки; evaluatedAt в таком ответе — время захвата определения. При невозможности восстановить эту версию возвращается InventoryUnavailable. GetHistory и чтение уже записанного результата возвращают факты журнала и не требуют предварительного списания. Системная подготовка перед запросом доступности может записывать BatchExpired; сами расчёты не расходуют ингредиенты и не записывают события заказа.

| Запрос | Содержание результата |
| --- | --- |
| GetProducts | Все зарегистрированные продукты: productID, name, baseUnit, включая продукты без поступлений. |
| GetDishCatalog | Все определённые блюда: dishID, name, включая недоступные; внутренний справочник, не доступное меню. |
| GetDish | По обязательному dishID — dishID, name и рецептура одной порции: productID, quantity, baseUnit. |
| GetMenu | В serving — только доступные блюда: dishID, name. Количество доступных порций в ответ не входит. |
| GetInventory | Пригодные остатки по продуктам; по партиям — идентификатор, единица, учтённый остаток, даты изготовления, поступления и окончания годности, пригодность. |
| GetStopList | Идентификаторы недоступных блюд и дефициты ингредиентов на одну порцию. |
| GetExpiringBatches | Партии с положительным остатком и expiresAt не позднее обязательного cutoffAt, отсортированные по expiresAt и batchID. cutoffAt раньше evaluatedAt недопустим. |
| GetRecommendations | Упорядоченные рекомендации с объяснениями. |
| GetHistory | События в порядке записи, включая поступления, продажи и списания просрочки. |

Пустой справочник возвращает пустой список. GetProducts сортируется по productID; GetDishCatalog и GetMenu — по dishID. GetDish сохраняет порядок ингредиентов определения. Пустой dishID даёт InvalidArgument, неизвестный непустой — DishNotFound. GetProducts/GetDishCatalog/GetDish не изменяют склад. Определения неизменяемы в этой версии, но результат не предоставляет изменяемых ссылок на внутреннее состояние.

GetMenu и GetStopList используют независимые оценки блюд из EvaluateMenu порта warehouse, определённого в разделе 11. На одной паре evaluatedAt/stateVersion их множества дополняют друг друга: блюдо доступно для одной порции или входит в стоп-лист. Разные свежие вызовы могут получить разные версии; общий результат формируется из одной оценки. Доступность нескольких блюд не обещает их совместное приготовление одним заказом.

До обработки срока или при её ошибке в неподготовленной проекции может оставаться положительный просроченный остаток. Он не выдаётся как успешно рассчитанная доступность: операция получает InventoryUnavailable до завершения подготовки. После успешного BatchExpired остаток обнулён; история списания доступна через GetHistory.

GetExpiringBatches возвращает batchID, productID, remainingQuantity, baseUnit, expiresAt, remainingSeconds и isExpired. remainingSeconds = max(0, floor(разница expiresAt и evaluatedAt в секундах)). В успешном результате с положительными остатками isExpired равен false: наступившие списания уже применены. Расчёт оставшегося времени относится к отображению и не создаёт отдельного допуска партии к приготовлению. Вызывающая сторона явно задаёт границу мониторинга через cutoffAt. Скрытого порога предупреждений в бизнес-логике нет.

Алгоритм GetRecommendations:

1. Оценить каждое блюдо независимо по одним и тем же пригодным остаткам.
2. Пропустить блюда, для которых нельзя приготовить одну порцию.
3. Рассчитать точное распределение партий по FEFO для одной порции без расходования остатков.
4. Установить priorityExpiresAt равным ближайшему окончанию годности среди используемых партий.
5. Отсортировать по возрастанию priorityExpiresAt, затем dishID.
6. Вернуть причину для каждой используемой партии, чей срок равен priorityExpiresAt. Причины сортировать по productID и batchID.

Каждая рекомендация содержит обязательные dishID, dishName, priorityExpiresAt и непустой reasons. Каждая причина содержит productID, productName, batchID, quantityPerPortion, baseUnit и expiresAt.

Например, объяснение указывает, что одна порция использует 40 г сыра из партии, срок которой истекает через шесть часов. Количество соответствует реальному расходу из этой партии по FEFO. При использовании нескольких партий оно не подменяется полным количеством ингредиента в рецептуре.

Дополнительные пороги остатков и окно срочности не применяются. Ранжируются все доступные блюда. Расчёт повторяется при каждом запросе, учитывая изменения остатков и течение времени. Ранжирование рекомендаций не сохраняется как источник бизнес-фактов в журнале событий.

## 10. События и конкурентные изменения

Umir-warehouse использует один поток с фиксированным техническим streamID inventory. Запись в этот поток выполняет warehouse; serving вызывает его команды через порт. Оболочка каждого события содержит обязательные eventID, streamID, sequence, schemaVersion, commandID, commandFingerprint, recordedAt, type и payload. Начальная schemaVersion — 1. sequence возрастает последовательно, без пропусков.

| Событие | Обязательные бизнес-данные payload |
| --- | --- |
| ProductRegistered | Полное определение продукта. |
| DishDefined | Полное определение блюда и количества ингредиентов для одной порции. |
| DeliveryReceived | Полные данные поставки и зарегистрированные партии с исходными количествами и рассчитанным expiresAt. |
| OrderPlaced | orderID, proposalID, принятые позиции, точные списания по партиям, placedAt. |
| BatchExpired | batchID, productID, writtenOffQuantity, причина EXPIRATION, expiresAt, processedAt. |

Событие содержит факты, необходимые для восстановления. Обработчики восстановления применяют их без обращения к часам, расчёта срока годности, повторного выбора партий по FEFO и генерации идентификаторов.

EventStore.AppendBatch принимает streamID, expectedVersion, идентификатор и отпечаток команды, полный набор событий. Операция атомарно проверяет версию, предотвращает повтор уже записанной команды и добавляет все события. Частичная запись запрещена.

EventStore сохраняет границы полных наборов AppendBatch и выдаёт их для применения/replay целиком. Чтение после lastSequence снапшота начинается после завершённой команды; неполный набор нельзя считать восстановленной версией. Публикация InventoryState/индекса и захват снапшота выполняются только на конечной sequence полного набора. GetHistory может представлять эти записанные события последовательно, сохраняя их порядок.

- Та же записанная команда с тем же отпечатком возвращает сохранённый результат без новых событий.
- Тот же записанный commandID с другим отпечатком возвращает CommandIdentityConflict.
- Конфликт версии возвращает ConcurrentModification без событий этой попытки. Перед новым расчётом загрузить состояние и пройти подготовку по разделу 8 с новым evaluatedAt. Ранее рассчитанные списания и время повторно не использовать. Время истекает и без изменения версии потока.
- Неопределённый технический результат записи отличается от доказанного конфликта версии. Пока исход неизвестен, адаптер разрешает исходную запись и при необходимости повторяет ровно тот же набор eventID, payload, commandID, отпечаток и expectedVersion. Новые идентификаторы и повторный расчёт допустимы после определённого отказа без записи; успешная запись возвращает исходный результат.
- Уникальность deliveryID и оформленного proposalID проверяет warehouse в состоянии этой expectedVersion. Проверка версии делает эти проверки обязательными заново после конкурентной записи; одного предварительного поиска по идентификатору недостаточно.
- Команда, не записавшая событий, не считается записанной командой. Её повтор заново оценивает текущее состояние. Подтверждение другого предложения требует нового commandID.
- Отпечатки и результаты записанных команд восстанавливаются из событий и включаются в снапшот.
- OrderPrepared не записывается. Завершение задач истечения не удаляет исторические события.

MenuUpdated, StopListChanged, RecommendationsUpdated и SnapshotCreated не добавляются: это вычисляемые результаты и техническая оптимизация, а не новые движения склада.

Защита commandID/отпечатка/результата — требование нашего EventStore, которое должен выполнить адаптер. Она не возникает автоматически от использования базы событий: [KurrentDB описывает повтор записи по тем же eventID и проверкам версии](https://docs.kurrent.io/clients/python/v1.3/appending-events). Уникальность deliveryID и proposalID остаётся правилом warehouse. KurrentDB приведён как референс поведения записи; выбор постоянного хранилища ещё не сделан.

## 11. Контракты зависимостей, снапшоты и восстановление

| Зависимость | Владелец | Обязательное поведение |
| --- | --- | --- |
| now (функция часов) | Каждый бизнес-сервис | Предоставлять время операции в Europe/Moscow; тесты явно продвигают часы. Расчёт склада сохраняет собственный evaluatedAt. Отдельный интерфейс Clock не требуется. |
| newID (функция генерации) | Каждый бизнес-сервис | Выдавать уникальные непустые идентификаторы; в тестах источник детерминированный. Идентификаторы сохраняются в событиях. Отдельный интерфейс IDSource не требуется. |
| EventStore | warehouse | Читать полные наборы команд по порядку и записывать их атомарно с проверкой версии и команды; отдельно читать записанные результаты. |
| SnapshotStore | warehouse | Загружать корректные снапшоты завершённых команд; атомарно публиковать полностью сохранённый кандидат и не заменять более новую версию старой. |
| ProposalStore | serving | Хранить неизменяемые предложения и метаданные pendingCommandID/supersededBy; атомарно сохранять замену и снимать незавершённую попытку. OrdersService сериализует весь ConfirmOrder по proposalID, а не только операции хранилища. |
| Индекс задач истечения | warehouse | Закрытая проекция batchID/dueAt с lastSequence; публикуется вместе с InventoryState, при известном сбое восстанавливается до допуска. Отдельный интерфейс ExpiryTaskQueue не нужен. |
| Порт склада | Используется serving | Передавать команды warehouse и получать согласованные расчёты, версии и результаты оформления; в тестах связывает бизнес-сервисы в памяти. |

Адаптеры в памяти должны соблюдать эти контракты, включая атомарность и конфликты. Они не должны скрывать ошибки, которые обязан обрабатывать адаптер постоянного хранилища.

Интерфейсы нужны на заменяемых границах: EventStore, SnapshotStore, ProposalStore и порт warehouse. Для логических компонентов достаточно конкретных Go-типов и функций; имя Service в графе не требует интерфейса, базового класса, отдельного процесса или универсального репозитория. Сборка зависимостей относится к точке запуска сервиса. RestaurantFactory, RestaurantService и сущность Restaurant не добавляются.

Интерфейс порта задаётся в вызывающем сервисе по операциям, которые использует конкретный потребитель. Он не обязан объединять все команды и запросы warehouse. [Effective Go](https://go.dev/doc/effective_go#interfaces_and_types) описывает небольшие интерфейсы поведения; точный набор доменных моделей и границ остаётся решением этого проекта.

Минимальные операции порта warehouse для заказов: EvaluateOrder — оценить упорядоченные позиции без расхода; CommitAcceptedOrder — повторно проверить принятый состав и атомарно оформить его; чтение записанной команды и заказа по proposalID. CommitAcceptedOrder получает commandID, proposalID и неизменные acceptedPositions. Он возвращает записанный заказ либо RecheckRequired с evaluatedAt, stateVersion, сокращёнными позициями и changes без записи заказа; сбой подготовки до оформления возвращает InventoryUnavailable. EvaluateOrder и новое CommitAcceptedOrder используют подготовку из раздела 8, а чтение записанного результата ей не блокируется. Только serving создаёт новое proposalID и результат RequiresConfirmation. Повтор после конфликта версии пересчитывает склад; после неопределённого ответа повторяется тот же вход, без новой команды. Схема HTTP и восстановление незавершённых сетевых попыток проектируются при реализации API.

Для MenuService порт предоставляет GetProducts, GetDishCatalog, GetDish и команды регистрации по разделам 6 и 9. Для доступности меню, стоп-листа и рекомендаций используется EvaluateMenu без входных позиций: warehouse готовит склад, захватывает одно неизменяемое состояние и независимо оценивает каждое определённое блюдо на одну порцию. Результат имеет общие evaluatedAt/stateVersion и список оценок, отсортированный по dishID. Оценка содержит dishID, dishName, isAvailable, deficits и allocations. Доступное блюдо имеет пустые deficits и точные FEFO-распределения одной порции; недоступное — непустые deficits и пустые allocations. Каждый дефицит содержит productID, requiredQuantity, availableQuantity для одной порции. Каждое распределение содержит productID, productName, batchID, quantity, baseUnit, expiresAt. Распределения сохраняют порядок рецептуры и FEFO внутри ингредиента. Остатки между оценками блюд не уменьшаются. Serving фильтрует меню/стоп-лист и ранжирует рекомендации по этим данным. Количество доступных порций не входит в EvaluateMenu; заказ рассчитывает его через EvaluateOrder.

Синхронный адаптер в памяти завершает проверку и попытку записи до возврата управления, в том числе при внедрённой технической ошибке. После возврата он не оставляет фоновую попытку, способную записать заказ позднее. Ошибка после успешной записи моделирует потерю ответа: повтор находит записанный заказ. Сетевой адаптер не может считать RecheckRequired окончательным решением, пока более ранний вызов ещё способен записать этот заказ; предотвращение поздней записи и восстановление попытки после перезапуска должны войти в отдельный контракт API.

ProposalStore сохраняет содержание предложения неизменяемым. Конкурирующие попытки заменить одно предложение возвращают уже сохранённую замену. Факт оформления заказа определяется событиями warehouse независимо от временных отметок ProposalStore.

Снапшот содержит обязательные schemaVersion, streamID со значением inventory, lastSequence и InventoryState: справочники, поставки, партии, оформленные заказы, отпечатки и результаты записанных команд. ProposalStore и восстанавливаемый список задач истечения в снапшот не входят.

Warehouse задаёт положительное eventsPerSnapshot. После полной команды проверить, что её конечная sequence минус lastSavedSequence не меньше eventsPerSnapshot; lastSavedSequence — версия последнего подтверждённого сохранения, изначально ноль при отсутствии снапшота. При достижении порога захватить неизменяемое полное InventoryState этой команды. Если команда пересекла порог несколькими событиями, используется её конечная sequence. Снапшот части команды запрещён. Рабочие остатки и очередь обновляются после каждой записанной команды и не ждут этого порога.

Один snapshot worker сериализует и сохраняет кандидат вне сериализации warehouse. Допускается не более одного выполняемого и одного ожидающего задания; ожидающий кандидат заменяется более новой полной версией. Передача не ожидает свободного места. Объединять можно задания на снапшоты, а не бизнес-события. Захваченный кандидат V не меняется после команды V+1; если данные изменяемые, отделённая копия выполняется внутри захвата. Копирование и разделение неизменяемых частей выбираются при реализации и проверяются на стоимость.

SnapshotStore публикует только полностью сохранённый корректный кандидат, не заменяет более новый старым и при сбое сохраняет предыдущий корректный снапшот. lastSavedSequence продвигается монотонно только после установленного успеха, не после назначения задания; старое подтверждение его не понижает. Неизвестный исход разрешается чтением/повтором того же кандидата без понижения более новой версии. После ошибки возможен новый кандидат на следующей команде и явный повтор последнего кандидата при отсутствии новых команд; технический повтор организует приложение/worker, доменная логика таймеров не создаёт. В тестах работа worker запускается управляемо. Ошибка сохранения не отменяет записанную команду и не закрывает допуск склада: журнал достаточен для восстановления.

Восстановление загружает последний корректный снапшот, затем последовательно применяет события после lastSequence. При отсутствии корректного снапшота начинает с пустого состояния и воспроизводит поток полностью. Пропуск последовательности и неподдерживаемая схема события приводят к ошибке; факты нельзя молча пропускать. Список задач строится по восстановленным партиям с положительным остатком, просроченные задачи сразу передаются на выполнение. Полное воспроизведение и восстановление из снапшота с последующими событиями должны давать одинаковое бизнес-состояние и задачи при одинаковом времени расчёта.

Проверка снапшота включает фиксированный streamID, поддерживаемую схему, ссылки на сущности и неотрицательные остатки. lastSequence должен соответствовать завершённой команде и не превышать последнюю записанную версию потока. Снапшот, не прошедший проверки, не используется для восстановления.

Точка начала восстановления меняется только после успешного сохранения: снапшот на 100 и поток до 135 означают загрузку состояния 100 и применение команд после него до 135. После сохранения снапшота 200 следующее восстановление начинается с 200. История не удаляется; снапшоты ускоряют replay, но не ограничивают накопление данных. In-memory хранение само по себе не сохраняет журнал или снапшоты после завершения процесса. Для заявлений о длительной работе понадобятся отдельные пределы хранения, допуска и нагрузки.

## 12. Приёмочные сценарии с хранилищами в памяти

Тесты используют построители фикстур вне производственного кода, детерминированные функции now и newID, адаптеры в памяти с соблюдением контрактов. Реальное ожидание времени, внешние базы данных и сервисы не используются.

| Сценарий | Ожидаемый результат |
| --- | --- |

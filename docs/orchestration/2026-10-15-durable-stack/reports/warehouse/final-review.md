## Важные

**I1. `internal/adapters/authkeys/client.go:100-115` (ветка `unknownRefreshed`): параллельный запрос с новым kid получает `ErrInvalidToken`, пока идёт обновление.**
Сценарий (воспроизведён временным тестом, файл удалён): ключи свежие, Auth ротировал ключ, два запроса подряд приходят с `kid=two`. Первый ставит `unknownRefreshed=true` и ждёт flight (замок отпущен). Второй входит в `Key`, видит `unknownRefreshed==true`, ключа нет в `c.keys` и сразу возвращает `ErrInvalidToken` (401), хотя обновление, которое принесёт ключ, уже идёт. Раньше замок держался на время сети и второй запрос ждал и находил ключ. Это ломает валидные токены при ротации. `TestConcurrentKeyCallsOneRefresh` проверяет только холодный старт с известным kid.
Исправление: в этой ветке, если `c.flight != nil`, присоединиться к нему (`refreshLocked`) и после этого проверить `c.keys[kid]`; добавить тест «ротация + два параллельных вызова с новым kid, оба успешны, один запрос к Auth».

**I2. `internal/application/recovery.go` `projectFromSnapshot` + `internal/domain/batch_index.go`: индекс партий строится только в `Clone*`; состояние снапшота, пришедшее из десериализации, остаётся без индекса навсегда.**
`LoadLatest` памяти возвращает `CloneSnapshot` (индекс есть), но владелец «берёт состояние как есть» и не вызывает `reindex`. Хранилище волны 2 (Postgres, JSON/строки) вернёт `InventoryState` с `indexed=0`, `len(Batches)>0`. `productBatchIDs` тогда честно идёт полным перебором (корректно), а `indexBatches` при `indexed != len` ничего не расширяет, то есть индекс не появится до рестарта: commit снова O(число партий) на каждый ингредиент, регресс FIN-10 без единой красной проверки. Экспортной функции для построения индекса нет.
Исправление: в `projectFromSnapshot` (и в `Merge` при несовпадении счётчика) перестраивать индекс один раз (`reindex` через экспортированный `domain.NewIndexedState`/`(*InventoryState).Reindex`); тест: состояние без индекса после восстановления даёт `AllocsPerRun`, не растущие с числом партий.

## Мелкие

- M1. `tests/perf`: проверка «HTTP commit не дороже Owner более чем на 1 мс» (W1-2 «Готово») не сделана (в отчёте указано). Покрыто косвенно `TestCommitDoesNotReadJournalOverHTTP` и абсолютным commit 37 мкс. Закрыть в G1 или явно снять с группы.
- M2. Порог Movements 12 -> 20 обоснован: чтение периода линейно (8x по корпусу), CPU-отношение в моём прогоне 12.42 (>12, при 9.6 у recover); квадратичная регрессия даёт 64x и до правки была 53x, порог её ловит. Маскирует только регрессию константы между 1.5x и 2.5x. Не дефект; при желании добавить абсолютную границу `Movements(8000) < 1 с`.
- M3. `domain/quantity.go` `ValidateInventoryTotalsWith` обходит все партии на каждую поставку (O(партии), не O(история)). Пока допустимо (поставки редки), но не зависит от индекса; при росте числа исчерпанных партий (они остаются в состоянии) стоимость поставки растёт.
- M4. `bootstrap/registry.go:92-105`: `UpdateSettings(ctx, ...)` ждёт замок владельца, пока держится `Registry.mu`. Занятый владелец задерживает регистрацию всех ресторанов до дедлайна контекста запроса. Лучше обновлять настройки вне `r.mu` либо по `TryLock`/короткому ожиданию.
- M5. Тест `TestConcurrentKeyCallsOneRefresh` синхронизируется `time.Sleep(20ms)` («пусть остальные дойдут до ожидания»). На загруженной машине он может проходить и без ожидающих. Заменить счётчиком вошедших в `Key` (например хук в `Doer`/атомарный счётчик ожидающих).

Принятые решения (Ruling) оспаривать не стоит: загруженный при восстановлении снапшот не сверяется с журналом (по подспеке), цепочка «предыдущий снапшот + хвост» может унаследовать структурно валидную ошибку предыдущего снапшота (смягчено откатом на полный проход при расхождении). Обратная совместимость конфигурации: `WAREHOUSE_API_MODE` без умолчания, `compose.yaml` задаёт `legacy`, миграция записана в CHANGELOG (BREAKING). Слияние только после правки compose у factory (C35); в этой ветке это отмечено.

## Проверка особых зон
- Aliasing: `prepareLocked` отдаёт заимствованное представление; все внутренние потребители (`orders`, `stock`, `queries`, `product_batches`, `delivery`, `writeoff`, `expiration`) используют его только под замком и не после записи батча; внешние читатели получают `CloneReadView` (карты и слайсы индекса клонируются, `removeFromIndex` правит слайс на месте, но чужие копии его не делят). Payload событий в состояние не попадает (`CloneDish`, значения `Batch`/`Product` без указателей). Дефекта не найдено.
- Снапшот и журнал: проверка при сохранении вне замка (`verifySnapshot`), отклонённый кандидат не роняет воркер; `observeSaved`/`onSaved` без инверсии замков (`w.mu` не берётся под `o.mu` в обратном порядке). Потеря событий при восстановлении: кандидат собирается локально, публикуется после совпадения версии хранилища; `completeProjection` различает `version >` (конкурентный писатель, повтор) и `version <` (повреждённый журнал). `syncProjectionLocked` при отмене оставляет согласованный префикс. Дефекта не найдено.
- FEFO по индексу: индекс = остаток > 0 и не pending, порядок по сроку/приёму/ID сортируется в `AllocateFEFO` (не от порядка индекса), недоступные/исчерпанные партии не попадают; сравнение со старым перебором покрыто случайным тестом. Граница дня Europe/Moscow в FEFO не менялась (`EligibleBatch` сравнивает моменты; расчёт сроков не тронут).
- C1: повтор confirm с другим `commandID` идёт по `FindOrderByProposal` под замком владельца и возвращает существующий заказ без `AppendBatch`; уникальность proposal также держит хранилище. Двойного списания нет. Есть и путь с неизвестным исходом (`pendingOrder`).
- Отмена/дедлайн: `usable=false` остался только на несогласованности журнала (все 20 мест просмотрены), `markUnusable` пропускает ctx-ошибки, `recoverLocked` публикует кандидата только при успехе, `ctxMutex.Lock` не берёт замок с завершённым контекстом. `lockUncancellable` остаётся только в конфигурации и в `confirmSnapshotSaved`.
- `_FILE`: оба заданы, пустой файл, нечитаемый файл - ошибки без значения ключа; читаются только в v2 (в legacy игнорируются, как и сами ключи).
- Коммиты: Conventional Commits, футеров нет, `git diff --check` чист, секретов и `.superpowers` в диффе нет.

## 3. Ревью планов: итог и правила (rulings)

Планы в #17 и шести issue подробные и аккуратные. Разделы «Verified findings» верно отделяют подтверждённое от неподтверждённого, требования к outbox, inbox, аренде с fencing, RLS и семантике 429/503 корректны. Планы принимаются как основа. Ниже правила, которые снимают их расхождения с решениями пользователя и между собой. Подспеки ссылаются на правила по номеру.

| № | Правило | Затрагивает | Почему |
| --- | --- | --- | --- |
| R1 | Требования импорта и lossless-переноса из issue снимаются целиком: Auth #8 «Migration» п. 1–5, Feedback #5 п. 1–2 и архив OTP, Warehouse #4 п. 2–3, Serving #3 п. 2–3, #17 «Migration» п. 2–3. Остаются: бэкап и восстановление новой базы, остановка старого стека перед стартом нового, runbook переключения на чистый лист, откат = запуск старых образов на старых томах, пока новый стек не принял записей. | все | U4 |
| R2 | `runtimeEpoch` в публичном и приватном контракте означает storage generation: стабильна при рестарте и при смене реплики, меняется только при сбросе или восстановлении базы на более раннюю историю. Поле и формат на проводе не меняются. Идентификатор экземпляра процесса отделён и виден только в health и логах. Это записывается явно в дополнении DUR1 — значит, не «тихое» переназначение, которого опасается Serving #3. | auth, warehouse, serving, gateway, frontend, factory | U6; клиент и так трактует `RuntimeReset` как потерю состояния, а при стабильной генерации это снова верно |
| R3 | **Gateway перестаёт быть пиром жизненного цикла Auth.** Пиры Auth — только `warehouse` и `serving`. Auth больше не вызывает `GET/PUT/DELETE /internal/gateway/v2/runtime|registry` и не проверяет готовность Gateway в `authorize`, `access-check` и `service-tokens`. Gateway берёт множество ресторанов и надгробия из реестра Auth по ревизии (R5) и сам закрывает scope удалённых. Это корень исправления критичного C01 (готовность Gateway от планировщика) и условие для двух Gateway без общего состояния. | auth, gateway, factory | U6, U7 |
| R4 | **Live.** Владелец (Warehouse, при необходимости Serving) пишет событие в outbox в одной транзакции с изменением → relay → exchange `umir.events` (topic). Каждая реплика Gateway держит свою exclusive auto-delete очередь (рассылка всем репликам) и ограниченное кольцо на ресторан в памяти: ленивое, небольшое, с вытеснением неактивных. Локальное `Append` после проксированного ответа убирается; сигнал идёт только от владельца. SSE закрепляется за репликой по сессии: Nginx `hash $cookie_<session> consistent`. Курсор несёт идентификатор экземпляра и generation; чужой экземпляр, разрыв последовательности, рестарт или истёкший курсор → `refresh-required`. Postgres в Gateway не нужен, Redis cache не источник replay. Это вариант «отдельные очереди подписчиков» из #17. | gateway, warehouse, serving, frontend, factory | U6, U7 |
| R5 | **Реестр Auth по ревизии.** Auth отдаёт ревизию реестра и поддерживает условный запрос (`If-None-Match` → 304) и точечное чтение одного ресторана. Serving держит локальную проекцию «ресторан → generation склада и готовность» и обновляет её точечно. Ни один бизнес-запрос не скачивает весь реестр. Сверка Auth вызывает статус пира один раз на сервис за проход. | auth, serving, gateway | U6 |
| R6 | **Просрочку по-прежнему запускает Gateway** (U6; вариант «просрочку в склад» пользователь не выбрал). Одновременно работает один планировщик: аренда в Redis limiter с fencing-токеном. Пул параллельных вызовов ограничен. Warehouse отдаёт ближайший срок по ресторану (или список ресторанов с наступившими сроками), чтобы не вызывать каждый ресторан каждую секунду. Здоровье планировщика отделено от готовности. Строку #17 «Warehouse owns expiry schedules» читать как «владеет данными сроков и индексом». | gateway, warehouse, factory | U6, C01 |
| R7 | **Восстановление limiter Redis.** AOF `appendfsync everysec` и маркер непрерывности: ключ `umir:limiter:generation` со значением из конфигурации. Если маркера нет (потеря данных), limiter на самое длинное окно политики (не больше 1 ч) переходит в строгий режим: квоты сжаты до минимума, но не до нуля. Затем маркер записывается заново. Полное закрытие входа на час после перезагрузки ВМ недопустимо. Отступление от #17: барьер в Postgres не нужен — у Gateway нет базы, а надёжные бюджеты безопасности Auth (коды, неверные попытки, пароли) и так лежат в Postgres. | factory, auth, gateway | U8 |
| R8 | RLS обязателен (#17). Роль среды выполнения не владелец таблиц, миграции идут отдельной ролью. Контекст `SET LOCAL umir.org_id`/`umir.restaurant_id` ставит обёртка транзакции. Утечки контекста через пул проверяются тестом с настоящей ролью. | auth, warehouse, serving, feedback | #17 |
| R9 | Сроки хранения — таблица в DUR1 (раздел 6). Значения — предложение; их утверждает пользователь на шлюзе G1. До G1 сохраняются действующие гарантии повтора команд. | все с данными | #17 п. 2 |
| R10 | Бюджеты допуска — таблица в DUR1 (раздел 6), утверждаются на G1. Старые процессные лимитеры удаляются; запасного пустого лимитера в памяти нет. | auth, gateway, factory | #17 |
| R11 | **IP клиента.** Внешний Nginx Proxy Manager → frontend Nginx (по ZeroTier) → Gateway. Frontend Nginx доверяет `X-Forwarded-For` только от адреса NPM (`set_real_ip_from`, параметр развёртывания) и **перезаписывает** `X-Forwarded-For $remote_addr` в сторону Gateway. Gateway доверяет заголовку только от сети frontend (настраиваемый CIDR). | frontend, gateway, factory | Gateway #25 п. 6 |
| R12 | Часы. Все сервисы на одной ВМ, допуск на расхождение `iat` остаётся нулевым. Требование одной ВМ (или синхронизации часов) записывается в README factory, тесты фиксируют поведение явно. Это закрывает п. 5 #17 без ослабления срока токена. | все Go-сервисы | U8 |

Одна группа на репозиторий. Группа работает только в своём репозитории.

| Группа | Репозиторий | Подспека | Главное |

| G-auth | umir-auth | `auth.md` | Построчные таблицы и очистка по сроку, outbox писем и событий, допуск через Redis, R3, R5, готовность по возможностям. |

| G-warehouse | umir-warehouse | `warehouse.md` | Журнал и снапшоты в Postgres, горячая проекция с границей, FIN-10, outbox, ближайший срок для R6, различие живой и оборванной попытки (FIN-04). |
| G-serving | umir-serving | `serving.md` | Предложения и попытки в Postgres, проекция реестра (R5), FIN-04 с Warehouse, `CommandConflict`, готовность по ресторанам. |

Состав группы:

- **Ведущий группы** — агент Sonnet (effort high). Он ведёт журнал группы, пишет план по подспеке (superpowers:writing-plans) и исполняет его по superpowers:subagent-driven-development: свежий исполнитель на задачу, ревью задачи, финальное ревью ветки.
- **Исполнители и ревьюеры задач** — Sonnet (effort high), их запускает ведущий.
- **Финальное ревью ветки** — Opus.
- **Оркестратор** — основная сессия (Opus). Он принимает решения по запросам на изменение (раздел 7), сводит интерфейсы, ведёт общий журнал и шлюзы.

## 6. Общие контракты волны 0 (готовит G-factory)

Всё ниже кладётся в `umir-factory/docs/durable/` и в `docs/api`. Подспеки групп ссылаются на эти имена.

1. **DUR1** — дополнение к REG1, `2.0.0-DUR.1`. Замороженные байты C2/UA1/FIN1/REG1 не меняются. Содержит:
   - R2: смысл `runtimeEpoch`;
   - R3: убранные вызовы Gateway в приватном контракте Auth;
   - R5: ревизию реестра, условный запрос и точечное чтение;
   - статус попытки склада «выполняется / оборвана» для FIN-04;
   - ближайший срок для R6;
   - `CommandConflict` вместо `CommandIdentityConflict`;
   - 429 и 503 допуска (definite, до отправки) против 503/unknown после отправки;
   - лимиты позиций и активных предложений.
2. **ADR 0002** — PostgreSQL + RabbitMQ + Redis по U1–U8 и R1–R20. Заменяет ADR 0001, который так и не попал в `main`.
3. **Каталог событий** (`docs/durable/events.md`; уточнено решениями C1–C3, C30, C38, C39).
   - **Обменники:**
     - `umir.events` (topic) — события Warehouse для live, единственный производитель;
     - `umir.auth` (topic) — уведомления жизненного цикла Auth;

### Имена и топология

- **C1 (№1). События `umir.auth`** — строчные, через точку:
  - `auth.restaurant.deleting`, `auth.restaurant.deleted`;
  - `auth.organization.deleting`, `auth.organization.deleted`, `auth.organization.settings_changed`;
  - `auth.membership.revoked`, `auth.assignment.revoked`.

  Типа «ресторан создан» нет. Настройки принадлежат организации, поэтому Serving по `auth.organization.settings_changed` сбрасывает проекцию всех ресторанов организации. Gateway и Serving обрабатывают `deleting` (сразу перестать обслуживать) и `deleted` (очистка). Feedback обрабатывает только `deleted`, ресторана и организации.
- **C2 (№2). Обменники, очереди и объявление топологии** — по разделу 6 п. 3. Письма Auth переезжают в `umir.tasks`, ключ `auth.mail`. Очередь Feedback для событий Auth называется `feedback.auth`.
- **C3 (№3). Возврат `mandatory`.** Политика задаётся по routing key в `events.md`, эталонный relay поддерживает обе:
  - **accept** (строка помечается опубликованной, `routed=false`, растёт метрика): `umir.events`, а также `auth.*.deleting`, `auth.organization.settings_changed`, `auth.membership.revoked`, `auth.assignment.revoked` — у них только fan-out потребители;
  - **retry** (это ошибка конфигурации): все ключи `umir.tasks`.
  - **C45.** Все ключи `umir.auth` — accept, включая `auth.*.deleted`. Feedback — необязательный профиль: без него очереди `feedback.auth` нет, и retry шёл бы бесконечно. События Auth — только подсказки. Feedback сверяет scope с реестром Auth (`?since=<revision>` с надгробиями, C13) при старте и периодически, поэтому пропущенное удаление всё равно дойдёт. `mq-init` объявляет `feedback.auth` только при включённом профиле Feedback.
- **C30 (№30). `aggregateRevision`.**
  - У `warehouse.*` это версия потока ресторана: подряд в пределах generation, разрыв обнаруживает потребитель.
  - У `auth.*` — монотонная, но не подряд; потребители на непрерывность не рассчитывают.
- **C38 (№38).** Единственный производитель `umir.events` — Warehouse. Gateway привязывается только к `warehouse.#`. Serving ничего не публикует.
- **C39 (№39). Темы live.** Warehouse кладёт в событие узкий набор тем, но Gateway пока рассылает все пять, как сейчас. Узкий набор включается после теста Gateway и Frontend «каждая мутация обновляет нужные экраны».

### Эталон и общий код (R15)

- **C4 (№4). Аренды и outbox.**
  - Сервисы с базой (Auth, Warehouse, Serving, Feedback) держат аренды фоновых работ в Postgres: таблица эталона `worker_leases(name PK, holder, fence bigint, expires_at)`. Redis-аренды — только у Gateway (планировщик, SSE). Это уточняет U3 и R15.
  - Эталон даёт одну форму outbox — `outbox(id uuid PK, position bigserial UNIQUE, exchange, routing_key, headers jsonb, body jsonb, org_id NULL, restaurant_id NULL, created_at, not_before, published_at, routed bool, attempts int, claimed_by, claim_fence, claim_expires_at)` — и inbox — `inbox(consumer, message_id, received_at, PK(consumer, message_id))`. Сервисы берут их без своих столбцов.
  - Блокировка предложения Serving — строка с lease и fence в самой таблице предложений. Это не фоновая работа, поэтому она вне эталона.

- **C8 (№8). Роли и миграции.**

  - Сам себя ни один сервис не мигрирует, Serving тоже. При старте каждый сервис вызывает `AssertRuntimeRole` (роль не суперпользователь и не владелец).
- **C9 (№9). Поколение и подкоманды.**

  2. Gateway, PR-1: сам читает реестр по ревизии, готовность от планировщика не зависит, старые маршруты пока работают.
  3. Auth, PR: убирает Gateway из пиров.
  4. Gateway, PR-2: убирает маршруты `runtime|registry` и JWKS-проверку для Auth без `sync-contract`.
  5. `2.0.0-DUR.2` физически удаляет операции, после этого `sync-contract` у Gateway.

  Мост совместимости есть — это шаги 2–4. FIN1-профиль для отката не трогается: у него свои старые образы.
- **C11 (№11). Сервисные токены** (DUR1 и волна 2 Auth):
  - `expiry.due` уровня ячейки, без ресторана — для списка сроков;
  - `order.resolve` для Serving → Warehouse: один ресторан, generation склада, только пассивные `/order-attempts` и `/commands`.

  Warehouse принимает оба. Повтор commit остаётся за клиентом.
- **C12 (№12).** Все бюджеты «по клиенту» на публичных входах Auth держит Gateway. Auth держит бюджеты по логину, адресу, preauth и глобальные — в Postgres, плюс грубые глобальные счётчики Redis до Argon2. Заголовка с ключом клиента в Auth нет.
- **C13 (№13). Реестр.**
  - Список: `limit/after`, `ETag`/304 по ревизии, `?since=<revision>` — изменения, включая надгробия.
  - Точечное чтение `/registry/{restaurantID}`: `ETag`/`If-None-Match`.
  - Список отдаёт только живые рестораны; надгробия — через `since` и точечное чтение, хранятся бессрочно.
  - Записи реестра отражают подтверждённую готовность, живых `Status` в чтении нет.
  - Квота 10 000 активных ресторанов, удалённые не считаются. Отказ — 409 `LimitExceeded`, `not_committed`.
- **C15 (№15). Лимиты заказа.**
  - Позиций в заказе не больше 200. Превышение — 400 `InvalidArgument`, `not_committed`.
  - Активных предложений на ресторан не больше 2000. Превышение — 409 `LimitExceeded`, `not_committed`.
  - **C43.** В действующем контракте у `ClientCommandID` и `ID` верхней границы нет, только `minLength: 1`. Ключ индекса Postgres такую длину не выдержит. DUR1 вводит `maxLength: 256` (кодовые точки) для обеих схем. Владельцы проверяют длину до записи; превышение — 400 `InvalidArgument`, `not_committed`. Браузер генерирует UUID, его это не затрагивает.
  - Числа утверждаются на G1.
- **C16 (№16). Коды допуска.**
  - 429 `RateLimited`: заголовок `Retry-After` и поле `details.retryAfterSeconds`.
  - Отказ хранилища допуска — 503 `ServiceUnavailable` (код уже в enum): `outcome` `not_committed` для записи, `unavailable` для чтения.
  - Нового кода `AdmissionUnavailable` нет. Сбой после отправки сохраняет прежние коды с `unknown`.
- **C21 (№21). Попытка склада.** Состояние на проводе — `Interrupted`. DUR1 описывает переходы: `Pending` (попытка выполняется) → `Interrupted` (выполнение прекратилось без записанного исхода). `Interrupted` разрешает точный повтор commit той же командой. Serving переименовывает своё состояние.
- **C22 (№22). Сроки для планировщика.** `GET /internal/warehouse/v2/expiry-due?asOf&limit&after` с токеном `expiry.due` и `nextDueAt` в ответе `expiry-runs`. Имена — из `warehouse.md`.
- **C29 (№29). `CommandConflict`** — во всех публичных и приватных ответах Serving, Warehouse и Auth.
  - Serving меняет код в волне 1: код уже в enum, контракт не меняется.
  - Warehouse меняет код в волне 2 через DUR1.
  - Регрессию на границе (enum ошибок scoped) ведёт Gateway.
  - Повтор команды Auth после очистки её результата — 409 `CommandConflict`, `outcome: unknown`: результат уже не известен.
- **C32 (№32). Здоровье.**
  - У каждого сервиса два адреса. `GET /healthz` — процесс жив. `GET /readyz` — основная возможность готова; тело `{instance, generation, capabilities: {<имя>: ok|degraded|down}}`.
  - Healthcheck compose смотрит `/readyz`. Подпутей `/readyz/*` нет.
  - Имена возможностей перечислены в `configuration.md`.
- **C33 (№33).** Отдельного эндпоинта метрик нет. Приёмка читает SQL владельца (возраст outbox и pending), management API RabbitMQ (DLQ), `INFO` Redis и логи. Переменные `*_METRICS_ADDR(ESS)` убираются.

### Вопросы групп

- **Frontend:**

Если хранилище недоступно, команда (поставка, списание, каталог, заказ) отправляется, а пользователь видит предупреждение: после перезагрузки результат придётся проверить в истории. Блокирует только повреждённая существующая запись — до явной отмены. Заказ ведёт себя как сейчас;
  - **C42.** У frontend `/readyz` с возможностью `static`; factory вносит её в `configuration.md`;
  - CSP-хост карты проверяется в браузере.
- **Feedback:** фикстуры RPC1.1.0 удаляются в волне 2, если `grep` по factory не находит их использования; иначе переносятся минимально. `/feedback` остаётся до C28.
- **Auth:**

  - Q10 — числа бюджетов неверных кодов не меняются, решение пользователя на G1;
  - Q11 — остаточный риск H2 принят.
- **Warehouse:** Q4 — ротация generation остаётся ручным шагом runbook; Q5 — рост журнала без срока выносится на G1.
- **Serving:** Q4 — свежесть проекции 30 с, а при недоступном брокере 5 с, принята.
- **Factory:**

### Дополнения после выравнивания подспек (C44–C46)

- **C44.** Подкоманды C9 привязаны к бинарникам репозитория. У Feedback это `server serve`, `feedback migrate` и `feedback generation rotate`, а `server healthcheck` проверяет `/readyz`. Factory сводит фактические команды всех сервисов в `configuration.md`. По этой таблице работают `stack.sh` и задания `migrate-<svc>`.
- **C46.** Унаследованный `/feedback` и файловый журнал Feedback удаляются в волне 2. Legacy-профили закреплены на старых образах, поэтому это их не ломает. Фикстуры RPC1.1.0, которые использует factory, — это тестовые инструменты, а не боевые бинарники. Они работают на тестовом memory-адаптере за новым интерфейсом `Store`, Postgres им не нужен. Запрет memory (R20, C10) относится только к боевым бинарникам.

- **C47. Маркер limiter.**
  - Если маркер пропал во время работы, сервис ставит `SET umir:limiter:strict_since <now> NX`, и все реплики отсчитывают строгое окно от этого общего момента.
  - Когда окно (самое длинное окно политики, не больше 1 ч) прошло, любой сервис восстанавливает маркер командой `SET umir:limiter:generation <настроенное значение> NX` и удаляет `strict_since`.
  - Сторож не нужен. `redis-init` по-прежнему запускается при каждом `up` и `restore`.
- **C48. Каталог событий.**
  - `eventID` — непрозрачная строка не длиннее 256 символов, уникальная у владельца; UUID не обязателен. `outbox.id` — UUID строки outbox, это отдельное поле.
  - Отсчёт 7 дней для закрытого ресторана (C23) идёт от момента, когда владелец принял закрытие (`closed_at` у владельца). Поле `closedAt` от Auth не требуется.
  - Заголовки `X-Umir-Invalidation-Required` не меняются: Gateway после R4 их игнорирует, удаление — в DUR.2.
  - Цель задержки relay: p95 не больше 1 с.
  - Redis cache стартует с `maxmemory 512mb`. Один захват — не больше 16 MiB. Скрипт квоты захватов по размеру Warehouse пишет сам под `umir:wh:`. Число уточняется замером R13.
  - Режим `legacy` склада (по сути in-memory) живёт до C28; запрет memory в бинарнике полностью выполняется после волны 3.

- **C49. `/readyz` у сервисов без хранилища.**
  - У Gateway и frontend поля `generation` в теле нет.
  - Gateway отвечает 200, когда готовы `http` и `limiter`. Без limiter защищённые операции получают 503, поэтому сервис с ним не готов.
  - `events` при недоступности даёт `degraded` и не роняет готовность.
  - Счётчики допуска пишутся в логи (C33).

- **C50.** Сверка Feedback с реестром Auth (C45) читает приватный реестр (`?since=<revision>`) по сервисному ключу Feedback — так же, как его читают Warehouse и Serving. Новый вид токена не нужен. Auth добавляет Feedback в число читателей реестра (волна 2 Auth), factory выдаёт ключ. Интервал сверки `FEEDBACK_REGISTRY_RECONCILE_INTERVAL` по умолчанию 10 минут.

- **C51. Auth без Redis.**
  - Бюджеты по клиенту и по preauth держит Gateway (C12, C26).
  - Надёжные бюджеты Auth остаются в Postgres, в той же транзакции, что и действие: выдачи кодов (регистрация 30, сброс 60 за 10 минут), лимиты по адресу и логину, неверные коды.
  - Ограничитель Argon2 остаётся процессным `verificationGate`: две реплики дают вдвое больший предел, и это допустимо.
  - Redis-клиента у Auth нет, маркер C47 его не касается. Это уточняет C12 и отступает от #17 (там Auth владел грубым допуском в Redis), чтобы не дублировать Gateway.
- **C52. Файлы секретов Auth.** `secrets.sh` создаёт `owner.json`, конфигурацию и пароль первого администратора с владельцем uid/gid 65532 и режимом 0600. Каталог монтируется в Auth только на чтение, проверки `ReadPrivateFile` не ослабляются. `/healthz` и `/readyz` у Auth отвечают без сервисного ключа (C32).
- **C53. Повторы и квоты в DUR1.** После истечения 180-дневного надгробия (раздел 6 п. 4) повтор старой команды выполняется как новая. Это записывается в DUR1 как граница гарантии повтора. Статус `LimitExceeded` зависит от операции: 409 для квот (C13, C15) и 503 для существующих чтений страниц; DUR1 отмечает это явно.

### Решения по CR волн 0 и 1 (16.10)

- **C54 (CR 03). Sticky SSE без `consistent`.** На `nginx-unprivileged:1.30.5` связка `hash … consistent` + `server … resolve` раздаёт потоки по кругу (проверено тестом frontend). Действует обычный `hash $umir_live_key` с `zone`, `resolver` и `resolve`. При двух репликах (U7) разницы нет. При смене состава реплик переразмещается больше сессий, клиент получает `refresh-required` и перечитывает данные. Формулировки `hash … consistent` в подспеках frontend, factory и gateway читать как C54.
- **C55 (CR 02). `error_log` Nginx frontend — уровень `crit`.** Журнал ошибок не настраивается форматом и на уровне `error` пишет `client: <адрес>` и строку запроса, а правило ПДн (раздел 8) исключений не допускает. Frontend ставит `error_log stderr crit;`. Ошибки апстрима видны по статусам 502/504, `upstream_status` и `request_id` в журнале доступа. Срок 14 дней (раздел 8, «Журналы») остаётся для всех журналов Nginx.

- **C56 (CR 04, ревью W0 B1). Повторы и DLQ — как в эталоне.** Ключ dead-letter очереди `<q>` — `<q>.dlq`. Ошибку обработчика переносит сам потребитель: копия уходит в `<q>.retry` (TTL 30 с, возврат в `<q>`), подтверждение издателя приходит до `ack` исходного. Номер попытки — заголовок `x-umir-attempt`. После 5-й неудачи сообщение уходит в `<q>.dlq`. `x-delivery-limit` 5 у quorum-очереди остаётся защитой от падений процесса посреди обработки. Обработчики идемпотентны. Повторная подача из `.dlq` сбрасывает `x-umir-attempt`. Документ `events.md` и README эталона описывают ровно это; тест сверки документа проверяет аргументы очередей.
- **C57 (CR 05). Пассивная проверка топологии** видит только отсутствие обменника или очереди. Несовпадение аргументов ловит лишь `Declare` в `mq-init`. Возможность `events` недоступна, когда объектов топологии нет.
- **C58 (CR 06). Уточнения DUR1 приняты (п. 1–5 CR):** `maxLength: 256` из C43 вводится для `ID` (у `ClientCommandID` он уже есть в REG1); исходы `CommandConflict` разведены по CR; `gateway` в `LifecyclePeerReadiness` и `LifecycleResult.services` живёт до `2.0.0-DUR.2`; форма `Registry` — по CR (`nextAfter` есть ровно при `complete = false`, `limit` 1–1000); `RateLimited` везде несёт `details.retryAfterSeconds` и `outcome: not_committed`.
- **C59 (ревью W0 B2). Имена возможностей `/readyz`** — `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)?$`, чтобы проходили `delivery.smtp` и `delivery.telegram`. Примеры здоровья в DUR1 используют только имена из `configuration.md`. Составные файлы перегенерируются, таблица SHA-256 обновляется.
- **C60 (ревью W0 B3). Идентификаторы конверта.** `eventID` — печатный ASCII без пробела, до 256 символов. `causationID` и `correlationID` — до 256 кодовых точек без управляющих символов, потому что Warehouse кладёт туда `commandID` клиента.
- **C61 (CR 07). ACL Gateway в limiter** — исключение к C17: `GET`, `SET NX` и `DEL` только на `umir:limiter:generation` и `umir:limiter:strict_since`; скрипты через `+evalsha` и `+script|load` (не `+eval`). Тест ACL проверяет отказ на чужих ключах и на `FLUSH*`, `CONFIG`, `KEYS`, `DEBUG`, `SHUTDOWN`.
- **C62 (CR 08). Redis cache:** `maxmemory 512mb` (C48), слоты и захваты делят один пул `allkeys-lru`; замер R13 это учитывает.
- **C63 (CR 09). Конфигурация:** п. 1, 2, 5, 6, 7 CR — как в `configuration.md`. Healthcheck Auth — подкоманда `/server healthcheck` на листенере без ключа (листенер назван в `configuration.md`). Шесть секретов Feedback переходят на `_FILE` в волне 2 Feedback; волна 1 опубликована без этого.
- **Relay (ревью W0 M1).** После `Nacked` или `Unknown` relay делает общую паузу с ростом до 5 с, чтобы не клеймить строки впустую и не пускать поздние события агрегата вперёд задержанных.

# G1: пакет решений по переходу «Ровного хода» на PostgreSQL + RabbitMQ + Redis

G1 — ваша остановка после волны 0: вы утверждаете числа ниже, после этого все группы идут в волну 2 (запись в Postgres, RabbitMQ, Redis).
Все числа — «предложение до G1» из `00-orchestration.md` (разд. 6, 10) и документов волны 0. Меняются в одном месте у владельца, без правки логики.

Слова. **Окно** — отрезок, в котором считаем запросы (20 в минуту = окно 1 минута). **Аренда** — слот, занятый, пока его продлевают; перестали продлевать — освободился. **Надгробие** — след записи без личных данных (отпечаток), чтобы повтор команды не выполнился заново. **Строгий режим** — после потери счётчиков в Redis лимиты временно сжаты (не до нуля).

## 5. Рост журнала склада (Q5)

Журнал склада (история, партии, расход по FEFO) — источник истины для остатков. Срок для действующего ресторана: **без срока**. Объём при полной цели (100 организаций × 100 ресторанов, ориентир 100 заказов в день на ресторан): около 1 млн заказов и 2–3 млн строк журнала и outbox в сутки, сотни ГБ в год. Размер строки с индексами не измерен (замерят на `tests/seed`). Данных по стенду сегодня в источниках нет. Outbox и так чистится через 7 дней.

Скорость вместе с журналом больше не растёт: `make perf` склада зелёный. «До» → «после» на 8000 заказах (машина была занята, цифры шумные): commit 17,8 мс → 37 мкс; Movements 23,1 с → 7 мс; восстановление с журнала 31,8 с → 29 мс; heap владельца 12,8 → 0,5 MiB. Рост 1000 → 8000 заказов: восстановление было до 62×, стало ≈9×. Остаётся цена диска, бэкапа и восстановления. Журнал разбит на 16 секций по хэшу ресторана; архива нет.

| Вариант | Что это | Плюс | Минус |
| --- | --- | --- | --- |
| A. Без срока (предложено) | Хранится всё, пока ресторан действует | История и повтор команд всегда на месте | Диск и бэкап растут линейно, сотни ГБ в год при полной цели |
| B. Срок и отсечка | Старые секции удаляются или уходят в архив через N месяцев | Диск ограничен | Числа N нет в источниках. Архива нет, его надо делать. Теряются история и FEFO-факты за срок |
| C. A сейчас, срок решить на G2 по замеру | Принять A, замерить размер строки на seed и R13, поставить порог тревоги по диску | Решение по факту | Откладывает решение; диск ВМ проверить до выката |

Рекомендую **C**: удалить данные позже можно, вернуть нельзя.

## 7. Бюджеты нагрузки R13

Приёмка: 10 000 ресторанов, 100 клиентов, 30 минут (W3.6). Без утверждённых порогов нагрузка выдаёт отчёт без вердикта.

| Что | Предложение | Почему | Если увеличить / уменьшить |
| --- | --- | --- | --- |
| Операции одного ресторана | Остаются в текущих HTTP-бюджетах | Чужие рестораны не тормозят ваш | Чисел бюджетов в источниках не нашёл; взять из таймаутов сервисов |
| Рост из-за чужих ресторанов | В 10 раз больше посторонних — меньше 2× по работе и задержке | Стоимость не должна расти с историей | Строже: легче не пройти. Мягче: скроет деградацию |
| Горячая память | Выходит на плато | Не растёт с историей | — |
| Склад: цели FIN-10 | commit ≤ 5 мс, replay ≤ 2 с, Movements ≤ 2 с, heap на ресторан ≤ 15 MiB | Уже выполнены на 8000 заказах (разд. 5) | Для R13 нужен прогон на Postgres |
| Задержка relay (outbox → брокер) | p95 ≤ 1 с | C48 | Больше: живое обновление запаздывает |
| Свежесть проекции Serving | 30 с, при недоступном брокере 5 с | Принято | Больше: устаревшие данные заказа |
| p50/p95/p99 запросов, память контейнеров | **нет предложения** | В источниках чисел нет | Способ: пробный 10-минутный прогон на 10 клиентов; потолок = результат × запас, который выберете вы |
| Redis cache `maxmemory` | 512 MiB, уточнит замер | Один захват страницы до 16 MiB | Меньше: чаще вытеснение захватов |
| Redis limiter `maxmemory` | 128 MiB (≈500 000 записей допуска, оценка) | Хватает для лимитов | При нехватке отказ 503 до отправки владельцу |

Для справки: у Auth чтение готовности при 100 тыс. сессий занимало 16 МБ на вызов, теперь 288 Б (исправление волны 1, не решение G1). Нагрузка `AccessCheck` на Auth не замерена.

Варианты: A. Принять пороги таблицы, остальные числа назвать после пробного прогона. B. Дать числа сейчас без замера (риск нереалистичных). C. Принять принципы (две первые строки), p95/p99 пусть предложит Factory по пробному прогону, утвердить на G2. Рекомендую **C**.

## 8. Порядок R3 (C7): Gateway выходит из пиров Auth

Почему: готовность Gateway от планировщика ломала вход (C01), а две реплики Gateway нельзя держать, пока Auth опирается на него. Gateway сам читает реестр Auth по ревизии.

Порядок слияния (строго): (1) DUR1 помечает операции Gateway устаревшими. (2) Gateway PR-1: сам читает реестр, старые маршруты работают. (3) Auth PR: убирает Gateway из пиров. (4) Gateway PR-2: убирает маршруты `runtime|registry`. (5) `2.0.0-DUR.2` физически удаляет операции. Шаги 2–4 — мост совместимости; откат на FIN1 не трогается, у него свои образы.

| Вариант | Плюс | Минус |
| --- | --- | --- |
| A. Пять шагов (предложено) | После каждого PR `main` рабочий | Больше PR, старые маршруты временно живут рядом |
| B. Gateway и Auth одним согласованным слиянием | Меньше шагов | Нет моста, промежуточное состояние ломает вход, откат тяжелее |

Рекомендую **A**: цена один лишний PR.

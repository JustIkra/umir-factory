# Наблюдаемость базовой версии

Дата: 2026-10-10. Часовой пояс: Europe/Moscow.

Статус: **предложение для рассмотрения** по запросу пользователя. JSON-логи, метрики, трассировка и описанные ниже проверки ещё не реализованы. Названия полей, инструментов и пороги в этом документе предложены автором; они не обозначают согласование новых бизнес-правил.

Цель: по одному запросу восстановить путь gateway → serving → warehouse, отличить отказ от неизвестного исхода записи и обнаружить обработчик, который перестал продвигаться. [Основная спецификация](business-core.md) определяет поведение склада и заказов; наблюдаемость описывает выполнение этого поведения.

Текущий этап — логический каркас и его проверки в памяти. Сейчас проектируются записи прикладных операций, spans вызовов in-memory порта и снимки метрик; отдельный сетевой бизнес-API не добавляется. Контракт HTTP-корреляции применяется при последующей реализации API. Подключение хранилищ телеметрии и панелей относится к следующему этапу фабрики. Описание этих границ ниже нужно для совместимого развития, а не для увеличения первой реализации.

## 1. Три вида данных

| Сигнал | Для чего используется | Предложение для базовой версии |
| --- | --- | --- |
| Логи | Что произошло с конкретным запросом, командой и попыткой | Структурированный JSON через Go log/slog; вывод контейнеров. |
| Метрики | Ошибки, задержки, очередь и отсутствие прогресса | Снимок/registry в памяти; на этапе HTTP — Prometheus-совместимый GET /metrics каждого Go-сервиса. |
| Трассы | В каком сервисе и на каком шаге потрачено время | OpenTelemetry; HTTP server/client spans и spans основных операций. |

Журнал EventStore остаётся источником бизнес-фактов. Логи могут быть потеряны при аварии или переполнении доставки; наличие логов успеха не заменяет проверку записанного заказа. История движения партий читается из событий. Технические логи дополнительно описывают отклонённые запросы, повторы, ошибки и ожидание.

Go предоставляет [JSONHandler для построчного JSON](https://pkg.go.dev/log/slog#JSONHandler). OpenTelemetry Go поддерживает трассы и метрики; [статус компонентов](https://opentelemetry.io/docs/languages/go/) нужно учитывать при выборе версий. Предложение использует slog для логов и не требует перехода на отдельный OTel Logs SDK.

## 2. Связь запросов и команд

- Gateway назначает новый request_id каждому внешнему HTTP-запросу. Этот ID передаётся внутренним сервисам в X-Request-ID и возвращается клиенту тем же заголовком, включая ответы с ошибкой. Новый внешний повтор получает новый request_id. При прямом внутреннем вызове без ID принимающий сервис назначает его сам.
- Валидный traceparent извлекается стандартным W3C Trace Context propagator. Без него создаётся корневая трасса. Вызовы gateway → serving/warehouse и serving → warehouse передают traceparent и поддерживаемый tracestate; каждый span имеет собственный span_id. Произвольный baggage базовой версии не нужен. [Механизм передачи контекста](https://opentelemetry.io/docs/concepts/context-propagation/) стандартный, собственный протокол трассировки не вводится.
- command_id сохраняется при повторе бизнес-команды по основной спеке. Он не равен request_id или trace_id. Разные HTTP-попытки одной команды могут принадлежать разным трассам.
- attempt_id различает отдельные попытки расчёта/записи внутри выполнения warehouse. После доказанного конфликта начинается новая попытка. В живом процессе повтор исходной неопределённой записи сохраняет её attempt_id и исходные события; отдельный повтор отправки записи отмечается send_attempt. После перезапуска технический attempt_id может измениться; поиск записанного результата по-прежнему использует command_id/proposal_id.
- Фоновый цикл получает новый run_id и корневой trace. У него нет клиентского request_id. Партии и списания связываются через batch_id и command_id; месячная задача не удерживает контекст HTTP-запроса поставки.
- ID наблюдаемости генерируются инфраструктурой независимо от доменной функции newID. Время логирования не вызывает доменный now и не меняет evaluatedAt. Контекст наблюдаемости не входит в отпечаток команды, payload бизнес-событий или снапшот.

Для in-memory порта передаётся context.Context; те же поля доступны обработчикам без HTTP. Стандартный JSONHandler сам не извлекает trace_id/span_id: их добавляет прикладной адаптер из SpanContext. Формат этих полей следует [рекомендациям для JSON-логов](https://opentelemetry.io/docs/specs/otel/compatibility/logging_trace_context/).

## 3. Формат логов и уровни

Каждая запись содержит time, level, msg, event, log_schema_version=1, service, version и instance_id. time — RFC3339Nano со смещением +03:00; version — SHA сборки, instance_id — идентификатор запуска процесса. При наличии контекста добавляются request_id, trace_id, span_id и trace_flags. Для операции добавляются известные command_id, proposal_id, order_id, delivery_id, batch_id, attempt_id, state_version и evaluated_at.

time фиксируется при создании записи, а не при поздней выгрузке. Длительности измеряются техническими монотонными часами; в тестах измеритель управляемый. Техническое время отделено от фиксированного времени бизнес-решения.

INFO используется для начала/окончания запросов, записанных фактов и ожидаемых бизнес-результатов. Уменьшенный состав, EmptyOrder, ProposalSuperseded, ConfirmationPending и повтор записанной команды — ожидаемые результаты. WARN используется для восстановленного пропуска индекса, повторного расчёта после конфликта и восстановимых инфраструктурных проблем. ERROR используется для InventoryUnavailable, неизвестного исхода записи, panic и необработанных технических ошибок. DEBUG показывает дополнительные шаги; обязательные записи API сохраняются при стандартном уровне INFO.

HTTP-запись содержит method, route, status_code, duration_seconds, outcome и ограниченный error_code. route — шаблон обработчика без конкретных ID; неизвестный маршрут обозначается unmatched. При отсутствии отправленного статуса status_code=0; нельзя записать неотправленный 200. outcome HTTP описывает completed, cancelled или aborted, отдельно от результата бизнес-команды.

Логируются все принятые API-запросы, включая неизвестные маршруты, ошибки валидации и healthz. На входе — http.request.started, при завершении — http.request.finished. При аварии процесса запись завершения может отсутствовать; это не доказательство успеха или отказа команды. Запрос метрик также виден как технический маршрут; на прикладной панели healthz и metrics рассматриваются отдельно от бизнес-API.

Логи содержат выбранные ID, коды результатов, счётчики и версии. Тела запросов/ответов, Authorization, Cookie, токены и произвольная query-строка не включаются в стандартную запись. Техническое сообщение ошибки проходит адаптер нормализации. Методы и коды для метрик берутся из фиксированных наборов; неизвестные значения объединяются в other.

## 4. Какие операции отражать

| Место | Обязательные записи или span events | Что должно быть видно |
| --- | --- | --- |
| HTTP gateway, serving, warehouse | http.request.started/finished, upstream.call.started/finished | Метод, маршрут, статус, длительность, сервис назначения и ошибка связи. |
| Прикладной обработчик | operation.started/finished | Тип операции, ID, результат, версия и время оценки. |
| Подготовка склада | inventory.prepare.started/finished | Причина запуска, время ожидания доступа, восстановление проекции, результат подготовки. |
| Индекс истечения | expiration.index.reconciled при восстановлении либо ошибка подготовки | Версии, количество восстановленных/удалённых задач; известное нарушение закрывает допуск до восстановления. Произвольный незаметный пропуск при корректных маркерах обычная подготовка не гарантирует обнаружить. |
| Цикл просрочки | expiration.cycle.started/finished | trigger=tick/request/recovery, run_id, число задач, завершённых списаний и результат. Пустой успешный цикл тоже фиксирует прогресс. |
| AppendBatch | event_store.append.started/finished | expected_version, типы/ID событий и исход committed/replayed/conflict/rejected/unknown. |
| Установленная новая запись события | business.event.committed | event_id, sequence, command_id, тип события и ID связанных сущностей. |
| Подтверждение предложения | confirmation.pending.started/resolved, operation.finished | Возраст ожидания, исходный command_id, найденный заказ либо определённый результат без записи. |
| Замена предложения | proposal.replaced после успешного сохранения | Старый/новый proposal_id, число уменьшенных/удалённых позиций. |
| Восстановление и снапшот | recovery.started/finished, snapshot.save.finished | Исходная версия, использование снапшота, число применённых событий, ошибка и итоговая версия. |

Для операции outcome берётся из фиксированного набора: committed, replayed, no_change, recheck_required, rejected, failed, unknown. Для serving результат дополнительно содержит точное имя из основного контракта, например OrderConfirmed или RequiresConfirmation. Запросы чтения используют no_change как отсутствие собственной бизнес-записи; подготовка склада внутри них отдельно отражает BatchExpired.

business.event.committed выпускается при установленной новой записи. Повтор уже записанной команды имеет outcome=replayed. Replay при восстановлении отражается сводкой recovery и при необходимости DEBUG-записями; он не выдаётся за новые продажи и списания. После сбоя между записью и логированием факт проверяется через журнал.

Неизвестный исход оформляется outcome=unknown, а не committed/rejected. Если OrderPlaced записан, последующий сбой очереди или снапшота отражается отдельной технической записью; успешный факт не переименовывается в отказ. Определённый InventoryUnavailable до попытки OrderPlaced отражается как отказ подготовки и разрешение незавершённого подтверждения без заказа.

## 5. Трассировка

Трасса подтверждения должна показывать HTTP gateway, вызов serving, ожидание сериализации предложения, вызов warehouse, ожидание склада, подготовку проекций, обработку просрочки, повторную оценку и AppendBatch. Замена предложения или поиск уже записанного результата видны отдельными шагами. span начинается до ожидания соответствующего доступа, чтобы блокировка не исчезла из длительности.

HTTP server/client spans создаются библиотекой OpenTelemetry для net/http. Логические шаги имеют ручные spans с фиксированными именами. ID сущностей являются атрибутами, а не частью имени span. Бизнес-результат и ошибка транспортного span различаются: потерянный ответ может сопровождать уже записанный OrderPlaced.

В базовой версии локальные корневые трассы записываются полностью. Входное решение sampling сохраняется через ParentBased sampler; независимо от него записи API и бизнес-операций выпускаются полностью. Экспорт трасс асинхронный с ограниченной очередью. Его доступность не участвует в допуске к складу.

## 6. Минимальные метрики

Имена ниже — предложенный контракт проекта. Они не обозначают автоматически создаваемые метрики библиотеки. service/instance задаются идентичностью target или ресурсом; названия измерений и наборы значений фиксируются в коде.

HTTP, process_started и telemetry_failures относятся ко всем Go-сервисам. operation_results относятся к serving и warehouse. confirmation относится только к serving; expiration, projection и stream — только к warehouse. Сервис не экспортирует чужие бизнес-метрики как нулевые. Правила алертов выбирают target соответствующего сервиса; отсутствие цикла просрочки в gateway не считается остановкой обработчика.

| Метрика | Тип и смысл | Допустимые labels |
| --- | --- | --- |
| umir_http_requests_total | Counter завершённых HTTP-попыток | method, route, status_code, outcome |
| umir_http_request_duration_seconds | Histogram длительности завершённых запросов | method, route |
| umir_http_requests_in_flight | Gauge незавершённых запросов | Нет дополнительных labels. |
| umir_http_oldest_request_started_timestamp_seconds | Gauge начала самого старого незавершённого запроса; 0 при отсутствии | Нет дополнительных labels. |
| umir_operation_results_total | Counter результатов отдельных выполнений; повтор также считается выполнением | operation, outcome, error_code |
| umir_confirmation_pending | Gauge числа предложений с pendingCommandID | Нет дополнительных labels. |
| umir_confirmation_oldest_pending_timestamp_seconds | Gauge самого раннего начала ещё незавершённого подтверждения; 0 при отсутствии | Нет дополнительных labels. |
| umir_expiration_next_due_timestamp_seconds | Gauge ближайшего expiresAt партии с положительным остатком из InventoryState; 0 при отсутствии | Нет дополнительных labels. |
| umir_expiration_last_success_timestamp_seconds | Gauge окончания последней успешной подготовки истечения, включая пустой цикл; 0 до первого успеха | Нет дополнительных labels. |
| umir_projection_last_sequence | Gauge последней полностью применённой команды проекции | projection=inventory/expiration |
| umir_stream_last_sequence | Gauge последней известной подтверждённой версии потока | Нет дополнительных labels. |
| umir_process_started_timestamp_seconds | Gauge времени старта текущего процесса | Нет дополнительных labels. |
| umir_telemetry_failures_total | Counter ошибок доставки и отброшенных записей | signal=logs/traces; reason из фиксированного набора |

request_id, trace_id, command_id, proposal_id, batch_id, product_id и delivery_id используются в логах/трассах. Они не становятся labels метрик. Это ограничивает число временных рядов согласно [рекомендациям Prometheus](https://prometheus.io/docs/practices/instrumentation/). operation, error_code и route берутся из зарегистрированных наборов, а не произвольного входного текста.

Метрики timestamp экспортируют Unix seconds, потому что это формат вычислений Prometheus. Это техническое представление момента времени; доменные даты и логи остаются московскими. Возраст вычисляет мониторинг как time() - timestamp. Приложение не обязано обновлять счётчик возраста, когда обработчик завис. [Prometheus рекомендует экспортировать момент события](https://prometheus.io/docs/practices/instrumentation/#timestamps-not-time-since).

Снимок метрик обновляется на старте/завершении запросов, смене pendingCommandID и применении/восстановлении событий. Начало pending фиксируется один раз и не обновляется при точном повторе. Ближайший срок берётся из InventoryState, чтобы пропуск задачи в индексе не скрывал задержку. Источник последней версии — подтверждённые чтения/записи EventStore; это последняя известная версия, не дополнительный запрос к базе при каждом scrape.

Механизм поддержания next_due независимо от рабочего индекса и его стоимость нужно определить при реализации наблюдаемости. Это предложенный диагностический сигнал, а не обещание обнаружить любую незаметную порчу или требование вернуть полный скан в обычную подготовку склада. Фоновое сохранение снапшота отражает завершение своего задания с захваченной версией; назначение задания не считается успешным сохранением.

GET /metrics читает отдельный потокобезопасный снимок, не захватывает блокировку бизнес-операции и не запускает ProcessDueExpirations. Маршрут /metrics исключён из gauges in_flight/oldest и гистограммы прикладных задержек, чтобы scrape не наблюдал сам себя; его завершения допускаются в requests_total с отдельным route. Снимок может отставать от записи при аварии; метрики не используются для учёта количества реальных продаж.

## 7. Как обнаружить отсутствие движения

Предложенные пороги предназначены для демо и задаются настройками наблюдаемости. expirationCheckInterval остаётся существующей настройкой приложения.

| Ситуация | Условие обнаружения | Начальный порог |
| --- | --- | --- |
| Сервис не отвечает мониторингу | Prometheus up=0 | 30 секунд. |
| Запрос застрял | in_flight > 0 и возраст oldest_request выше порога | 30 секунд. |
| Подтверждение не разрешается | pending > 0 и возраст oldest_pending выше порога | 30 секунд. |
| Просрочка не списывается | next_due > 0 и time() - next_due выше порога | max(30 секунд, 3 × expirationCheckInterval). |
| Цикл истечения остановился | Последний успех слишком старый либо отсутствует после запуска | max(30 секунд, 3 × expirationCheckInterval); начальное ожидание 30 секунд. |
| Индекс отстаёт | Версия inventory/expiration ниже последней известной версии потока | Непрерывно 30 секунд. |
| Подготовка или запись дала техническую ошибку | Новый результат failed с техническим error_code либо unknown | Сразу в логах и на панели ошибок. |

Для нулевых timestamp сигнал возраста отключён. Отсутствие первого успешного цикла проверяется по umir_process_started_timestamp_seconds при up=1, а не как возраст от 1970 года. Пустой склад и нулевой RPS сами по себе не являются ошибкой. Будущая задача не считается просроченной. HTTP healthz подтверждает работу процесса, а сигналы выше показывают прогресс бизнес-обработчиков.

Алерт сообщает о необходимости диагностики. Повтор выполняется обычным контрактом команды; просрочка обрабатывается существующим ProcessDueExpirations. Телеметрия не создаёт новых движений склада и не снимает pendingCommandID по таймауту. Возраст очереди не добавляет второй допуск партии к приготовлению.

## 8. Пример разбора ошибки

1. Клиент подтверждает proposalID=P1, commandID=C1. Gateway выдаёт request_id=R1; сервисные spans входят в одну трассу.
2. Warehouse фиксирует начало подготовки, затем ошибку обязательного BatchExpired. Результат подготовки — InventoryUnavailable; OrderPlaced для C1 не пытались записать.
3. Serving отражает определённый исход без заказа и снятие pendingCommandID. Ответ клиенту содержит X-Request-ID=R1. Логи по R1 показывают причину; command_id=C1 связывает последующий повтор.
4. Если ответ потерян после записи OrderPlaced, API отмечает техническую неопределённость. Повтор C1 получает новый request_id, находит исходный заказ и отражает replayed. История содержит одну продажу.

Frontend сохраняет request_id из ответа для диагностики запроса. Ошибка сети до ответа видна в структурированной записи браузерного API-клиента с методом, маршрутом, временем и типом ошибки; серверный ID в таком случае может быть неизвестен. Удалённый сбор браузерных логов в этом предложении не определён. Интерфейс не отображает неподтверждённый заказ как успешно оформленный.

## 9. Размещение и отказ доставки

Инструментация находится на границах HTTP, прикладных команд, вызовов портов и адаптеров EventStore/SnapshotStore. Она не требует интерфейса логгера у каждой сущности или добавления ObservabilityService к бизнес-графу. Общие функции подключения можно разместить в инфраструктурном пакете каждого Go-сервиса; отдельный публичный репозиторий SDK не нужен.

Логи первоначально доступны через docker compose logs. Для HTTP-этапа предлагается отдельный внутренний listener метрик на порту 9090 каждого Go-контейнера, без публикации порта хоста. Бизнес-HTTP остаётся на 8080; маршруты gateway не передают запросы на 9090. Это сохраняет /metrics внутри сети сборки. OTLP endpoint трасс задаётся конфигурацией. Для текущих тестов используются приёмники в памяти без запуска этих listener и внешнего backend.

Визуальное хранилище логов/трасс и мониторинг с панелями оформляются следующим этапом фабрики после выбора backend; Prometheus/Grafana — предложение для метрик, backend трасс ещё не выбран. Подключение этого стека не меняет закреплённые сервисные образы автоматически.

Очереди доставки логов и трасс ограничены. Для логов предложена очередь до 4096 записей с drop-new при переполнении и счётчиком telemetry_failures; запись в stdout выполняется вне блокировки склада. Slog JSONHandler сам по себе синхронный: ограниченную асинхронную доставку обеспечивает прикладной адаптер. Для OTLP используется ограниченный batch processor и конечный timeout. Конкретные размеры SDK-очереди и timeout можно выбрать при реализации.

Сбой доставки телеметрии отражается собственной диагностикой и не меняет результат AppendBatch, заказа или списания. Повторная диагностика отказавшего sink не должна рекурсивно писать в него без ограничения. Shutdown выгрузки ограничен отдельным бюджетом, предложено 2 секунды. Это применение [принципов обработки ошибок OpenTelemetry](https://opentelemetry.io/docs/specs/otel/error-handling/) к нашему контракту; сбой обязательного бизнес-списания по-прежнему возвращает InventoryUnavailable.

## 10. Приёмочные проверки

Это запланированные проверки, а не выполненные тесты. Для логов используются записи в памяти, для spans — тестовый exporter, для метрик — тестовый registry и управляемое техническое время. Доменные now/newID остаются прежними.

### 10.1. Текущий этап: каркас в памяти

- Прикладная операция получает started/finished с ID, кодом результата и версией. Вызов in-memory порта сохраняет контекст и родительскую связь spans.
- Повтор C1 сохраняет command_id и возвращает replayed. Поля наблюдаемости не меняют отпечаток, последовательность вызовов доменных now/newID или события команды.
- Незавершённый pending сохраняет первоначальный timestamp. По этому снимку и продвинутому техническому времени возраст растёт без работы обработчика.
- Пропущенная задача при положительном остатке остаётся видна по next_due из InventoryState. Пустой успешный цикл обновляет last_success.
- InventoryUnavailable не сопровождается логом нового OrderConfirmed или business.event.committed для OrderPlaced. Неизвестный исход не переименовывается в отсутствие заказа.
- Сбой индекса/снапшота после OrderPlaced оставляет успешный бизнес-факт. Replay при восстановлении не увеличивает число новых записей событий.
- Чтение MetricsSnapshot работает при занятой блокировке склада и не создаёт бизнес-событий. Конкретные ID не появляются в labels.
- Тестовый exporter, возвращающий ошибку, и переполненная очередь логов дают потерю телеметрии с диагностикой; результат записанного заказа не меняется. Не возникает рекурсивного потока ошибок.

### 10.2. Последующий этап: HTTP-границы

- Успешный API-запрос, 404, ошибка валидации и технический сбой дают started/finished с одинаковым request_id и корректным статусом. При отмене без отправленного статуса не появляется ложный 200.
- Через gateway → serving → warehouse сохраняется request_id/trace_id и корректная родительская связь spans. Невалидный traceparent не ломает запрос.
- Новый внешний HTTP-повтор получает другой request_id, сохраняя command_id. В браузере доступен ID из ответа.
- Зависший запрос сохраняет первоначальный oldest_request timestamp. Завершение/отмена освобождает gauge; маршрут metrics не включает себя в in_flight.
- GET /metrics читает снимок при занятой блокировке склада; маршрут доступен на внутреннем listener и отсутствует на бизнес-порту/маршрутах gateway. Технические маршруты отделяются на панели прикладных задержек.

### 10.3. Последующий этап: сборка мониторинга

- Логи и spans позволяют найти одну операцию во всех сервисах по ID; метрики снимаются с ожидаемых внутренних targets.
- Алерты pending применяются к serving, а истечения/проекций — к warehouse. Gateway не получает ложный сигнал отсутствия цикла просрочки.
- Мониторинг вычисляет растущий возраст неизменного timestamp и показывает остановленный обработчик. Будущая задача, нулевой RPS и отсутствие pending не вызывают сигнал задержки; до первого цикла действует начальное ожидание.
- Отключённый backend/OTLP endpoint не меняет бизнес-результат; ошибки доставки видны через оставшиеся доступные сигналы. Алерт не снимает pending и не создаёт движения склада.

Проверки 10.2–10.3 не входят в первый каркас в памяти. До их этапов не требуются сетевой бизнес-API, работающий listener метрик, мониторинг или внешние хранилища.

## 11. Что нужно рассмотреть

Предлагается принять этот минимальный контракт сигналов, корреляции, отсутствия прогресса и изоляции доставки. Названия полей/метрик и демо-пороги являются предложениями автора. Конкретный backend, панели, доставка алертов и срок хранения выбираются перед реализацией стека фабрики. Внешние уведомления сейчас не подключены.

Основная спека теперь определяет чтение справочников и независимые оценки блюд через EvaluateMenu. Observability использует эти контракты и не меняет бизнес-правила. Её инструменты и пороги остаются предложениями; код, зависимости, Compose и CI этим документом не изменяются.

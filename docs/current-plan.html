Закончить версию для защиты.

Убрать зависания, добавить CI Auth и собрать сервисы с готовым интерфейсом в один воспроизводимый запуск. Закрыть обязательный пункт М6 в минимальном виде, усилить горячие предложения и выложить сборку по ссылке. Остальные нереализованные функции остаются за пределами этой работы.

Документ описывает будущие изменения. Новые исправления, CI, публикация и деплой ещё не выполнены.

Просроченная партия автоматически переходит в «ожидает списания». Окончательно списывает человек с ролью «Склад».

Это правильный текущий сценарий. Автоматическое окончательное списание добавлять не требуется: Д1 в ТЗ необязателен. На защите подаём это как осознанный выбор — система сама выводит просрочку из оборота, а списание подтверждает ответственный.

Стабильность существующих механизмов

FIN-01CI Auth — обязательный минимумПроверки PR/main, production image и публикация из проверенного commit.Auth+

Изменить

Добавить workflow с repository-pinned Go/tools, полными quality/race gates и сборкой production image. PR проверяется без publishing secrets. GHCR job запускается после gates для разрешённого main push; SHA tag, OCI revision и digest связываются с одним commit.

Готово, когда

Есть зелёный CI именно на final source SHA. Ошибка gate блокирует публикацию; production image проходит start/health. После отдельно разрешённой публикации registry readback подтверждает exact identity. Локальная сборка не закрывает remote CI.

FIN-02Auth восстанавливается после временного сбояПочтовый timeout не оставляет постоянный 503; сеть вне общей блокировки.Auth+

Изменить

Разделить временные IO failures и действительно фатальные ошибки authority. Сохранить реальные mail outcomes и retry policy. Выполнять peer calls вне Accounts mutex; перед commit повторно проверить revision, lifecycle и epochs.

Готово, когда

После mail/peer timeout и восстановления Auth снова обслуживает JWKS и независимые запросы без restart, ресторан доходит до ready. Storage corruption продолжает закрывать admission. Нет stale-ready результата или изменения mail semantics.

FIN-03Ошибки входа одного пользователя не блокируют всехLogin throttle по login; корректное чтение текстовых password files.Auth+

Изменить

Сохранить лимиты, но изолировать login failure counter по сравнимому login. Для текстовых password/SMTP files убрать один завершающий LF/CRLF, сохранив значимые bytes и пробелы. Binary keys не нормализовать. Ошибка старта показывает безопасную причину без секретов.

Готово, когда

Пять неверных входов A не запрещают корректный вход B; cooldown A сохраняется. Known/unknown login, capacity, concurrent attempts, LF/CRLF/без newline и пустые файлы проверены. User existence и credentials не раскрываются.

FIN-04Подтверждение заказа не зависает навсегдаПовтор исходного commit с тем же commandID в том же Warehouse epoch.Serving+

Изменить

Для unresolved attempt разрешить bounded retry исходного commit, когда warehouse подтверждает unseen в сохранённом epoch. Сохранить commandID, proposal, payload и scope. Pending работа не дублируется; известный terminal result закрывает попытку.

Готово, когда

Сбой до доставки и потеря ответа после commit сходятся к одному результату после восстановления сети. Заказ и списание возникают один раз. Changed payload отвергается; epoch change не превращает старый unknown в успех.

Обязательное ТЗ и критерии жюри

FIN-11Предложение поставок (М6), минимальная версияОбязательный пункт базового мониторинга. Считается из уже имеющихся данных склада.Warehouse + Frontend+

Изменить

Для каждого продукта посчитать расход за последние N дней по заказам и списаниям, средний суточный расход и число дней, на которое хватит доступного остатка. Просроченные и ожидающие списания партии в запас не входят. Предлагать поставку, если запаса меньше порога (например, 3 дня) или продукт держит блюдо в стоп-листе. Объём — до целевого запаса (например, 7 дней), но не меньше дефицита на одну порцию. Причину показывать текстом.

  • Отдельное чтение в API склада, контрактное дополнение оформить так же, как UA1; gateway и frontend обновляются в той же сборке.
  • Считать по событиям периода, без полного replay с клонированием состояния.
  • В интерфейсе — блок или вкладка на странице «Склад». Цены и поставщиков не добавляем.

Готово, когда

На seed-данных продукт с малым запасом и продукт из стоп-листа получают предложение с объёмом и причиной, а продукт без расхода и с запасом — нет. Расчёт детерминирован при фиксированном времени, количества точные. Проверены пустая история, нулевой расход, переполнение и граница порога.

FIN-12Горячие предложения учитывают объём под рискомКритерий жюри №3: горизонт, масса под риском, доля порции, top-N.Serving+

Изменить

Брать в расчёт только партии с истечением в пределах горизонта (по умолчанию 72 ч). Скор блюда — сумма по его горящим продуктам: срочность × доля порции, которая реально тратит горящий объём (не больше 1) × доля риска, которую блюдо успеет израсходовать до истечения. Сортировка: скор по убыванию, затем ближайший срок, затем dishID.

  • Отдавать top-N (по умолчанию 10); блюда из стоп-листа исключены.
  • В объяснении: продукт, объём под риском, срок и «нужно продать около N порций».
  • Данные — существующее чтение партий с истекающим сроком у склада. Формула и пример расчёта — отчёт по serving, раздел 5.
  • Новые поля ответа — через контрактное дополнение; строгие схемы gateway обновляются в той же сборке.

Готово, когда

Проба из ревью проходит: рыба (3 кг под риском, 300 г на порцию) стоит выше блюда с 1 г петрушки, рис со сроком 6 месяцев в список не попадает. Порядок детерминирован. Существующие тесты рекомендаций обновлены, а не удалены. Интерфейс показывает новую причину на текущей вкладке «Рекомендации».

FIN-13FEFO и партии видны в интерфейсеКритерий жюри №1 и обязательный М2 на уже готовом API.Frontend+

Изменить

В итоге заказа и в событии истории «Продажа» показать списание по партиям: партия, количество, срок. Данные order.allocations уже декодируются, но нигде не выводятся. На странице остатков дать раскрыть продукт и увидеть его партии через UA1 GET …/warehouse/products/{productID}/batches в порядке FEFO. Перевести сгенерированные типы с C2 на composed UA1.

Готово, когда

После заказа видно, из каких партий и в каком порядке списан каждый продукт. У продукта виден список партий с остатком, сроком и оставшимся временем. api:check сверяет UA1, тесты декодеров и рендера проходят, на 390 строки не вылезают за карточку.

Доставка и показ по ссылке

FIN-05Образы соответствуют проверенным сервисамПочинить зависающий тест Gateway; восстановить Feedback pipeline, если он участвует.Service owners+

Изменить

Сверить current remote CI и registry с финальными commit.

  • Gateway: зависание TestExpiryEndsTheStreamAfterPeekConfirmsIt не исправлено. Коммит-исправление 136a3fe уже входит в main 9a8461e, а CI на этом коммите завис на том же тесте (9 мин 52 с, таймаут 10 мин), поэтому образ main не опубликован. Тест читает поток без дедлайна и зависит от гонки фейковых часов с созданием таймера: дать чтению дедлайн и сделать продвижение часов детерминированным.
  • Feedback: использовать существующий production target; CI ветки checkpoint ссылается на удалённую цель otp-smoke-probe. Test fixture не может стать production owner.

Готово, когда

CI gateway на финальном main зелёный и образ опубликован. У каждого участвующего компонента записаны exact source SHA, CI run, OCI revision и image digest. Чужой/старый SHA не закрывает gate. Publication выполнена только по отдельному поручению.

FIN-06Актуальная версия запускается из FactoryПеренести существующие scripts/configs в поддерживаемый candidate Compose.Factory+

Изменить

Собрать Auth, Gateway, Warehouse, Serving, готовый Frontend и existing proxy. Включить существующие private config/key setup, Auth bootstrap и readiness. Повторный start сохраняет authority и owner secrets. Backend ports остаются во внутренней сети.

Feedback вынести в отдельный необязательный профиль: для старта ему нужны SMTP, бот Telegram и VPN, а анонимная форма лендинга зависит от Auth. Основная сборка не должна от него зависеть.

Готово, когда

Новый checkout воспроизводит запуск без файлов чужой рабочей директории. Cold/repeated start и restaurant ready проверены. Сборка без профиля feedback стартует и проходит сценарий FIN-09. Auth volume сохранён; README содержит запуск/stop/reseed. Candidate проверяется до переключения selected pins.

FIN-07Демо воспроизводится существующим seedЗафиксированные данные и public API; без генератора нагрузки.Factory+

Изменить

Перенести нужные demo data в tests/examples или existing dev/examples. Использовать supported API и безопасные repeat identities. Только явный изолированный demo project; никакой записи Auth JSON вручную или автоматического seed пользовательской authority.

Данные склада и заказов живут в памяти, поэтому после любого рестарта стенд по ссылке пуст. Для стенда нужна процедура пересева одной командой. Допустим и автоматический seed изолированного демо-проекта при пустом состоянии. Данные подобрать так, чтобы на показе были видны стоп-лист, горячие предложения, предложение поставки и партии с близким сроком.

Готово, когда

Есть каталог, рецептуры и партии для всех текущих сценариев, включая FIN-11 и FIN-12. Повтор в одном epoch безопасен. После in-memory reset выполняется явный fresh-epoch seed без автоматического повтора старых unknown заказов. На ВМ после рестарта данные восстанавливаются одной командой, процедура описана в README.

FIN-08Доставить уже готовый интерфейсExisting frontend stack и реальный API. Новых разделов не добавляем, пустые скрываем.Frontend owner+

Изменить

Получить от текущего разработчика точные commits/зависимости готового стека. Исправить только дефекты existing flows. Подготовить его сборку и SHA image. Публикация по отдельному поручению; write scope разработчика сохраняется.

  • Скрыть пустые «Меню» и «Аналитика» вместе со ссылками из сайдбара и плиток «Обзора», если их не успеем наполнить.
  • Убрать вход в организации на фейковых данных или явно пометить экран как демо.
  • Поставить меню и стоп-лист на тот же минутный такт, что и рекомендации, чтобы экраны не расходились при обрыве SSE.

Готово, когда

Frontend gates проходят, interface commit воспроизводим. Login, склад/партии, заказ/отказ, стоп-лист, рекомендации и просрочка работают на настоящих Auth/Gateway. Ни одна ссылка не ведёт на пустую страницу или фейковые данные. Mock screenshots не дают live acceptance.

FIN-09Проверить одну сборку и выложить её по ссылкеЖивой сценарий, точные identities, деплой на существующую ВМ и проверка по публичному адресу.Factory + owners+

Изменить

Пройти login → поставка → остатки/партии → заказ → отказ → стоп-лист → горячие предложения → предложение поставки → просрочка → подтверждение списания. Проверить SSE/refetch, reload, роли и восстановление peers. Затем подготовить exact pins/commands/rollback и по поручению развернуть ту же сборку на existing VM/NPM/HTTPS. Критерий ТЗ — «решение задеплоено и доступно по ссылке», поэтому деплой — последний шаг этой работы, а не отдельная будущая задача.

Готово, когда

Все шаги подтверждены для одной assembly; изменения source требуют affected recheck. Сценарий повторён по публичной ссылке https://ровный-ход.empty-lab.ru, стенд засеян по процедуре FIN-07. Local ready, published и deployed фиксируются раздельно. Публикация/deploy требуют поручения и readback. Demo smoke не заменяет полный backend acceptance.

Если останется время

FIN-10Состояние от снапшота; меньше полного копированияДоработать имеющуюся projection. На объёмах демо выигрыш незаметен, поэтому после пунктов для защиты.Warehouse+

Изменить

Использовать existing snapshot/recovery и хвост событий. Измерить командные и read paths; убрать доказанное копирование всей растущей истории минимальным owner-local изменением. Сохранить atomic publication и изоляцию readers/snapshots.

Почему не в обязательной части: по данным приложенного ревью, 1000 заказов обработаны примерно за 0,84 с суммарно. Это исходное измерение ревью, а не новый benchmark текущей сборки. Правка ядра event sourcing перед защитой рискованна, а нагрузку, на которой рост заметен, создал бы только генератор, которого в этой работе нет.

Готово, когда

Snapshot+tail совпадает с full replay по состоянию, FEFO, command results и expiry index. Failed append и concurrent read безопасны. На одинаковых корпусах 1000/4000/8000 заказов измерены latency/allocations до и после. Новые аналитические функции не добавлены.

Почему считать от снапшота — правильно

Такой механизм уже есть в Warehouse. Его нужно довести до быстрых существующих операций, а не добавлять новую функцию. Направление верное, но это FIN-10: он выполняется после пунктов для защиты.

Проверенный снапшот + события после него = актуальное состояние

Снапшот ускоряет восстановление, но сам не убирает полную копию состояния при каждом batch и чтении. Нужна доработка copy/projection paths с сохранением атомарности.

Аналитика не приоритет. Текущий snapshot не содержит все движения за период: для них нужны события периода или историческая projection. Новые отчёты откладываем.

Что сохраняется

FEFO, exact quantities, доступ и роли, SSE/refetch, JSON authority Auth и текущий in-memory режим Warehouse/Serving. Просрочка требует подтверждения списания человеком. Рекомендации меняют только формулу ранжирования и текст причины (FIN-12), сам механизм и вкладка остаются.

Предыдущие планы и их полный qualification backlog отменены. Исторические manifests/results сохраняются без нового PASS. Добавления FIN-11/12 получают явное контрактное дополнение; текущая приёмка определяется FIN-пунктами и необходимыми repository gates.

Что откладываем

Д3/Д4, новые страницы аналитики, генератор нагрузки, Grafana, персистентность склада, оптимизацию копирования (FIN-10), если на неё не останется времени, v4, новую инфраструктуру и редизайн.

Пакет стабилизирует текущую версию и закрывает обязательный М6 в минимальном виде. Полное выполнение дополнительной части ТЗ этим не заявляется.

Порядок и время

Сначала FIN-01–FIN-04 и FIN-05 (без них нет образов и стабильной сборки), затем FIN-11–FIN-13 параллельно с FIN-06–FIN-08, последним — FIN-09 с деплоем. Проверки планируются по необходимому объёму и не расширяются без новой причины. CI на final SHA, digest и readback остаются условиями приёмки; лимит времени не превращает незавершённую проверку в PASS. Перед реализацией оценить трудоёмкость пунктов. Дату защиты пользователь предложил опустить; календарный дедлайн в этом документе не задаётся.

Основание: последнее указание пользователя, исходное ревью, текущие source mechanisms Auth/Serving/Warehouse и существующая backend specification.

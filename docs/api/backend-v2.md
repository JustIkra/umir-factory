# Backend contract 2.0.0-draft.2

C1 candidate, 2026-10-13, Europe/Moscow. This is a proposed implementation contract under the authorized backend plan. C2 must approve its complete content identity before any service line starts. It is not a released API or proof of implemented behavior.

The machine contracts are [public OpenAPI](backend-v2-public.json), [private OpenAPI](backend-v2-private.json), and [conformance examples](backend-v2-examples.json). This text defines relational rules that JSON Schema cannot prove. Both OpenAPI documents carry identical common schemas. A contract amendment changes the identity and returns to the C2 gate.

The four binding product policies come from the resolved decision record: Gateway owns scheduled expiry; scoped revoke preserves global User sessions; computed month targets use earlier fold/first valid gap; analytics defaults are 48 physical hours and seven local calendar days. Every other exact protocol value below is a C1 technical choice for review. No open protocol choice is delegated implicitly to an implementer.

## Ownership and compatibility

Auth module identity is `github.com/JustIkra/umir-auth`, Go 1.26.9, initial private contract v1. Auth is the sole writer of `auth.json` and sole Ed25519 signer. The module does not yet exist. Warehouse and Serving own separate restaurant runtimes in one process each. Feedback retains its own durable journal and delivery jobs. Gateway owns browser transport, authorized summary composition, live notifications, and the only scheduled expiry runner. It never computes stock, writes Auth state, signs a token, or receives SMTP credentials.

The current `openapi.yml`, `warehouse-public.yml`, and `warehouse-internal.yml` remain the selected legacy assembly contract. This candidate is a separate major wire version: `/api/v2/r/{restaurantID}/...` is mandatory for business access. Product/dish IDs remain opaque editable strings, percent-encoded once as URL values; User/org/restaurant/session/epoch IDs are canonical lowercase UUIDv4. Query keys and JSON fields are case-sensitive. Reject duplicate/unknown keys, null, a second JSON value, invalid UTF-8, duplicate query values, raw semicolon separators, or unsupported methods. Bodies are bounded to 1 MiB; feedback remains 16 KiB. IDs cannot be `*` or a hidden default scope.

In the new backend topology, old unscoped `/api/warehouse/*`, `/api/serving/*`, and `/api/live` business routes return 400 `InvalidArgument`, `outcome=not_committed` for mutations and `unavailable` for reads, with no dispatch. There is no implicit first restaurant or browser tenant header. The legacy selected topology keeps its existing behavior and acceptance mode independently. `/api/operator/*` remains an alias to Auth-owned session/profile operations: preserve old `operator`/`session` keys and known errors. In aliases, `operator.id` is the migrated User ID, not a restaurant ID. New `/api/v2/me` uses `user`/`session`. The v2 time scalar accepts RFC3339 instants with explicit offsets, including Z; fixed +03:00 validation belongs only to the old selected business API.

Quantities, portions, versions and journal sequences remain canonical decimal int64 strings. Quantity is thousandths of g, ml or pcs: `1000` means one base unit. No floating-point arithmetic, rounding, cross-unit total, negative stock, exponent, leading zero or overflow is allowed. Exact `9007199254740993` is valid. No change to FEFO, immutable proposal composition, actual allocation, or unknown-outcome handling is implied by a route migration.

## Membership and capabilities

Membership has one `orgID`, one `userID`, an optional `orgRoles=[Admin]`, and explicit assignments. Each assignment has immutable `assignmentID`, monotonic `assignmentVersion`, one restaurant in that org, and unique `roles` from Warehouse/Waiter. Multiple assignments are allowed; duplicates for a restaurant are rejected atomically. Membership versions increase on any aggregate change. Revocation targets the specific membership/assignment ID and expected version; it cannot revoke a newer replacement. Invite assignments contain only restaurant roles and cannot grant Admin.

| Preset | Effective capabilities in the selected restaurant |
| --- | --- |
| Warehouse | catalog.read, catalog.write, stock.read, delivery.create, analytics.read, writeoff.confirm, menu.read, recommendations.read, feedback.submit |
| Waiter | menu.read, recommendations.read, order.prepare, order.confirm, order.read, feedback.submit |
| Admin | Union of Warehouse and Waiter in every active restaurant of its own org, plus org.read, org.settings.write, restaurant.create, restaurant.delete, org.delete, membership.manage, invitation.manage, org.summary.read, feedback.read, feedback.export |

`user.org.create` is a User-global operation, requiring an active authenticated User without requiring an existing organization membership. It is not a business JWT permission. Being a member elsewhere does not prevent it. A creator atomically becomes the new org's first Admin. Employees have no org management capabilities. Role union is calculated independently per restaurant. Warehouse in A and Waiter in B never combine. Auth returns the authoritative capability set; Gateway maps a route to an operation ID and checks fresh Auth on every request. IDs in path/body must agree with that context. Unknown/missing/deleted/cross-org scopes fail closed. Admin summary does not grant wildcard business access.

Auth serializes last-admin checks with the proposed final aggregate and mutation. An active org must retain an active Admin. Concurrent removals of its last two Admins permit at most one; the second returns 409 `LastAdmin`, no state/mail mutation. Authorized org deletion ends the active lifecycle and is allowed. Normal invitation acceptance binds the verified email to the authenticated User, or creates a new invited User; it grants exactly the saved active assignments.

## Browser and Auth transport

Preserve the source session policy: password 8–32 Unicode code points, no trimming/normalizing/truncation; PHC Argon2id verifier, credential version and existing login identity migrate unchanged. Ordinary sessions have 30-minute idle and eight-hour absolute duration. RememberMe fixes expiry at login + 30 physical days; activity never extends it. Maximum 32 sessions per User, evict oldest atomically. Password change succeeds only after durable commit and revokes every session of that User; logout-all also does so. Scoped role revoke/cascade increments scoped access versions and keeps other scopes and the global session valid.

Secure cookies remain `__Host-umir_operator_session` and `__Host-umir_operator_preauth`: HttpOnly, Secure, SameSite=Strict, Path=/, no Domain. Explicit loopback development uses the existing names without `__Host-`/Secure. Ordinary session cookie has no browser expiry; remembered cookie has the fixed absolute deadline. Auth stores SHA-256 digests, never raw cookie values. Auth returns a raw session token only in private `SessionIssued`; Gateway sets the cookie after confirmed persistence and removes the token from public JSON. A lost/unknown persistence result sets or clears no success cookie and returns the corresponding unknown error. Exact completion returns the same recoverable token after restart using Auth-encrypted result material.

Every unsafe browser route, including anonymous feedback, login and challenge flow, requires exact configured Origin, `Sec-Fetch-Site=same-origin` when present, and the synchronizer CSRF token bound to session/preauth. `GET csrf` may issue preauth and never extends a session. Preauth lasts 30 physical minutes, capacity 1024 per process. Challenge binding includes the initiating session or preauth digest; proof alone never authorizes a different browser. Gateway strips browser Authorization, service keys, user/org/tenant/role headers, internal context headers, gateway cookies, CSRF and activity before business dispatch. It rejects attempted browser internal credentials. No internal token, proof, cookie, password, OTP, key or email body is logged.

Each Auth private façade route mirrors the corresponding public Auth request body. Only the Gateway's configured `X-Umir-Service-Key` may use it. `X-Umir-Session`, `X-Umir-Preauth`, `X-Umir-CSRF-Token`, `X-Umir-Activity` carry verified browser context privately. Gateway enforces Origin; Auth independently verifies CSRF/session binding. A private csrf result is `CsrfTokenView` for a live session or `PreauthIssued` for a newly created anonymous context; Gateway installs the preauth cookie and emits only csrfToken. Profile responses and every protected response are no-store.

Foreground authorized business dispatch persists idle extension before dispatch. Definite storage failure blocks dispatch. `/me` retains the existing rule: if extension definitely fails it can return 200 with the already persisted deadline. Unknown persistence enters fail-closed recovery. Exact `X-Umir-Activity: background`, SSE, token validation, registry, scheduler and access-check never extend idle time. Every new request uses current Auth state; unavailable Auth yields 503 and no protected dispatch.

Existing login capacity stays two active verifications/eight queued; five failed credential verifications per rolling 60 seconds impose 60-second cooldown. Existing password-change policy stays five actual wrong current-password verifications in 60 seconds, then 60-second cooldown. The fifth atomically revokes only its calling session, returns 429 `PasswordChangeRateLimited`, `sessionRevoked=true`, Retry-After, and clears that cookie; other sessions remain valid. During cooldown `sessionRevoked=false`. Oversized currentPassword fails validation before verification and does not consume the counter. A new login does not clear the cooldown. HTTP 422 carries typed fieldErrors; successful password change remains 204. Transport unknown is never authentication success.

Auth storage format is `schemaVersion=1`, `aggregateRevision` as positive decimal string and complete collections `users`, `organizations`, `restaurants`, `memberships`, `sessions`, `invitations`, `challenges`, `mailJobs`, `idempotency`, `lifecycleIntents`, `tombstones`. Store wire identity objects plus owner-private verifier, session digest/versions, challenge encrypted secret/proof, recoverable response material and job delivery state. Those secrets are excluded from all public schemas. One writer lock spans process lifetime; validate the complete aggregate, fsync temporary file, rename and fsync directory on the same durable volume. A definite failure preserves the previous revision; ambiguous replacement enters recovery and returns unknown. Corrupt/unknown schema, invalid references, duplicate identity or lock contention fails readiness and grants no access. Migration stops old writers, protects a backup, preserves deadlines/verifier/credential versions, assigns explicit legacy org/restaurant and Europe/Moscow settings version 1, then validates the complete aggregate. No business state is migrated from Auth. Rollback must preserve revocations and never run two writers.

## Internal JWT and consumer calls

Exact issuer: `urn:umir:auth`. Header: `alg=EdDSA`, `typ=JWT`, unique opaque kid. Ed25519 only; no none, HMAC, algorithm fallback, embedded jwk/jku/x5u or duplicate header/claim keys. Audience is a nonempty exact allowlisted array of `umir-warehouse`, `umir-serving`, `umir-gateway`, `umir-feedback`; each target must be included. Lifetime is exactly 60 physical seconds: `nbf=iat`, `exp=iat+60`. Require `iat<=now`, `nbf<=now<exp`; zero clock leeway. Clocks must be synchronized; missing/invalid clocks fail readiness. jti is UUIDv4. Reject unknown claim shapes and missing claims.

User claims: `kind=user`, `sub=userID`, `sid`, session_version, credential_version, access_version, org_id, tenant_id, time_zone, settings_version, lifecycle_version, operation, permissions, azp=`umir-gateway`, plus issuer/aud/time/jti. Versions are canonical positive decimal strings. Claims are a captured current Auth decision; services validate signature, time, audience, subject kind, route tenant, epoch header where required, operation ACL and their actual caller identity. Service JWTs do not establish instantaneous in-flight revocation; acceptance before local close may complete.

`POST /internal/auth/v1/authorize` accepts a private session token, restaurant, public operation ID, audiences and activity. Auth recomputes current membership/session and settings. Caller-supplied permissions, org, roles or timezone are forbidden. Audiences must equal the operation's fixed target set; a caller cannot request a broader audience. Auth signs minimum necessary permissions for that operation, including only the required consumer capabilities. Public response never contains AuthorizationResult/token. `access-check` returns RestaurantAccess without minting or activity extension.

Every private listener additionally verifies its per-caller `X-Umir-Service-Key`, with a constant-time comparison and explicit caller allowlist. Gateway→Auth, Auth→runtime, Gateway→business/Feedback, Serving→Warehouse each use separate secrets. Keys authenticate caller transport and never sign JWTs. Serve private listeners only on the private network; no published ports. Missing/invalid transport credentials return 401 Unauthenticated; an invalid JWT returns 401 InvalidToken, unavailable keys return 503 AuthUnavailable, and valid credentials with a forbidden caller/operation return 403 Forbidden. TLS with certificate/hostname validation is required off the isolated test network. Factory tests may use ephemeral synthetic credentials and isolated plain HTTP internally. Never trust a forwarded caller header from the browser.

Gateway cannot invoke consumer paths with its transport key; Serving cannot use a forwarded token to call public stock, delivery, catalog write or final writeoff. Forwarding through Serving retains the same user/sub/tenant and operation, never creates a wider token. Warehouse checks the consumer capability and operation pairing, not a Warehouse role preset. Only an authorized human `kind=user` plus `writeoff.confirm` can confirm a writeoff.

Scheduler: Gateway's service credential requests Auth service-tokens for one restaurant and current Warehouse epoch, operation `expiry.due`, sub=`service:gateway`, kind=service, aud=[umir-warehouse], permissions=[expiry.due], azp=umir-gateway. It cannot call final writeoff. Runtime registration/close tokens belong to Auth alone, sub=`service:auth`, one exact target/restaurant/epoch, permission runtime.register or runtime.close. Auth rejects another caller requesting these. Anonymous feedback uses kind=anonymous, sub=service:gateway, aud=[umir-feedback], permission and operation feedback.anonymous.submit; it has no user/org/tenant. Business services reject anonymous claims.

Auth exposes authenticated JWKS with public OKP/Ed25519 signing keys only. Publish a next key at least 60 seconds before switching signing kid; retain the previous key at least 60 seconds after its last issuance. No more than active/next/previous three keys. Services refresh at most every 30 seconds and once on unknown kid; absent discovery/unknown key fails closed. A valid already cached key may verify until its documented overlap ends; it never replaces new-request Auth access checks. Emergency key revocation requires coordinated private cache invalidation; this stage promises only the stated 60-second token window. Auth signing material is a private mounted secret, not `auth.json`, browser, Gateway or logs.

## Tenant lifecycle and epochs

Every Warehouse, Serving and Gateway start generates a new UUID epoch. Runtime status returns service, epoch, ready and tzdata version. Registry lists current Auth revision, complete active/deleting entries and durable restaurant tombstones. A missing/unavailable/partial registry never means an empty successful registry or permission to delete other runtimes. In this stage registry is one complete bounded document: at most 10,000 restaurants; overflow returns 503, not truncated success.

Creation commits Auth entities, creator membership when applicable, idempotent result and a registration intent atomically; response is 201 with lifecycle=registering until all required peers acknowledge ready for their exact current epochs. No business reads/writes start while registering or after a peer epoch changes. Gateway's Auth authorization checks the current peer epoch readiness. Auth owns retry/reconciliation: one serial worker, attempts bounded to five seconds each, exponential delays 1/2/4/8/16/30 seconds capped at 30 seconds indefinitely while intent remains pending, shutdown cancellation. It obtains peer status, issues epoch-bound register tokens, installs empty runtimes, receives readiness acknowledgments, and durably records current-epoch ready. Business services also request reconciliation at startup using their own credentials; readiness remains false until complete. New restaurants use the same path after startup.

Each accepted creation/deletion has an immutable UUIDv4 operationID, issued independently of the caller's opaque commandID and durably committed with its intent and accepted result. Exact command replay or Auth command recovery after a lost reply/restart returns that same operationID and original acceptance result. Lifecycle GET uses this UUID and the returned orgID; it never interprets an opaque commandID as a UUID. Polling after cutoff retains the initiating-User/global-session exception below.

LifecycleResult.services contains exactly one entry per (restaurantID, service), for every restaurantIDs member and each of warehouse, serving, gateway, ordered by restaurantIDs input order then that service order. Each entry requires restaurantID and lifecycleVersion. LifecyclePeerReadiness requires an exact current acknowledged epoch for ready/closed. Unacknowledged peers appear as pending with the current epoch if known; if the peer status is unavailable, omit epoch and keep pending without inventing an identity. Duplicate/missing pairs, out-of-scope restaurant IDs or inconsistent versions are invalid responses. RuntimeReadiness in RegistryEntry services and runtime register/close replies still requires epoch and carries the same explicit association and must agree with their envelope/route. Lifecycle ready requires every pair ready at current epochs; deleted/cleanup=complete requires every pair closed at current epochs. A peer restart returns its pair to pending until reconciliation; historical closed state is insufficient.

Registration is idempotent by saved operationID, restaurantID, service, expectedEpoch and lifecycleVersion. Same epoch never resets business state. Wrong epoch returns 409 RuntimeReset; old readiness never satisfies a new epoch. A deletion marker/higher lifecycle version/tombstone overrides registration and denies new runtime creation. Local registry update/close is serialized with command admission. Expected epoch header is required on every business POST/PUT/DELETE, including read-by-POST evaluation; resolution GET includes the original saved Warehouse epoch in required X-Umir-Runtime-Epoch on consumerCommand, consumerOrder and consumerAttempt. Validate current scope access, then compare epochs before looking up any ID; a reused ID in a new epoch cannot resolve an old attempt. A fresh caller gets epochs from previous context/readiness results, never guesses them. Old epoch mutation/resolution returns 409 `RuntimeReset`, outcome=indeterminate; it never starts a new command. Empty state in a new epoch is not evidence of an old refusal or success. New business action requires an explicit fresh command ID/epoch. Auth does not reconstruct stock/proposals/attempts.

Deletion accepts DELETE with commandID and Admin scope. Auth atomically records immutable affected entity IDs, cutoff/access versions, lifecycle=deleting, tombstones, suppressed invitations and cleanup intent/result. Return 202 with cleanup=pending. Global Users, credentials, sessions and neighboring scopes remain. New auth decisions deny access immediately after that commit; existing requests may complete before local close. Auth closes Warehouse, Serving and Gateway epochs idempotently and retries the saved intent after restart. One peer failure keeps deleting/pending; it never rolls back access or reports complete. GET lifecycle returns the same accepted operation and per-peer epochs. Only the saved initiating User with a currently valid global session, or a still-authorized own-org Admin, can poll. The initiating User can replay the exact accepted deletion command after scope cutoff; this control-plane exception grants no business, invitation or Feedback access. Once all current peers acknowledge closed, lifecycle=deleted and cleanup=complete. The successful initial DELETE still replays its original accepted result; polling obtains later cleanup state. Deleted IDs can never be registered or recreated; a replacement receives a new ID. Restaurant/org lookups return 410 ScopeDeleted in an authorized scope, cross-scope lookups remain 403.

Tombstones, audit, completed idempotency records, completed outbox evidence and Feedback records have no automatic purge in this stage. Suppress undelivered scoped invitation jobs at delete/cancel/expiry admission; a send accepted earlier can be delivered and is not recalled. No cascade removes Feedback facts or undelivered unrelated jobs. Shutdown cleanup cannot invent outcomes of in-flight business attempts. Service-local tombstones last for the epoch, while durable Auth tombstones and reconciliation restore cutoff after restart. `LastAdmin` applies to active organizations, not the authorized deletion of the organization itself.

## Invitations, OTP and durable retries

Enrollment is closed: private explicit bootstrap creates the initial operator with supplied verifier/profile, never a default password or public signup. A current User may create its own org. An invitation-bound verification creates another User. Login/password reset email challenges only target an existing verified address and cannot enroll a new User. The initial legacy User may have no email until an explicit verified migration; preserve login and never invent an address.

Email comparison uses trimmed NFC and lowercase domain only, matching the existing stricter case-sensitive local-part policy; preserve original delivery/display address. Validate a single unquoted address, at most 254 UTF-8 bytes, no control characters. One active invitation per comparisonEmail + orgID; its saved assignment set must match on retry. Lifetime seven physical days, resend no sooner than 60 seconds, three invitations/mail issues per target in ten minutes and no extension of expiry by resend. Cancel invitation and revoke accepted membership are separate operations. Invitation acceptance checks active scope, identity binding and current assignments atomically; deletion or cancellation wins over a later acceptance.

OTP preserves the stricter existing bounds: six digits; ten-minute fixed lifetime; 60-second resend gap; at most four issues per challenge, three target issues per ten minutes, five wrong verifications then locked; 60 issues globally per ten minutes, 300 verification events per minute, 4096 challenges maximum. Store challenge/proof binding to purpose, invitation or verified User, credential version, initiating preauth/session, comparisons and attempts durably. At now>=expiresAt a fresh verification fails. Verified proof is one-use, retains recoverable completion material for at least 24 physical hours; completed command/idempotency evidence remains until explicit future retention policy. A fresh completion after proof expiry fails; exact committed completion replays before expiry checks. password_reset requires newPassword and forbids rememberMe; login allows rememberMe and forbids newPassword. New password follows the same 8–32 rule. Reset revokes all prior sessions and atomically issues one replacement session. Invited-user completion atomically creates User, membership, session and proof consumption; existing-User acceptance never changes its password.

Auth idempotency namespace is `(actorID or initiating preauthDigest, operationID, orgID/restaurantID when applicable)`, then commandID. Fingerprint is SHA-256 over a versioned canonical tuple of operation, actor, exact scope and validated canonical input; do not include fresh JWT, current time, or current timezone. Sensitive password/proof input uses a secret keyed digest within the canonical fingerprint tuple, never plaintext audit. Same key/same fingerprint returns original typed result; same key/different fingerprint returns 409 CommandConflict and does not mutate state. Exact replay precedes expiry/settings version checks but still requires current access, surviving scope and original actor. Revoked/deleted scope denies replay without changing the recorded outcome, except the narrowly authorized deletion-result/polling exception above. A durable `unseen` lookup is a statement about Auth's own recovered store; a transport/ambiguous write stays unknown until recovery. Command lookup is restricted to the requesting actor's namespace. New v2 login/display-name/password bodies add commandID; old operator aliases retain their old bodies and recovery limitations. Logout uses the session digest as its natural idempotent revoke identity. Auth command lookup returns a completed operationID/httpStatus/aggregateRevision plus a typed original response tagged by its schema name, or unseen/unknown. It never exposes a raw session token. requiresSessionRestore instructs an exact retry of the original completion/login through Gateway to recover the saved cookie, never a fresh login or session. Auth results include aggregate revision, resource and stable job IDs. A commit, challenge transition, membership and corresponding outbox acceptance share one aggregate replacement.

Mail jobs: pending→sending→sent, retry, unknown, failed or suppressed. At most three attempts, delays 60 and 300 physical seconds; interrupted sending recovers as unknown, retries under the same job ID. SMTP timeout can cause duplicate delivery. Stable queue/job creation is exactly once; actual mail delivery is not. Private synthetic SMTP is required in tests. Production TLS/hostname validation, announced PLAIN/LOGIN selection and explicit Hello from the verified baseline remain. Feedback's independent SMTP/Telegram failure does not fail Auth; no Gateway email send is added.

## Expiry, final writeoff and FEFO

Warehouse owns atomic due-expiry preparation and serializes it with every fresh stock/menu/evaluation/order operation. At now>=expiresAt, remaining usable stock becomes pending_writeoff, quantity stays physical, and exactly one `BatchExpiryPending` schemaVersion=2 fact is appended. Available excludes pending; FEFO/recommendations never allocate it. Gateway alone schedules expiry-runs using current per-restaurant service JWTs; Warehouse has no timer. Repeated runs create no duplicate transition and no final writeoff. C0 exact Gateway 6053cd817d47f780ef8ef69e4b29918fa08cd6a7 and Warehouse 986d23f975631f390c32357f22096a053f3905ac source evidence establishes this scheduler baseline, not future runtime acceptance.

Authorized human final writeoff is one tenant/epoch/command/fingerprint-bound operation. Serialize the pending state and residual quantity check. `BatchWriteoffConfirmed` schemaVersion=2 stores actorUserID, confirmedAt, actual residual quantity, base unit and eventID. Exact replay returns that fact; a different command against the already written-off batch returns 409 AlreadyWrittenOff, not_committed for the new command. Never create another fact or retarget a command. Final writeoff of an available batch returns 409 NotPendingWriteoff. Historical `BatchExpired` schemaVersion=1 still means final writeoff with WrittenOffQuantity; no reinterpretation as pending. JournalRecord adds restaurant/epoch envelope metadata without changing historical payload. Unknown event type/schema fails the report with 503 UnknownEventSchema; do not drop it.

GET /api/v2/r/{restaurantID}/warehouse/writeoffs/commands and its private counterpart /internal/warehouse/v2/r/{restaurantID}/writeoffs/commands resolve final-writeoff attempts with required commandID, batchID and X-Umir-Runtime-Epoch. Gateway obtains fresh human writeoff.confirm authorization with audience umir-warehouse; Waiter-only, scheduler and Serving consumer credentials cannot use this port. This passive read never appends, retries, prepares expiry, generates event IDs or changes a command. Validate access and original epoch before lookup; mismatch returns 409 RuntimeReset/indeterminate even if the ID is reused in the new epoch. GET transport failure is unavailable and says nothing about the original action.

The final-writeoff namespace is (restaurantID, runtimeEpoch, commandID), shared across authorized humans. Compute commandFingerprint as lowercase SHA-256 of UTF-8 compact JSON with exactly these fields in this order: {"operation":"writeoff.confirm","orgID":<verified orgID>,"restaurantID":<route UUID>,"runtimeEpoch":<original epoch>,"batchID":<exact opaque ID>}. For canonical JSON strings, escape quotation mark and backslash, use \b/\t/\n/\f/\r for those controls, and lowercase \u00xx for other U+0000..U+001F controls. Encode all other Unicode scalar values directly as UTF-8, including slash and U+2028/U+2029; reject unpaired surrogates. Do not normalize Unicode or use optional HTML/non-ASCII escapes; no whitespace, commandID or actor is included. Confirmation and passive lookup use this same fingerprint. Compare a retained fingerprint before exposing its result: a changed batchID for the same command returns 409 CommandConflict, outcome=unavailable on GET (not_committed for a rejected new POST), never the other result. Same command by another authorized human returns the original outcome and original actor; it cannot reattribute a fact. New commands competing for one batch serialize, with one committed residual writeoff and AlreadyWrittenOff/not_committed for each losing command.

WriteoffCommandLookup always carries verified context, requested commandID/batchID and computed fingerprint. observation is committed/committed with the original immutable ScopedWriteoffResult, pending/unknown for a retained unresolved attempt, unseen/unknown when no result can be proved in the same epoch, or rejected/not_committed with an owner-recorded definite refusal. The outer context is the observation context; a committed nested result retains its original context/time/version/actor/event/quantity. Corresponding tenant/epoch/IDs/fingerprint must agree. Rejected.error.outcome must be not_committed. Pending/unseen must not include a result or refusal. No inference from history or pending-batch absence replaces this protocol. A changed epoch produces the typed error instead of an unseen response. Serving consumer.order.resolve retains its existing order-only models and cannot read human final-writeoff results.

Fresh stock GET can commit pending preparation before scheduled tick. Already-expired intake atomically appends DeliveryReceived schemaVersion=2 with BatchV2 captured settings/tzdata and the pending transition; it never finally writes off that intake. Its committed version/invalidation must be published even if the following analytics calculation fails. Gateway processes context/version before reporting the calculation failure. Warehouse emits committed invalidation metadata in response headers `X-Umir-Committed-Version` and `X-Umir-Invalidation-Required: true`, plus the tenant/epoch from the authenticated route and `X-Umir-Runtime-Epoch`; these are private response metadata and Gateway removes them from browser headers. Lost replies may prompt a redundant invalidation, never a final writeoff. Failed preparation returns explicit unavailable and no partial stock. Movements can still read the captured journal when only stock preparation failed.

Recommendations use the existing Serving service and Warehouse FEFO evaluation of one portion per dish. Sort by earliest actually allocated expiry then dishID. Reasons include every allocation at that minimum expiry, sorted productID/batchID. No reservation, portion-count estimate or second ranking engine. Confirmation rechecks current stock and preserves immutable accepted proposal/replacement semantics. Unknown commit/retained attempt must be resolved before a new evaluation or retry, in the same tenant/epoch. Every Serving scoped result carries warehouseEpoch in ServingContext; immutable OrderProposal stores the same warehouseEpoch. Consumer evaluation/commit/resolution use that saved peer epoch, never substitute a fresh epoch after Warehouse restarts. Loss of either Serving or saved Warehouse epoch returns RuntimeReset/indeterminate for the original proposal/attempt. A fresh recommendation/evaluation may capture a new peer epoch only as a new operation.

## Catalog ID suggestion

For product or dish in one explicit restaurant, suggest the smallest free positive integer as a canonical decimal string starting at 1, with no sign, leading zeros or fixed-width/int64 bound. Occupancy is exact opaque string equality in that kind's catalog: 01, 1.0 and manual Unicode IDs do not occupy 1; 1,2,4 yield 3. Product and dish namespaces, and T1/T2 namespaces, are independent. Repeated queries do not reserve, append or change stateVersion. Manual IDs remain editable and are stored exactly; atomic creation checks the final supplied ID, never renames it, and returns the existing ProductConflict/DishConflict on a competing definition. Query failure is unavailable, never an invented suggestion. An unknown creation must be resolved in its original epoch before any fresh action.

## Timezone and calendar protocol

Organization settings are durable IANA timeZone plus monotonic settingsVersion, inherited by every restaurant. Only its Admin patches with expectedSettingsVersion and commandID. Unknown zone: 422 UnknownTimeZone, no mutation. Missing packaged tzdata: 503 TimeZoneDataUnavailable and failed readiness, no Local/UTC fallback. Load IANA data explicitly and report the packaged version at readiness; all time-consuming containers must use the same data version. Manual instants are validated but their offset need not equal the org offset. Civil localDateTime requires matching zone data; a fold requires offset or occurrence=earlier/later (if both, they must agree). Unspecified ambiguous input returns 422 AmbiguousLocalTime; gap returns 422 NonexistentLocalTime. No silent normalization. Supply creation requires the existing non-unique delivery number and accepts TimeInput for created/manufactured/received times; received>=manufactured and accepted operation time>=received/created remain instant comparisons.

Day shelf life is value×24 physical hours, checked for overflow. Month shelf life converts manufacturedAt to the captured org zone, advances the full calendar month count, clamps day to target month's last day and keeps civil time. Fold chooses earlier instant; gap chooses the first valid instant at or after the target civil value, not preservation of minute offset through the gap. A wholly skipped target date follows that computed gap rule. Store resolved expiresAt, timeZone, settingsVersion and tzdata version in the new supply event; replay never recomputes them. Existing recorded expiresAt, recordedAt, order times, session/JWT/invite/OTP TTLs and FEFO facts remain immutable after zone change.

Fresh timezone-sensitive write/filter compares expected version with current verified Auth settings and returns 409 SettingsChanged before new calculation. A retained exact command/unknown candidate is looked up using its original fingerprint and captured settings before that check. The current Auth access decision must not reject such a permitted retry solely for the old settingsVersion. A changed payload with the old command ID conflicts. No retained record in a reset epoch returns RuntimeReset/indeterminate instead of a stale-settings refusal. An accepted in-flight request finishes using its captured settings even if the profile changes later and reports that version. Subsequent requests fetch new settings. Calendar cursor under new settings returns RefreshRequired.

Calendar date boundaries use the first valid instant of that date and the earlier repeated midnight. A wholly missing requested boundary date returns 422 SkippedDate. Requested movements use fromDate and inclusive throughDate, both or neither, resolved to `[start(fromDate), start(dayAfter(throughDate)))`; validate the successor boundary too. Default is today and six preceding local dates in current org settings. A day can span 23/25 hours; never use date count×24h. Maximum 366 local dates, riskHours integer 1..8784 (366×24), default 48 physical hours. Risk cutoff=evaluatedAt+riskHours×1h. Expiring stock is available with expiresAt<=cutoff, and excludes already expired pending stock.

## Analytics, pagination and organization summary

Stock and movements capture one tenant epoch/state version and event prefix; stock is independent of the movement period. For each product/base unit, onHand=available+pendingWriteoff, expiring<=available. No total across units/products. Movements aggregate only committed DeliveryReceived quantities, actual confirmed OrderPlaced allocations, historical BatchExpired final quantities, and BatchWriteoffConfirmed residual quantities by Event.RecordedAt in the half-open period. Pending, rejected, proposed, unknown and duplicate event IDs do not contribute. Products with movements and zero current stock remain rows. Exact integer addition and unit integrity are checked for overflow/mismatch.

Filters are productID exact or case-folded NFC substring search of product name, maximum 100 code points; both intersect. Sort productID ascending by UTF-8 byte order, then baseUnit. Apply server filters before paging. Limit defaults 100, maximum 500. Query arrays in org summary use repeated restaurantID values; all other query duplicates are rejected. Cursor is an opaque server-issued unguessable handle bound to actor, tenant, epoch, stateVersion, prefixSequence, normalized filters, limit, period, risk cutoff, applied settings and next index. Never decode/trust browser cursor contents. Retain the captured immutable report for five physical minutes with at most 128 active reports per tenant; exhausted capacity is 503, evicted/expired/version-unavailable cursor returns 409 RefreshRequired with refreshRequired=true. Every page repeats identical identity/period/cutoff. New settings, scope, epoch, actor or filters invalidate it. End page omits nextCursor, never null. Coverage states current epoch start and complete=false when requestedFrom<coverageFrom; return only available facts, availableFrom=max(requestedFrom,coverageFrom), with that explicit limitation. An incomplete covered segment is never labelled full history or zero sales before coverage.

Gateway `GET /api/v2/orgs/{orgID}/analytics/summary` requires current own-org Admin and a nonempty list of up to 100 explicitly selected restaurant IDs; each must belong to that org and be currently authorized. It sends separate Warehouse stock and movements requests per restaurant with distinct Auth tokens. Do not merge products, add units, use wildcard tenant or create org business state. Return one item per requested ID in input order: ok with both captured reports or unavailable with typed error. If either report for a restaurant fails, its whole item is unavailable; no fake zero report. Status complete/partial/unavailable represents all/some/no successful restaurants, HTTP 200 for typed partial results. Cross-org IDs fail the whole request with 403 before dispatch; missing expectedSettingsVersion gets 400. Each restaurant's own epochs, settings, stateVersion, times, units and coverage are preserved; no globally atomic snapshot is promised. Summary retrieves complete per-restaurant reports, including their pages, within five-second target request deadlines; a failure to finish paging is explicit unavailable. Successful summary items use CompleteStockReport and CompleteMovementReport: concatenate every captured page's items in order, preserve the report's context/page identity and period/cutoff/coverage fields, and omit nextCursor. Unlike standalone pages, these complete arrays have no 500-row cap. Validate identical identity and metadata across all pages within each report and reject missing/duplicate rows or a repeated cursor; any identity drift, timeout, unavailable cursor or paging failure makes that restaurant unavailable without stock/movements. The two reports may have distinct captured versions/times; preserve each independently. There is no summary cursor or silent truncation.

## Failure and consumer signatures

Every wire method and request/result schema is fixed in the two OpenAPI documents and recorded in the C1 manifest. Consumer-owned Go ports use local typed equivalents, not imports of a peer's production packages. Signature notation is `Method(context.Context, Request) (Result, error)`; error must preserve typed code/outcome and cause. Gateway AuthClient: Authorize(AuthorizationRequest) AuthorizationResult, AccessCheck(AccessCheckRequest) RestaurantAccess, ServiceToken(ServiceAuthorizationRequest) Token, AnonymousToken(AnonymousAuthorizationRequest) Token, Registry(empty) Registry, plus each `authFacade*` operation's exact request/result. Gateway AccessChecker uses AccessCheckRequest and never activity extension. SchedulerCredentialProvider uses ServiceAuthorizationRequest for expiry.due only. Auth TokenSigner: Sign(UserClaims|ServiceClaims|AnonymousClaims) Token; only Auth composition supplies it. Auth RuntimeRegistry: Status(empty) RuntimeStatus, Register(RegisterRuntime) RuntimeReadiness, Close(CloseRuntime) RuntimeReadiness for one explicit restaurant/service. Serving WarehouseClient uses consumerMenu/Evaluate/Commit/Command/Order/Attempt signatures and the scoped catalogue reads with the same Auth-issued token. Warehouse authorization port: Validate(rawToken, callerIdentity, routeTenant, operation, expectedEpoch) validated Claims; it does not trust browser DTOs. Feedback authorization validates token against ScopedFeedback before journal admission.

Auth AggregateRepository locally uses Load(context.Context) (ValidatedAggregate, error) and Commit(context.Context, expectedRevision, completeNextAggregate) (CommitResult, error), with CommitResult outcome committed/not_committed/unknown and persisted aggregateRevision. Inject Clock.Now() Instant, IDGenerator.NewID() EntityID, PasswordVerifier.Verify(verifier,password) result, ChallengeSecrets digest/seal/open operations and MailSender.Send(job) delivery outcome. Domain code reads neither wall clock nor environment. Storage implementation fields/Go package layout are private; published wire models above are exact consumer values.

| Failure | HTTP | Outcome and retry |
| --- | --- | --- |
| Definite input/auth/ACL refusal before mutation | 400/401/403/422 | not_committed for that mutation; unavailable for a read |
| Conflict, LastAdmin, SettingsChanged, already written off | 409 | not_committed for fresh mutation; do not infer status of an original unknown attempt |
| Deleted authorized scope | 410 | not_committed for a new action; stored old outcomes remain unchanged |
| Auth definite storage failure | 503 AuthStorageUnavailable | not_committed; dispatch prohibited |
| Auth ambiguous replacement | 503 AuthUpdateOutcomeUnknown | unknown, same key/payload recovery only |
| Service transport timeout/malformed reply | 502/504 UpstreamUnavailable | unknown for modifying POST, unavailable for GET; no automatic new command |
| Business epoch loss / passive absent result after reset | 409 RuntimeReset | indeterminate, no automatic retry of old action |
| Missing tzdata, registry or stock calculation | 503 | unavailable for report; expose committed preparation metadata when present |
| Invalid/expired report cursor | 409 RefreshRequired | unavailable, explicit refresh |
| Rate/capacity policy | 429 RateLimited + Retry-After | definite refusal for this fresh input |

An absent order/attempt in the same live epoch remains the inherited passive Unseen/unknown rule; it is never proof of not_committed. Only the owner can state a definite refusal. Where a read-by-POST evaluates without writing a command, authoritative read failure uses unavailable; its transport failure still preserves unknown observation. Error `retryable` means the same identity may be queried/retried under the stated owner rules, never that a new action is safe. Errors contain no secrets or evidence of another tenant. The optional details object reports current epoch/settings/refresh only in an authorized scope. Capability check failure never invokes the owner. A successful Auth cookie/profile compatibility error keeps its existing typed OperatorError fields as specified in the OpenAPI alias.

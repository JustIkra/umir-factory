# Архитектура Go для этапа в памяти

Дата: 2026-10-10. Часовой пояс: Europe/Moscow.

Этап создаёт бизнес-сценарии warehouse и serving, заменяемые хранилища и совместные проверки без HTTP. [Бизнес-спецификация](business-core.md) определяет поведение и приёмочные сценарии. Здесь задана выбранная для реализации организация Go-кода; пакеты и тестовый runner ещё не созданы. Имена пакетов являются техническим выбором для плана, а не новыми бизнес-сущностями.

## Направление зависимостей

Чистая архитектура требует направлять зависимости исходного кода к бизнес-правилам. Сценарий обращается к внешнему механизму через свой порт; внешний адаптер реализует этот порт. Это [правило зависимостей](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html), а не требование иметь одинаковое число слоёв в каждом репозитории.

В Go интерфейсы обычно определяет потребитель, а конструктор реализации возвращает конкретный тип. Интерфейс нужен для используемого поведения, а не для каждого типа с именем Service. Эти рекомендации приведены в [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments#interfaces). Для этого проекта заменяемые границы — EventStore, SnapshotStore, ProposalStore и небольшие порты склада для serving.

| Пакет | Содержимое и допустимые зависимости |
| --- | --- |
| `internal/domain` | Значения, валидация и чистые бизнес-расчёты; стандартная библиотека. Не читает env, не запускает таймеры и не обращается к хранилищам. |
| `contract` | Собственные значения входов/выходов сервиса, коды результатов; стандартная библиотека. В serving также экспортирует используемые потребительские порты для сборки между модулями. Не содержит HTTP/ORM-моделей, внутренних карт состояния или бизнес-алгоритмов. |
| `internal/application` | Сценарии, координация и интерфейсы собственных хранилищ. Зависит от domain и собственных contract; не импортирует адаптеры. |
| `internal/adapters/memory` | Конкретные реализации хранилищ; зависит от интерфейсов и значений application/domain. Выполняет атомарность, конфликты и изоляцию копий. |
| `bootstrap` | Публичная точка сборки в памяти: создаёт конкретный Runtime и предоставляет вызовы сценариев с типами contract. Зависит от application и адаптеров. Не содержит FEFO, правил подтверждения или восстановления. |
| `cmd/server` | Читает настройки, собирает приложение, управляет жизненным циклом HTTP и фоновых обработчиков. Текущий HTTP остаётся healthz; бизнес-маршруты относятся к следующему этапу. |
| `tests/testsupport` и файлы `*_test.go` | Фикстуры, управляемые часы, обёртки ошибок и построители тестовых данных. Производственные пакеты их не импортируют. |

Порты хранилищ определяются рядом с их потребителем в application. Публичные порты serving в contract — узкая граница межмодульной сборки; они используют только собственные значения serving. Это сознательное размещение экспортируемого контракта, а не общий пакет интерфейсов для всей системы. Сборка через обычные конструкторы достаточна; DI-контейнер и архитектурный framework на этом этапе не требуются.

Даты Go-контракта передаются как полные time.Time. Исходное текстовое значение без времени обязан отклонить входной адаптер до преобразования; по готовому time.Time нельзя определить, был ли исходник датой без времени. В каркасе в памяти текстового API нет: проверяются смещение, порядок дат и корректный момент, включая допустимую полночь. Строгая проверка исходной строки войдёт в следующий этап входного адаптера.

Все внутренние объекты одной реализации получают общий механизм сериализации warehouse. Разделение файлов и компонентов не создаёт независимых владельцев остатков. Порядок допуска и полная публикация команды остаются правилами business-core.

## Владельцы портов и состояния

| Владелец | Порт или состояние | Условия замены реализации |
| --- | --- | --- |
| Warehouse application | EventStore | Атомарный полный набор, expectedVersion, commandID/отпечаток, чтение результата, различение отказа и неизвестного исхода. |
| Warehouse application | SnapshotStore | Проверенный полный снапшот, атомарная монотонная публикация и прежний корректный снапшот при сбое. |
| Serving application | ProposalStore | Неизменное содержание, pendingCommandID и атомарная замена/supersededBy. |
| Serving contract | OrdersWarehouse | EvaluateOrder, CommitAcceptedOrder и чтение записанных результатов до загрузки временного предложения. |
| Serving contract | CatalogWarehouse | GetProducts, GetDishCatalog, GetDish, RegisterProduct и DefineDish. |
| Serving contract | MenuWarehouse | EvaluateMenu на одной паре evaluatedAt/stateVersion. |

Сами InventoryState и индекс истечения остаются закрытыми проекциями warehouse. Очереди истечения не нужен интерфейс. now и newID передаются функциями. Чистые расчёты получают неизменяемое значение и не вызывают часы повторно. Ошибки хранилищ не преобразуются в дефицит ингредиентов или успешный заказ.

## Сборка двух модулей без сети

Warehouse и serving остаются независимыми Go-модулями. Производственные пакеты serving не импортируют warehouse, и warehouse не импортирует serving. Каждый сервис публикует только собственные contract и bootstrap для вызова из проверочной сборки. Общий доменный модуль и шестой репозиторий не добавляются.

Совместные проверки будут созданы в `umir-factory/tests/business`, отдельном тестовом Go-модуле. Его bridge должен реализовать порты serving, вызывать конкретный warehouse Runtime и явно переводить значения между двумя contract. Перевод сохраняет commandID, proposalID, lineNo, количества, evaluatedAt/stateVersion, результаты и коды ошибок. Он не оценивает наличие продуктов, не выбирает партии и не принимает решения о продаже.

Совпадающие по полям именованные Go-типы разных пакетов не делают сигнатуры методов одинаковыми. Поэтому Runtime warehouse не объявляется автоматически реализацией порта serving. Проверка соответствия bridge интерфейсам выполняется компилятором; преобразования проверяются отдельными тестами.

Правило [internal packages](https://go.dev/doc/go1.4#internalpackages) запрещает фабрике импортировать внутренности соседнего сервиса. [Workspace Go](https://go.dev/doc/tutorial/workspaces) позволяет работать с несколькими локальными модулями, но не отменяет это ограничение. Основная логика серверов остаётся internal по [рекомендациям Go о структуре серверного проекта](https://go.dev/doc/modules/layout#server-project).

Планируемый автономный Go-модуль `tools/assembly-checks` предоставляет команды business, check-images и smoke. Python не используется по уточнению пользователя от 2026-10-10; существующие Python-проверки сборки будут заменены и удалены после проверки соответствия. Пока новые инструменты не реализованы, текущий workflow ещё вызывает прежние скрипты.

Команда business создаёт временный go.work с тестовым модулем и двумя сервисами и запускает `go test -race ./...` в тестовом модуле. Обязательный абсолютный factory-dir определяет расположение тестов и соседних checkout независимо от cwd. Режим CI получает два полных SHA явно, проверяет их и использует отдельные временные checkout; SHA берутся из выбранных образов фабрики. Общий go.work и машинные replace-пути не сохраняются в сервисных репозиториях. Обычные проверки каждого сервиса выполняются с `GOWORK=off`. CI вызывает собранный бинарник, чтобы сохранить код дочерней проверки; go run используется только для интерактивной проверки успеха/ошибки.

Проверочная сборка не заменяет транспорт двух контейнеров: вызовы в памяти существуют в одном тестовом процессе. Будущий HTTP-адаптер serving реализует те же порты после определения сетевого контракта, предотвращения поздней записи и восстановления pending после перезапуска.

## Проверки первой реализации

1. Собственные domain/application пакеты проверяются без сети и реального ожидания времени.
2. Одни и те же контрактные проверки хранилищ применяются к адаптерам в памяти, а позднее — к постоянным адаптерам.
3. Ошибки до записи, после записи и при обновлении проекций внедряются обёртками зависимостей и тестами владельца. Общие тестовые fault switches в производственные модели не добавляются.
4. Bridge проверяет преобразование всех полей и сохранение технической неопределённости. Совместные сценарии проверяют реальную бизнес-логику обоих сервисов.
5. Race detector и тесты изоляции копий проверяют читателя V во время записи V+1, предложения, результаты EventStore и захваченный снапшот.
6. Приложение владеет lifecycle worker: запуск явный, отмена и завершение управляемые. Тесты выполняют сохранение пошагово или запускают worker с управляемой зависимостью; доменные таймеры и sleeps не нужны.

Секция 12 business-core задаёт обязательные сценарии. Дополнительно проверяются несколько причин рекомендации с одинаковым ближайшим expiresAt и фактическими количествами из разных партий.

## Что требуется перед подключением HTTP

Сначала проходят контрактные и совместные проверки в памяти. Затем определяется схема запросов, ответов и ошибок, включая определённый отказ, записанный результат и неизвестный исход. Gateway передаёт запросы, frontend отображает эти состояния; бизнес-решения остаются в сервисах.

Параллельная [спецификация передачи gateway/frontend](gateway-frontend-handoff.md) позволяет подготовить эту границу с HTTP-моками и Figma до подключения реальных сервисов. Её transport seams — http.Handler и http.RoundTripper; доменный BFF в gateway не добавляется. Реальное сетевое восстановление требует отдельной приёмки владельца ядра, даже если mock-этап уже завершён.

При подключении новых пакетов к cmd/server нужно обновить Dockerfile: сейчас Go-образы копируют только go.mod и cmd. COPY должен включить созданные производственные пакеты; тестовые данные в образ не включаются. Выбор постоянной базы, HTTP-пути, инструменты observability, численный RPS и долговременное хранение относятся к своим последующим этапам.
